Chapter 1: Prometheus Fundamentals (Architecture, Trade-offs & Scrape Loops)

Prometheus is a graduate-level CNCF project designed for active, pull-based metrics collection from dynamic cloud environments. Originally created at SoundCloud, it was specifically engineered to address the limitations of push-based agents, which frequently lead to network congestion, socket exhaustion, and a complete lack of visibility into down-target health. By pulling metrics via HTTP GET requests on a `/metrics` endpoint, Prometheus shifts the resource burden of monitoring from the application container to the monitoring infrastructure itself. This model provides immediate down-state detection through the `up` metric, indicating if a target is unreachable.

The trade-off of a pull-based monitoring system is the dependency on a robust Service Discovery mechanism to locate active targets and the need for a Pushgateway to buffer short-lived batch jobs. When a target is scraped, Prometheus establishes a TCP connection, reads the exposition format payload, parses it into internal memory structures, and immediately writes it to the TSDB Head block. This ensures that the scrape operations are highly efficient and decoupled from disk writes.

Compared to legacy systems like Nagios, which rely on executing scripts that spawn heavy processes and consume host CPU, Prometheus is incredibly lightweight. Compared to SaaS offerings like Datadog or New Relic, it is self-hosted, keeping all performance data local and eliminating expensive data egress fees. Compared to general-purpose time-series engines like InfluxDB or Elasticsearch, the Prometheus TSDB is strictly optimized for numeric timestamp-value pairs, achieving superior write throughput and storage compression.

# Example of Prometheus scrape configuration for static and dynamic targets scrape_configs: - job_name: 'api-server' scrape_interval: 15s scrape_timeout: 10s metrics_path: '/metrics' static_configs: - targets: ['api-service.prod.svc.cluster.local:8080']
SRE OPERATIONAL RUNBOOK NOTE

Production scaling requires understanding that pull-based systems put the network load on Prometheus itself. If you have 10,000 pods scraped every 10 seconds, Prometheus will establish 1,000 connections per second. Make sure to optimize TCP reuse by configuring keep-alive timeouts appropriately and using HTTP proxies if traversing WAN segments.

CRITICAL SRE WARNING

Never use the Pushgateway as a general-purpose aggregator for push metrics. The Pushgateway does not aggregate metrics automatically; it acts as a buffer. If multiple replicas push to the same job/instance index, they will overwrite each other's metrics, resulting in data loss.

Chapter 2: Complete Prometheus Component Details & Architecture Blueprint

Every Prometheus instance runs as a single process containing several modular engines. The Scrape Manager handles target scheduling based on user-defined configurations. It coordinates with the Service Discovery (SD) Manager to listen for dynamically discovered targets. The SD Manager maintains a set of target groups and updates the Scrape Manager when endpoints are added, updated, or removed.

Once targets are discovered, they pass through the Relabeling Engine, which applies rule-based labels to filters. The Storage Engine (TSDB) is the destination for all scraped samples. It buffers data in memory (Head block) and handles disk writes to the Write-Ahead Log (WAL) and persistent blocks.

The Rule Evaluator is an independent internal loop that runs query expressions against the TSDB at configured evaluation intervals. If an alerting rule evaluates to true, the Rule Evaluator transitions the alert state to Pending or Firing and ships active triggers to the Alertmanager. Alertmanager is a separate microservice (usually deployed as a StatefulSet) that deduplicates, groups, and routes these alerts to notification receivers such as PagerDuty, Slack, or Webhook backends.

Chapter 3: Prometheus Data Model & Time Series Layout

At its core, the Prometheus data model is multi-dimensional. A Time Series is uniquely identified by its metric name and a set of key-value pairs called Labels. Every unique combination of label values defines a completely separate time series in the database. A sample is a single data point within a time series, consisting of a float64 value and a millisecond-precision epoch timestamp.

Internally, Prometheus maps every time series to a unique 64-bit integer called a Series ID. When data is ingested, the label names and values are stored in an inverted index (postings list). This index allows queries to quickly locate all Series IDs matching specific labels (e.g. `env="production"` and `method="POST"`) without scanning the raw samples.

High cardinality occurs when a label has an extremely large set of unique values (such as user IDs, request IPs, or temporary container hashes). High cardinality causes a series explosion, creating millions of unique series IDs. Each series ID requires memory inside the TSDB Head block for indexing, leading to rapid RAM exhaustion and slow query execution.

# Inverted index postings example (conceptual visualization) LabelName='env', LabelValue='prod' -> Postings List: [102, 105, 203, 305] LabelName='app', LabelValue='api' -> Postings List: [102, 203, 401] # Query matching {env='prod', app='api'} performs an intersection of the two postings lists: # Result: [102, 203] (Series IDs to look up)
SRE OPERATIONAL RUNBOOK NOTE

Calculate cardinality regularly using the TSDB status endpoint: `GET /api/v1/status/tsdb`. Monitor the metric `prometheus_tsdb_head_series` to track series growth and alert when it exceeds pre-established capacity limits.

CRITICAL SRE WARNING

Never include raw dynamic values like request IDs, session tokens, or timestamps in Prometheus label keys or values. Doing so will create an infinite number of time series, crash your Prometheus pod, and corrupt the TSDB index.

Chapter 4: Core Metric Types (Counters, Gauges, Histograms, Summaries)

Prometheus exposes four main metric types, each serving a distinct operational purpose:

1. Counter: A cumulative metric that only increases or resets to zero on restart. It is used to track events like total requests, errors, or CPU seconds. Never calculate rates or averages directly on a raw counter; always use functions like `rate()` or `increase()` which are designed to detect and compensate for counter resets.

2. Gauge: A metric that represents a single numerical value that can arbitrarily go up or down. Examples include memory usage, CPU load, queue length, or active threads. Gauges are analyzed using instant queries or time-averaged aggregators like `avg_over_time()`.

3. Histogram: A client-side bucketed representation of observations (like request latencies). It provides a count of events and a sum of values, grouped into configurable cumulative buckets (e.g. `le="0.1"`, `le="0.5"`). Histograms allow the server to calculate quantiles (e.g., 95th percentile latency) across multiple target replicas using the `histogram_quantile()` function.

4. Summary: Similar to a histogram, a summary calculates configurable quantiles (e.g., p95, p99) over a sliding time window. While summaries are highly accurate and require less processing power on the Prometheus server, they are calculated on the client side and cannot be aggregated across multiple replicas or instances.

# PromQL to calculate 95th percentile latency from a histogram over 5 minutes: histogram_quantile(0.95, sum by (le, job) (rate(http_request_duration_seconds_bucket[5m]))) # PromQL to calculate rate of requests: sum by (status) (rate(http_requests_total[5m]))
SRE OPERATIONAL RUNBOOK NOTE

When defining histogram buckets, ensure they span the expected range of your service response times. If p99 latency falls outside your highest bucket (e.g. your maximum bucket is `le="10.0"` but actual latency is 15s), the `histogram_quantile` function will return an inaccurate linear extrapolation.

CRITICAL SRE WARNING

Do not create histograms with too many buckets (e.g., >30 buckets per metric). Because each bucket behaves like a separate time series, a high-bucket histogram multiplied by multiple label dimensions will trigger severe cardinality issues.

Chapter 5: Core Exporters Deep Dive (Node, Blackbox, KSM)

Because Prometheus relies on pull-based HTTP scrapes, application and infrastructure components must expose their metrics in the Prometheus text exposition format. For components that do not natively support this, Exporters are run alongside them to translate local metrics into Prometheus format:

• Node Exporter: An agent that runs on Linux hosts to expose hardware and OS-level metrics. It reads data directly from kernel subsystems `/proc` and `/sys`, capturing CPU usage, disk I/O, memory allocations, network traffic, and file descriptor limits. It also features a textfile collector that reads directory files to publish custom local metrics.

• Blackbox Exporter: An SRE probing tool. It receives target endpoints from Prometheus and performs active checks over network protocols (HTTP/S, DNS, TCP, ICMP). It returns probe results (latency, response codes, SSL certificate expiration dates) to verify target availability from the outside.

• Kube-State-Metrics (KSM): A Kubernetes agent that listens to the Kubernetes API server and generates metrics representing the state of objects: deployment replicas, pod phases, node availability, PVC bounds, and resource quotas. KSM does not measure system performance; it documents the structural state of the orchestrator.

# Blackbox Exporter configuration module for HTTP probes modules: http_2xx: prober: http timeout: 5s http: valid_http_versions: ["HTTP/1.1", "HTTP/2.0"] valid_status_codes: [200, 302] method: GET fail_if_ssl_not_present: true
SRE OPERATIONAL RUNBOOK NOTE

Always secure Node Exporters with firewall rules (or network policies in K8s). Node Exporter exposes sensitive system details (kernel parameters, active processes) that should never be accessible from the public internet.

CRITICAL SRE WARNING

kube-state-metrics can put significant load on the Kubernetes API server in large clusters. Configure resource caching and limit KSM queries to specific namespaces to prevent API server throttling.

Chapter 6: Service Discovery (Kubernetes, DNS, Consul)

In dynamic containerized environments, static IP target configurations are fragile. Prometheus solves this using Service Discovery (SD). The SD manager dynamically queries target provider APIs to maintain a list of active scrapable endpoints. In Kubernetes, the SD engine watches API server resources including Nodes, Pods, Services, Endpoints, and Ingresses. When a Pod is scaled up or down, the SD engine detects the change and updates the scraping schedule in near real-time.

For non-Kubernetes environments, Prometheus supports Consul SD, where it queries the Consul catalog for registered services. It also supports DNS SD, querying SRV or A records at regular intervals to resolve target IPs. If no native SD integration exists, File SD reads JSON or YAML files on the local disk. When these files are modified (e.g., by an external automation tool or daemon), Prometheus reloads the target list without requiring a server restart.

# Kubernetes discovery configuration for service endpoints scrape_configs: - job_name: 'kubernetes-endpoints' kubernetes_sd_configs: - role: endpoints relabel_configs: - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scrape] action: keep regex: 'true'
SRE OPERATIONAL RUNBOOK NOTE

When using Kubernetes SD in large clusters (>1000 nodes), Prometheus can consume significant memory and CPU just processing API server watch events. Use namespace filters in `kubernetes_sd_configs` and keep-alive limits to minimize resource usage.

CRITICAL SRE WARNING

Make sure your Kubernetes cluster role bindings give Prometheus read-only permissions to nodes, services, endpoints, and pods. Missing permissions will cause silent service discovery failures.

Chapter 7: Scraping Internals, Relabeling & Metric Modification

Scraping is the process where Prometheus performs an HTTP GET to a target, processes the response, and writes samples. The scraping loop is controlled by the `scrape_interval` and `scrape_timeout`. If the target response time exceeds the timeout, Prometheus discards the write and records the target as down (`up = 0`).

Relabeling is a powerful stage that occurs at two distinct phases: before scraping (relabel_configs) and before writing to the TSDB (metric_relabel_configs):

1. `relabel_configs`: Modifies the metadata labels discovered by service discovery. It is used to select which targets to scrape, change the target port, or rewrite the internal path.

2. `metric_relabel_configs`: Applies rules to the metrics returned by a scrape. It allows SREs to filter out noisy metrics, drop specific labels to reduce cardinality, or rewrite metric names before they are written to disk.

# Dropping high-cardinality metrics before they enter the TSDB scrape_configs: - job_name: 'noisy-service' static_configs: - targets: ['localhost:9090'] metric_relabel_configs: - source_labels: [__name__] regex: '(http_request_duration_seconds_bucket|go_gc_.*)' action: drop
SRE OPERATIONAL RUNBOOK NOTE

Use `metric_relabel_configs` to enforce metric quality standards. You can drop developer-level debug metrics or drop client IP labels to keep storage costs under control.

CRITICAL SRE WARNING

If you set `scrape_timeout` larger than `scrape_interval`, Prometheus will reject the configuration. A scrape must complete before the next interval begins.

Chapter 8: TSDB Engine, Storage Blocks & Compaction Loops

The Prometheus Time Series Database (TSDB) is optimized for high-write, low-read monitoring patterns. It partitions data into 2-hour Blocks on disk. When metrics are scraped, they are written to an active in-memory block called the Head Block. Simultaneously, they are written to a Write-Ahead Log (WAL) on disk for durability.

Every 2 hours, the Head Block rolls over, writes its contents to a permanent 2-hour disk block, and creates a new Head Block. The disk block contains a directory with chunk files (compressed raw samples), a metadata file (`meta.json`), and an index file mapped to memory.

In the background, a Compaction Loop runs continuously. It merges multiple adjacent 2-hour blocks into larger blocks (typically 24 hours). This reduces disk usage by deduplicating index entries and removing tombstones (samples marked for deletion by retention rules). This consolidation speeds up query performance.

# TSDB directory layout on disk /data/prometheus/ ├── 01FPZ6P... (2h block folder) │ ├── chunks/ (000001 raw chunk file) │ ├── index (inverted index) │ ├── meta.json (block metadata) │ └── tombstones (deletion offsets) ├── wal/ (write-ahead log directory) │ ├── 000001 (128MB binary segments) │ └── checkpoint.000000/ └── lock (process lock file)
SRE OPERATIONAL RUNBOOK NOTE

Ensure Prometheus runs on high-performance local storage (NVMe SSDs). Compaction loops create intense disk write activity. Using network-attached storage like AWS EBS can cause IOPS starvation, leading to query timeouts and dropped scrapes.

CRITICAL SRE WARNING

Never share the same TSDB directory across multiple running Prometheus instances. The lock file will prevent startup, and manual file modification will corrupt the index.

Chapter 9: WAL (Write-Ahead Log) Architecture & Corruption Recovery

The Write-Ahead Log (WAL) is the durability layer of Prometheus. The Head block keeps recent metrics in RAM, which would be lost if the server crashed. To prevent data loss, every sample is appended to the WAL before being acknowledged in memory. The WAL consists of sequential 128 MB binary segment files.

During startup, Prometheus replays all WAL segments, recreating the Head block's in-memory index and samples. Once the Head block is flushed to a disk block, older WAL segments are deleted. If the Prometheus host suffers an abrupt shutdown or disk full condition, the active WAL segment may become corrupted, preventing the server from restarting.

To recover from WAL corruption, SREs must isolate the corrupted segment. The SRE can use the `prometheus-tool` or delete the corrupted segment, sacrificing the last few minutes of metrics to restore the server immediately.

# Bash commands to diagnose and recover from a corrupted WAL # 1. Identify if Prometheus is in a crash loop: kubectl logs statefulset/prometheus-k8s -c prometheus | grep -i "WAL" # 2. Recovery: Rename the corrupted WAL directory to force a clean replay mv /data/prometheus/wal /data/prometheus/wal.corrupted # 3. Restart Prometheus (it will start cleanly and create a new WAL folder)
SRE OPERATIONAL RUNBOOK NOTE

Monitor `prometheus_tsdb_wal_replay_duration_seconds` to track startup time. If WAL replay takes too long (e.g. >10 minutes), it indicates slow disk read performance or an excessively large Head block size.

CRITICAL SRE WARNING

Deleting the entire WAL folder will result in the loss of all metrics scraped since the last 2-hour block write. Only rename/delete the WAL directory as a last resort.

Chapter 10: Chunks & Storage Block Lifecycles on Disk

Within each TSDB block, sample values are stored in Chunk files. Prometheus uses Gorilla compression, a double-delta float compression algorithm. Timestamps (usually spaced 15s apart) are stored as double-deltas, requiring only a few bits. Float values are XOR'd against the previous sample value. This reduces the storage footprint to an average of just 1.37 bytes per sample.

Historical disk blocks are read-only. Prometheus accesses them using memory-mapping (`mmap`). This OS feature allows the kernel to map the block files directly into virtual memory. Prometheus can query gigabytes of historical data without loading the raw contents into RAM; the OS kernel loads page files on-demand and discards them when memory is needed.

Tombstones are used when deleting metrics (via the administrative API). Instead of rewriting large chunk files, Prometheus writes the target offsets to a `tombstones` file. During compaction, the compactor reads these files and excludes deleted samples from the newly created block.

# Prometheus command-line flags to control block retention and size /bin/prometheus \ --storage.tsdb.path=/data/prometheus \ --storage.tsdb.retention.time=15d \ --storage.tsdb.retention.size=45GiB \ --storage.tsdb.min-block-duration=2h \ --storage.tsdb.max-block-duration=24h
SRE OPERATIONAL RUNBOOK NOTE

Always configure both size-based and time-based retention. Size-based retention (`--storage.tsdb.retention.size`) acts as a safety limit to prevent disk full conditions if metrics volume suddenly spikes.

CRITICAL SRE WARNING

Do not modify the `min-block-duration` and `max-block-duration` flags unless you are an expert. Changing these values can impair the compaction engine and cause fragmented disk blocks.

Chapter 11: PromQL (Query Language, Functions, Vectors)

PromQL is a functional query language designed for evaluating time-series data. It works with two primary vector types: Instant Vectors (a single value for each series at a specific timestamp) and Range Vectors (a list of values over a range of time, like `[5m]`).

Functions like `rate()`, `irate()`, and `increase()` require a Range Vector as input because they calculate change over time. Aggregation operators like `sum()`, `avg()`, and `count()` operate on Instant Vectors, allowing you to combine metrics across multiple labels.

SREs must understand the difference between `rate()` and `irate()`: `rate()` calculates the average rate of change over the entire range window (best for alerting because it smooths spikes), while `irate()` calculates the instant rate of change using only the last two samples in the range window (best for high-resolution dashboards).

# Calculate CPU utilization rate per container, ignoring low values: sum by (container) (rate(container_cpu_usage_seconds_total{container!="POD"}[5m])) * 100 > 80 # Predict disk fill rate over 4 hours based on 1 hour of history: predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h], 14400) < 0
SRE OPERATIONAL RUNBOOK NOTE

Avoid using `rate()` with small range windows relative to your scrape interval. Rule of thumb: the range window should be at least 4 times the scrape interval (e.g. `[1m]` for a 15s scrape interval) to prevent empty query results.

CRITICAL SRE WARNING

Never use the `increase()` function on gauges. `increase()` assumes counter reset logic, which will corrupt calculation results when applied to fluctuating gauge metrics.

Chapter 12: Alertmanager Engine (Routing, Grouping, HA Deduplication)

Alertmanager acts as the central notification dispatcher. It receives active firing events from Prometheus and routes them through a hierarchical Routing Tree based on alert label sets. The routing configuration determines who receives the alert and how they are notified.

To prevent alert fatigue, Alertmanager performs Grouping. It bundles related alerts matching specific labels into a single notification. The timing is controlled by three parameters: `group_wait` (initial buffering window), `group_interval` (delay between subsequent updates), and `repeat_interval` (time before re-sending resolved or active alerts).

For high availability, Alertmanager runs as a cluster using the Gossip Protocol (mesh topology via memberlist). When Prometheus sends duplicate alerts to multiple Alertmanager instances, the replicas communicate over Gossip to deduplicate notifications and coordinate silences, ensuring only one notification is sent.

# Alertmanager HA mesh startup arguments /bin/alertmanager \ --config.file=/etc/alertmanager/alertmanager.yaml \ --mesh.listen-address=0.0.0.0:9094 \ --cluster.peer=alertmanager-peer-1.monitoring.svc:9094 \ --cluster.peer=alertmanager-peer-2.monitoring.svc:9094
SRE OPERATIONAL RUNBOOK NOTE

Configure inhibition rules to suppress redundant alerts. For example, if a node goes down (`NodeDown`), inhibit all pod-level alerts (`PodDown`) running on that node. This prevents spamming on root-cause incidents.

CRITICAL SRE WARNING

If Alertmanager pods lose network connectivity, split-brain behavior can occur. Replicas may fail to coordinate, resulting in duplicate notifications sent to receivers.

Chapter 13: Recording Rules & Query Load Offloading

Dashboards often run complex calculations over long time ranges, which can overwhelm the Prometheus query engine. Recording Rules solve this by pre-calculating expensive PromQL expressions in the background and saving the results as a new, read-optimized time series.

Recording rules are defined in Prometheus configuration groups and evaluated at regular intervals (usually matching the scrape interval). For example, instead of calculating the p99 API latency across 5,000 pods on every dashboard refresh, a recording rule pre-calculates the rate and saves it. The dashboard can then perform a fast query on the pre-calculated metric.

This offloads the query engine, decreases dashboard load times, and saves memory. It also enables longer-term retention of historical trends, as the aggregated series consumes a fraction of the space required by the raw high-cardinality metrics.

# Recording rule configuration syntax groups: - name: custom_rules rules: - record: job:http_inprogress_requests:sum expr: sum by (job) (http_inprogress_requests) - record: instance:node_cpu:ratio expr: 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
SRE OPERATIONAL RUNBOOK NOTE

Create recording rules for all metrics used in high-traffic dashboards or automated alerts. Ensure that recording rule names follow the standard format: `level:metric:operations`.

CRITICAL SRE WARNING

Do not evaluate too many recording rules at very short intervals. If the evaluation time exceeds the group interval, the query engine will lag, creating gaps in your data.

Chapter 14: Hierarchical & Cross-Cluster Federation

Federation allows a Prometheus server to scrape selected metrics from other Prometheus servers. This enables hierarchical and cross-cluster monitoring layouts. In a typical federated architecture, regional Prometheus instances scrape local clusters in detail, while a central Prometheus server scrapes aggregated metrics from the regional instances.

The central server pulls data using the `/federate` endpoint, specifying target metrics via query parameters. This keeps the network overhead low, as only critical, pre-aggregated metrics are sent across WAN links.

Federation is useful for global capacity planning, multi-cluster dashboarding, and centralized alerting. However, SREs must avoid scraping raw high-cardinality metrics over federation, as this can easily overload the central Prometheus server.

# Central Prometheus configuration scraping regional instances scrape_configs: - job_name: 'federate-east' honor_labels: true metrics_path: '/federate' params: 'match[]': - '{__name__=~"job:.*"}' - '{__name__="up"}' static_configs: - targets: - 'prometheus-east.infra.corp:9090'
SRE OPERATIONAL RUNBOOK NOTE

Always configure `honor_labels: true` on federated scrape jobs. This tells the central server to preserve the original labels (like `instance` and `job`) set by the downstream server, rather than overwriting them.

CRITICAL SRE WARNING

Never perform wildcard scrapes like `match[]={__name__=~".+"}` over federation. This pulls all raw metrics across the network, overloading both the source and destination servers.

Chapter 15: Remote Write, Remote Read & Thanos Architecture

Prometheus is designed for short-to-medium-term metric storage. For long-term retention, high availability, and global queries, it must be paired with external storage systems. This integration uses two protocols: Remote Write and Remote Read.

• Remote Write: Prometheus tails its local WAL and streams incoming samples to an external endpoint (e.g. Thanos, Cortex, Mimir, or VictoriaMetrics) using a serialized Protobuf payload over HTTP POST. The streaming uses an internal queuing system with auto-scaling thread pools.

• Thanos Architecture: A popular CNCF framework that extends Prometheus. In a Thanos sidecar setup, a Thanos Sidecar container runs alongside Prometheus. Every 2 hours, it uploads finished TSDB blocks to object storage (like AWS S3). The Thanos Querier then executes global PromQL queries by pulling data from active sidecars (for recent metrics) and the Thanos Store Gateway (for historical object storage data).

# Prometheus remote write configuration with queue tuning remote_write: - url: "http://thanos-receiver.monitoring.svc:19291/api/v1/receive" queue_config: capacity: 10000 max_shards: 50 min_shards: 5 max_samples_per_send: 2000 batch_send_deadline: 5s
SRE OPERATIONAL RUNBOOK NOTE

When using Remote Write, monitor queue performance using `prometheus_remote_storage_sent_bytes_total` and `prometheus_remote_storage_highest_timestamp_in_seconds`. A widening gap indicates queue bottlenecks, which can lead to WAL growth and disk space exhaustion.

CRITICAL SRE WARNING

Remote Write increases the CPU and memory footprint of Prometheus by up to 25%. Ensure you size your Prometheus pods with extra headroom when enabling remote write.

Chapter 16: Kubernetes Cluster Observability Blueprint

Monitoring Kubernetes effectively requires a standardized architectural blueprint. The community-standard solution is the Prometheus Operator (often deployed via the `kube-prometheus-stack` Helm chart). The operator uses Custom Resource Definitions (CRDs) to manage Prometheus, Alertmanager, and their configurations declaratively.

Key CRDs include:

• `Prometheus`: Defines the deployment details of the Prometheus StatefulSet (replicas, storage, resources, remote write).

• `ServiceMonitor` & `PodMonitor`: Define how targets are discovered and scraped. Instead of writing raw scrape configs, SREs define monitors that select services and pods using standard Kubernetes label selectors.

• `PrometheusRule`: Defines alerting and recording rules. The operator automatically compiles these rules into file formats and mounts them to the Prometheus container, triggering dynamic configuration reloads.

# ServiceMonitor custom resource example apiVersion: monitoring.coreos.com/v1 kind: ServiceMonitor metadata: name: payment-service-monitor namespace: monitoring labels: release: kube-prometheus-stack spec: selector: matchLabels: app: payment-api endpoints: - port: metrics interval: 15s path: /metrics
SRE OPERATIONAL RUNBOOK NOTE

Enforce namespace limits on your Prometheus Operator. In multi-tenant clusters, configure the operator to discover `ServiceMonitors` only in allowed namespaces to prevent tenant teams from accidentally overloading the central Prometheus instance.

CRITICAL SRE WARNING

Make sure your `ServiceMonitor` labels match the `serviceMonitorSelector` defined in your `Prometheus` CRD. Mismatched selectors will prevent Prometheus from discovering the configuration.

Chapter 17: High Cardinality Diagnostics & Memory Optimization

High cardinality is a common cause of performance degradation in Prometheus. It occurs when a label contains an excessive number of unique values, creating millions of unique series IDs. Because Prometheus buffers index records in RAM, this causes high memory usage and can lead to OOM (Out Of Memory) crashes.

To diagnose cardinality issues, use the TSDB Status API (`/api/v1/status/tsdb`). This endpoint returns metrics on index utilization, identifying the labels with the most unique values, the largest label names, and the metrics with the highest series counts.

To optimize memory, SREs can drop high-cardinality labels during ingestion using `metric_relabel_configs`, configure scrape limits (`sample_limit`) to restrict targets, and tune the head block parameters to control memory usage.

# Script to find top cardinality metrics from Prometheus API curl -s http://localhost:9090/api/v1/status/tsdb \ | jq '.data.topSeries[] | {metric: .name, count: .value}' \ | head -n 10
SRE OPERATIONAL RUNBOOK NOTE

Implement automated alerts for high cardinality. Alert when the metric `prometheus_tsdb_head_series` exceeds 80% of your tested memory capacity, giving SREs time to locate and remediate the issue before an OOM occurs.

CRITICAL SRE WARNING

Do not execute large query ranges (e.g. `[30d]`) on high-cardinality metrics. This forces the server to load millions of historical index entries, which can trigger a query-time memory crash.

Chapter 18: Horizontal & Vertical Scaling Operations

Scaling Prometheus requires different approaches depending on the bottleneck:

• Vertical Scaling: Adding CPU and RAM resources to the Prometheus host or container. Memory consumption scales linearly with the number of active series. As a rule of thumb, allocate 1.5 GB to 2 GB of RAM for every 1 million active series, with additional headroom for query evaluations.

• Horizontal Scaling: Partitioning the scrape load across multiple independent Prometheus instances. This is achieved using Hashmod Relabeling. Each Prometheus instance scrapes a subset of targets based on a hash of their address. This allows you to scale metrics collection horizontally without a central coordinator.

# Scrape config sharding targets using hashmod relabeling scrape_configs: - job_name: 'sharded-app-scrape' kubernetes_sd_configs: - role: pod relabel_configs: - source_labels: [__address__] modulus: 4 # Total number of shards target_label: __tmp_hash action: hashmod - source_labels: [__tmp_hash] regex: '0' # Only scrape targets that match shard index 0 action: keep
SRE OPERATIONAL RUNBOOK NOTE

When sharding scrapers horizontally, use a central query engine like Thanos Querier or Grafana Mimir to query all shards simultaneously. This provides a unified view of the sharded data.

CRITICAL SRE WARNING

Horizontal sharding splits metrics across different servers. Queries that aggregate data across shards (e.g. calculating total requests across all pods) must be performed by a central querier.

Chapter 19: SRE Incident Recovery Troubleshooting Guide

When troubleshooting Prometheus incidents, SREs typically encounter three main scenarios:

1. Crash Loops due to WAL Corruption: This usually occurs after an ungraceful shutdown. SREs can fix this by locating and renaming the corrupted WAL segment on disk.

2. Out Of Memory (OOM) Crashes: Triggered by a sudden cardinality spike. SREs can recover the server by increasing memory limits, dropping labels at ingestion, or using the `tsdb analyze` tool to identify and remove the offending metrics.

3. Slow Query Performance: Caused by complex expressions or high-cardinality targets. SREs can debug this by checking the query log, configuring query limits, and using recording rules to offload calculation overhead.

# Command to check query logs for slow queries # 1. Enable query logging in prometheus.yaml: # global: # query_log_file: /data/query.log # 2. Inspect query execution times: tail -n 100 /data/query.log | jq 'select(.durationSeconds > 2.0)'
SRE OPERATIONAL RUNBOOK NOTE

Configure a 'dead man's switch' alert. This is a simple alert that is always firing (`expr: vector(1)`). If the Alertmanager stops receiving this signal, it indicates that Prometheus is down or unable to evaluate rules.

CRITICAL SRE WARNING

Do not restart Prometheus while it is writing a Head block to disk (indicated by high disk write I/O). Abruptly stopping the process during a write can corrupt the active disk block.

Chapter 20: Production Operation Best Practices

Follow these SRE best practices to ensure reliable production operations:

1. Use dedicated local SSD storage. Never run the Prometheus TSDB on network file systems (like NFS or AWS EFS), as they cannot support the transactional I/O required for the WAL and index operations.

2. Configure size-based retention limits in addition to time-based retention. This protects the disk from filling up if metrics volume suddenly spikes.

3. Use recording rules for all metrics queried by high-traffic dashboards to reduce server load.

4. Monitor your monitoring system. Deploy a separate, small 'meta-monitoring' Prometheus instance to scrape your primary Prometheus and Alertmanager infrastructure.

# Production Prometheus command-line arguments /bin/prometheus \ --config.file=/etc/prometheus/prometheus.yml \ --storage.tsdb.path=/data/prometheus \ --storage.tsdb.retention.time=30d \ --storage.tsdb.retention.size=180GiB \ --storage.tsdb.wal-compression \ --web.enable-lifecycle
SRE OPERATIONAL RUNBOOK NOTE

Enable the lifecycle API (`--web.enable-lifecycle`). This allows you to reload Prometheus configurations dynamically by sending an HTTP POST request to `/-/reload`, avoiding server downtime.

CRITICAL SRE WARNING

Enabling WAL compression (`--storage.tsdb.wal-compression`) reduces WAL disk usage by up to 50% but increases CPU usage. Ensure your host has sufficient CPU headroom before enabling this flag.

Chapter 21: Prometheus vs Alternatives (VictoriaMetrics, Datadog)

Selecting a monitoring system requires evaluating the trade-offs between self-hosted systems and SaaS platforms:

• VictoriaMetrics: A high-performance alternative to Prometheus TSDB. It supports the Prometheus querying API and Remote Write protocol but offers better compression, lower memory usage, and simplified clustering. It can run as a single binary, making it easier to operate at scale.

• Datadog: A popular SaaS monitoring platform. It is fully managed, eliminating the operational overhead of hosting your own TSDB. However, it introduces significant network data egress charges and vendor lock-in, and costs can scale rapidly with metric volume.

Prometheus remains the industry standard for Kubernetes monitoring due to its deep integration with the CNCF ecosystem and native operator support. SREs often use Prometheus for local metrics collection and forward data to long-term storage platforms for global analysis.

Chapter 22: Real-World Startup & Enterprise Architectures

Monitoring architectures scale with the size and complexity of your infrastructure:

• Startup Architecture: A single Prometheus instance scraping all targets in a cluster, storing metrics on local SSDs, and displaying dashboards with a local Grafana instance. This is simple, cost-effective, and easy to maintain.

• Enterprise Architecture: A multi-cluster, high-availability monitoring pipeline. Each Kubernetes cluster runs a Prometheus instance in Agent Mode (which scrapes targets and immediately streams data via Remote Write, without storing metrics locally). These metrics are sent to a centralized Thanos or Grafana Mimir cluster in a shared services VPC. Thanos aggregates and stores metrics in object storage (AWS S3), while a global Grafana instance queries the Thanos Querier to provide unified dashboards across all environments.

# Enterprise remote write setup for Prometheus Agent Mode /bin/prometheus \ --storage.tsdb.path=/data/prometheus \ --enable-feature=agent \ --config.file=/etc/prometheus/prometheus.yml
SRE OPERATIONAL RUNBOOK NOTE

Use Prometheus Agent Mode for edge clusters. It disables local TSDB storage, query APIs, and alerting loops, reducing memory usage by up to 80% and allowing edge instances to run on minimal resources.

CRITICAL SRE WARNING

Agent Mode cannot evaluate alerting rules locally. All rules must be evaluated on the central Thanos or Mimir cluster, which depends on network connectivity.

Chapter 23: SRE Interview Prep & 75 Core Q&A Bank

Here are key technical questions and answers for SRE interviews covering Prometheus architecture, scaling, and troubleshooting:

Q1: What is the difference between rate() and irate() in PromQL? A1: `rate()` calculates the average per-second rate of change over the entire range window (suitable for alerts). `irate()` calculates the instant rate of change using only the last two samples in the window (suitable for high-resolution charts).

Q2: How does Prometheus handle target downtime? A2: During every scrape, Prometheus automatically records a metric called `up`. If the scrape succeeds, `up` is set to 1. If the scrape fails, `up` is set to 0, indicating the target is down.

Q3: What causes WAL corruption and how do you recover from it? A3: WAL corruption is typically caused by ungraceful shutdowns or disk full conditions. SREs can recover by isolating and removing the corrupted WAL segment on disk, or renaming the WAL directory and restarting the server.

Q4: What is cardinality explosion and how do you diagnose it? A4: Cardinality explosion occurs when a label contains an excessive number of unique values, creating millions of unique series. SREs can diagnose this using the TSDB Status API (`/api/v1/status/tsdb`) to identify the high-cardinality labels.

Q5: Why shouldn't you run Prometheus on network-attached file systems (NFS)? A5: NFS systems cannot support the high-write transaction rates and low-latency disk writes required by the WAL and index operations, leading to IOPS starvation and performance issues.

Chapter 24: Comprehensive Glossary Reference

• **WAL (Write-Ahead Log)**: A database log file used for crash recovery, where transactions are recorded before being applied to memory.

• **TSDB (Time Series Database)**: A database optimized for storing and querying time-series data.

• **Scraping**: The process where Prometheus pulls metrics from target HTTP endpoints.

• **Cardinality**: The number of unique time series in the database, determined by the combination of metric names and labels.

• **Instant Vector**: A set of time-series samples containing a single value for each series at a specific timestamp.

• **Range Vector**: A set of time-series samples containing a list of values over a range of time for each series.

• **Compaction**: The background process of merging multiple small TSDB blocks into larger, optimized blocks.

• **Tombstone**: A database record indicating that a sample has been marked for deletion.

• **Pushgateway**: A buffer for short-lived batch metrics that allows push-based collection.

• **Service Discovery**: The automated detection of active monitoring targets in dynamic environments.
