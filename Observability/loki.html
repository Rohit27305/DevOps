1. Loki Fundamentals

Grafana Loki is a horizontally-scalable, highly-available, multi-tenant log aggregation system inspired by Prometheus. It is designed to be highly cost-effective and easy to operate, as it does not index the full text of the logs. Instead, it indexes only the metadata (labels) associated with a log stream—mirroring Prometheus's label model.

Traditional log search engines like Elasticsearch and OpenSearch index the full text of log messages. While powerful, this index is often larger than the log data itself, requiring expensive RAM, massive SSD arrays, and high operational overhead. Loki's design philosophy trades off full-text search speed to achieve drastically lower storage costs and minimal operational complexity.

Key Concept: Pull vs Push

Unlike Prometheus, which pulls metrics from targets, Loki receives pushed logs from log shippers (like Promtail, Fluent Bit, or Vector) via an HTTP API. However, Loki uses a pull-based querying model where Querier components pull log chunks from object storage to evaluate LogQL queries.

2. Complete Loki Architecture

Grafana Loki can run as a single binary (monolithic mode) or split into independent microservices (distributed mode) to allow fine-grained scaling. Here is how each component works:

  • Distributor: A stateless service that acts as the entry point for log ingestion. It validates incoming log streams, rate-limits requests, and routes logs to Ingesters using a consistent hash ring.
  • Ingester: A stateful service that buffers incoming log entries in memory. It appends logs to active chunks, writes to a Write-Ahead Log (WAL) on disk for durability, and flushes compressed chunks (using gzip or zstd) to object storage every 2 hours (or when target chunk limits are hit).
  • Querier: A stateless service that executes LogQL queries. It queries Ingesters for recent in-memory log entries, and queries object storage for historical log chunks.
  • Query Frontend: A stateless service that sits in front of the Queriers. It splits large queries into smaller intervals, parallelizes query execution across multiple Queriers, and caches query results.
  • Compactor: A stateless service that runs background compaction loops. It merges multiple small index files into single optimized files and applies data retention policies (permanently deleting expired chunks from object storage).
  • Index Gateway: A stateful service that serves index lookups for Queriers, caching index files locally to prevent database locks and latency.
  • Ruler: Evaluates alerting and recording rules against log streams, forwarding active triggers to Alertmanager.

3. Data Model & Streams

Loki organizes logs into **Streams**. A stream is a sequence of log lines sharing the exact same label set. For example, logs from Pod A in the `production` namespace belong to a different stream than logs from Pod B in the same namespace, or even Pod A in the `staging` namespace.

Labels are key-value metadata pairs (e.g. `app="api"`, `env="production"`). In Loki, labels are the only indexed fields. This means that filtering logs by labels is extremely fast, while filtering by text content (e.g. `|= "error"`) requires Queriers to decompress and scan log lines. Cardinality is the number of unique label combinations. High cardinality (like including `user_id` or `request_ip` in labels) explodes streams, causing Ingesters to exhaust memory buffering too many active streams.

4. Log Entry Pipeline Stages

Before log clients ship log lines to Loki, logs pass through a sequence of processing steps called **Pipeline Stages**. These stages parse log lines, extract metadata, and attach labels:

  • CRI & Docker Stages: Standard parsers that extract timestamps and clean log messages from raw container runtime JSON wraps.
  • JSON & Regex Stages: Parse structured log lines (JSON) or use regex to extract key-value fields.
  • Label Stage: Promotes extracted fields (like `level` or `service`) to Loki labels, creating separate indexable streams.
  • Multiline Stage: Merges consecutive lines (like Java stack traces) starting with specific characters (like whitespace) into a single log entry.

5. Log Shippers & Agents

Loki relies on external log agents to tail log files and push them to its HTTP API:

  • Promtail: The default agent, built by Grafana. It integrates deeply with Kubernetes, querying the API server to automatically discover pods, attach metadata labels, and tail logs.
  • Fluent Bit & Fluentd: High-performance, mature log shippers. Ideal for multi-destination pipelines.
  • Vector: Written in Rust, Vector is a blazingly fast log shipper with a powerful VRL (Vector Remapping Language) engine for parsing and filtering log data.

6. Service Discovery In Promtail

Like Prometheus, Promtail uses Service Discovery to dynamically discover scrape targets in dynamic environments:

  • Kubernetes Discovery: Queries the Kubernetes API server for pods and namespaces. Promtail uses pod labels and annotations to decide which logs to tail.
  • File Discovery: Scans local directories using glob patterns (e.g. `/var/log/*.log`).
  • Consul & DNS Discovery: Discovers services registered in Consul or via SRV DNS queries.

7. Ingestion & Push Internals

Logs are pushed to Loki via HTTP POST requests to `/loki/api/v1/push`. The payload format is a Snappy-compressed Protobuf message containing streams, labels, and an array of log lines with nanosecond-resolution timestamps.

Critical limits

Ingesters apply limits to protect themselves:
max_chunk_age: Default 2h. Limits how long a chunk can stay in memory before being flushed.
chunk_target_size: Target size of compressed chunks (typically 1.5 MB). If a chunk exceeds this, it is rolled over and flushed early.

8. Storage & Chunk Engine

Loki splits storage into two distinct components:

  • Chunks: Compressed log entries (compressed in blocks using gzip, lz4, or zstd). Stored in inexpensive object storage (AWS S3, Google Cloud Storage, Azure Blob, or MinIO).
  • Index: The directory map that connects labels and stream fingerprints to target chunk file paths. Today, Grafana recommends using **Single Store TSDB**, which writes index files directly into the same object storage bucket as the chunks, eliminating the need for separate databases (like DynamoDB or Cassandra).

9. Write-Ahead Log (WAL)

The Ingester buffers log streams in memory. If the Ingester pod crashes or is evicted, buffered logs would be lost. To prevent data loss, Loki writes incoming logs to the **Write-Ahead Log (WAL)** on persistent disk before sending an HTTP 200 response to the client.

On startup or crash recovery, the Ingester scans the WAL directory, replays all log segments, and reconstructs the in-memory chunks. Once a chunk is successfully flushed to object storage, the corresponding WAL segments are deleted.

10. Index & BoltDB Shipper

Before TSDB Single Store, Loki utilized BoltDB Shipper to ship local BoltDB index files to object storage. Under this model, Ingesters write index entries to local BoltDB files. The BoltDB Shipper then periodically uploads these files to the object storage bucket.

Queriers download and cache these index files locally to resolve queries. While functional, TSDB index is more modern, offering better compaction, lower read latency, and direct multi-tenant scoping.

11. LogQL Deep Dive

LogQL is Grafana Loki's query language, heavily inspired by PromQL. It supports two types of queries:
Log Queries: Retrieve log lines.
Metric Queries: Calculate metrics from logs (e.g., error rates).

LogQL Query Anatomy:

{namespace="prod", app="api"} |= "error" | json | status = 500

This query:
1. Selects the log stream matching the labels `{namespace="prod", app="api"}`.
2. Filters lines containing the string `"error"`.
3. Parses the log line as JSON.
4. Filters JSON properties where `status` equals 500.

Common LogQL Functions:

  • rate(): Calculates the number of log lines per second over a time range.
  • count_over_time(): Counts the total number of log lines in the range.
  • bytes_rate(): Calculates the volume of log data processed per second.

12. Ruler & Alertmanager

The **Ruler** runs alerting and recording rules defined in LogQL. It queries Loki internally at regular intervals. If a LogQL metric query (e.g. `rate({app="api"}[5m]) > 10`) triggers an alert threshold, the Ruler formats the alert and forwards it to Prometheus Alertmanager, which handles routing, silencing, and Slack/email dispatches.

13. Recording Rules in Loki

Recording rules pre-evaluate expensive LogQL metric queries (like counting error rates over large namespaces) and save the results as Prometheus-compatible metrics. This is highly recommended to speed up dashboard loads, since Grafana can query pre-calculated metrics from Prometheus rather than executing raw LogQL scans over terabytes of logs on every dashboard refresh.

14. Multi-Tenancy Engine

Loki is built from the ground up as a multi-tenant system. In a multi-tenant setup, Loki requires the HTTP header `X-Scope-OrgID` on all push and query requests. The Distributor uses this ID to partition the consistent hash ring, and Ingesters partition chunks and indexes in object storage under the corresponding tenant namespace, ensuring absolute data isolation.

15. Query Frontend & Splitting

Large LogQL queries scanning weeks of history can exhaust Querier memory. The **Query Frontend** acts as a query coordinator:

  • Query Splitting: Splits a large range query (e.g. 30 days) into smaller daily or hourly queries, executing them in parallel.
  • Query Caching: Caches results inside Redis or Memcached. If a user queries the same dashboard panel, the Query Frontend retrieves results from cache and queries Loki only for the most recent log gap.

16. Kubernetes Logging

In a Kubernetes cluster, container engines write logs to the host filesystem at `/var/log/pods/`. Promtail runs as a DaemonSet, mount-binding this directory. It queries the Kubernetes API to translate file paths (which contain pod UUIDs) into clean metadata labels (pod name, namespace, container name) and tails the logs, shipping them to Loki.

17. High Cardinality in Loki

Loki does not index log text; it only indexes labels. Adding high-cardinality values—like user IDs, session tokens, request paths, or container IPs—as labels is a **critical mistake** in Loki.

Every unique label combination creates a separate stream. If cardinality explodes, the Ingester has to allocate thousands of small memory buffers, leading to memory exhaustion (OOM kills) and slow index lookups. Use LogQL parser stages (JSON or Regex) to filter by high-cardinality fields at query time rather than promoting them to labels.

18. Scaling Loki Layouts

Loki supports three deployment layouts:
1. Single Binary Mode: All components run in one process. Good for development and small setups (< 100 GB/day).
2. Simple Scalable Deployment (SSD): Splits Loki into read and write paths. Allows scaling ingestion independently of query loads.
3. Microservices Mode: Every component (Distributor, Ingester, Querier, Frontend, Compactor) runs as a separate deployment, allowing granular scaling.

19. SRE Troubleshooting Guide

Diagnostic Scenarios

1. Ingester Out of Memory (OOM):
Cause: High cardinality labels or ingestion rate spikes.
Fix: Verify labels using `tsdb analyze` equivalents in Loki. Relabel and drop dynamic labels in Promtail.
2. 429 Ingestion Rate Limit Errors:
Cause: Target pushes logs faster than `ingestion_rate_mb` allows.
Fix: Raise `ingestion_rate_mb` (default 4MB/s per stream) and `ingestion_burst_size_mb` in Loki config.

20. Production Best Practices

Golden Rules for Loki SREs

1. Do Not Index Log Fields: Only use labels for service boundaries (app, env, component, namespace).
2. Enable WAL: Always run Ingesters with persistent volumes and WAL enabled to survive restarts.
3. Use Object Storage: Never run local filesystem storage in production; use S3, GCS, or Azure Blob.

21. Loki vs Alternatives

Feature Grafana Loki Elasticsearch / OpenSearch Splunk
Index size Minimal (Metadata only) Massive (Full-text index) Large
Storage Cost Extremely Low (Object Storage) High (SSD arrays) Very High
Query Model LogQL (PromQL-like) Query DSL / Lucene SPL
Resource Bound Query-bound (parallel scans) RAM & Write-bound Storage-bound

22. Real-World Deployments

In enterprise Kubernetes environments, Loki is commonly deployed using the Helm chart in Simple Scalable Mode. The write path (Ingesters, Distributors) handles continuous high-volume log streams, while the read path (Queriers, Query Frontends) scales up dynamically using Horizontal Pod Autoscalers (HPAs) during active incident investigations or dashboard updates.

23. Interview Prep & Outages

Scenario: The Loki disk is filling up, but retention is set to 7 days. Why?
Answer: The Compactor marks chunks for deletion, but the Sweeper deletes them after `retention_delete_delay` (default 2h). If ingestion rate is extremely high, the write throughput may exceed the compaction rate. Check compactor logs for "applying retention" errors and ensure the compactor working directory is on a Persistent Volume.

24. Architectural Glossary

  • WAL (Write-Ahead Log): Persistent disk log where uncompressed in-memory log entries are stored for crash durability.
  • Chunks: Compressed gzip/zstd files containing actual log text entries, shipped to object storage.
  • Memberlist: Gossip protocol used by Loki components to discover each other and maintain the hash ring.
  • Hash Ring: Consistent hashing system used to distribute streams evenly among Ingester pods.
