01 Section 1: AWS Networking Fundamentals Fundamentals ▾

1.1 AWS Global Infrastructure

AWS operates across a layered global infrastructure designed for high availability, low latency, and data sovereignty. Understanding this infrastructure is foundational to designing networks that leverage AWS's physical topology.

┌──────────────────────────────────────────────────────────────────────────┐ │ AWS GLOBAL INFRASTRUCTURE HIERARCHY │ │ │ │ AWS Regions (geographic areas: us-east-1, eu-west-1, ap-southeast-1…) │ │ └── Availability Zones (3-6 per region: discrete data centers │ │ with independent power, cooling, networking) │ │ └── Edge Locations (400+ PoPs for CloudFront/Route53) │ │ └── Regional Edge Caches (larger CDN tier) │ │ │ │ Special zones: │ │ • Local Zones: AWS infra in major metros (LA, Dallas, Miami…) │ │ → single-digit millisecond latency to end users │ │ • Wavelength Zones: compute embedded in telco 5G networks │ │ → ultra-low latency for mobile applications │ │ • Outposts: AWS rack hardware in customer data centers │ │ → run AWS services on-prem with same APIs │ └──────────────────────────────────────────────────────────────────────────┘

1.2 AWS Backbone Network

The AWS backbone is a private, high-throughput, low-latency fiber network interconnecting all AWS Regions, AZs, and edge locations. Traffic between AWS services stays on this backbone — never traversing the public internet unless explicitly configured to do so. This is why cross-region data transfer between, say, us-east-1 and us-west-2 is faster and more reliable than routing through the public internet.

2.1 VPC Architecture

A Virtual Private Cloud (VPC) is a logically isolated virtual network within an AWS Region. It spans all AZs in the region and is implemented via AWS's Nitro-based network virtualization — there are no physical switches or routers; all forwarding decisions are made in software by the hypervisor on every EC2 host.

2.3 Internet Gateway (IGW)

The IGW is a horizontally scaled, redundant, HA VPC component. It performs two functions: provides a target in route tables for internet-routable traffic, and performs NAT for instances with public IPs (maps the instance's private IP to its public/Elastic IP). The IGW itself has no bandwidth limit — your internet throughput is limited by the instance's ENI bandwidth.

hcl
Traffic flow (public EC2 → internet): EC2 (10.0.1.10) sends packet to 8.8.8.8 Route table: 0.0.0.0/0 → igw-xxxxx IGW receives packet, checks EC2's Elastic IP mapping Replaces source IP 10.0.1.10 → 54.x.x.x (public IP) Forwards to internet Traffic flow (internet → public EC2): Packet arrives at IGW destined for 54.x.x.x (public IP) IGW maps 54.x.x.x → 10.0.1.10 (private IP) Forwards to EC2 in subnet

2.4 NAT Gateway

NAT Gateway provides outbound internet access for private subnet resources without exposing them to inbound connections. It is a managed service, deployed per-AZ, with 5 Gbps bandwidth that automatically scales to 100 Gbps. Each NAT Gateway has an Elastic IP for its public-facing address.

hcl
Private EC2 (10.0.10.5) → internet: Route table: 0.0.0.0/0 → nat-xxxxx (NAT GW in public subnet) NAT GW replaces source 10.0.10.5 → Elastic IP (54.y.y.y) Records mapping in its connection tracking table Sends to IGW → internet Internet response → private EC2: Response arrives at IGW to 54.y.y.y IGW forwards to NAT GW NAT GW looks up connection table → translates to 10.0.10.5 Forwards to private subnet Cost: ~$0.045/hr per NAT GW + $0.045/GB processed Best practice: Deploy one NAT GW per AZ to avoid cross-AZ data transfer charges (traffic from AZ-1a private subnet to AZ-1b NAT GW costs $0.01/GB cross-AZ)

2.6 VPC Peering

VPC Peering creates a private networking connection between two VPCs (same or different accounts, same or different regions). Traffic flows through AWS backbone, not the internet. Limitations: non-transitive (if A peers B and B peers C, A cannot talk to C through B), requires non-overlapping CIDRs, and routes must be manually added to both VPCs' route tables.

hcl
VPC A (10.0.0.0/16) ←→ VPC B (10.1.0.0/16) Route table in VPC A: 10.1.0.0/16 → pcx-xxxxxxxx Route table in VPC B: 10.0.0.0/16 → pcx-xxxxxxxx Security Groups: must allow traffic from 10.0.0.0/16 or 10.1.0.0/16 CIDR Limitation: NOT transitive VPC A ←→ VPC B + VPC B ←→ VPC C ≠ VPC A can reach VPC C Use Transit Gateway for transitive multi-VPC routing

2.7 Transit Gateway (TGW)

Transit Gateway is a regional hub-and-spoke network transit hub that enables transitive routing between VPCs, VPNs, and Direct Connect. It eliminates the N×(N-1)/2 peering mesh problem — instead of 45 VPC peering connections between 10 VPCs, you have 10 TGW attachments and TGW handles all routing.

2.8 Elastic Network Interfaces (ENI)

An ENI is a virtual network card — the fundamental networking component attached to EC2 instances. It has: a primary private IP, optional secondary private IPs, an optional public IP (if subnet auto-assigns or manually allocated), MAC address, and references to Security Groups. You can detach an ENI from one instance and attach to another, preserving the IP addresses — useful for quick failover without changing DNS.

2.9 AWS PrivateLink

PrivateLink is the underlying technology behind Interface VPC Endpoints. A service provider exposes their service behind a Network Load Balancer. Consumers create an Interface Endpoint in their VPC, which provisions an ENI with a private IP. Traffic flows from consumer ENI → AWS PrivateLink → NLB → service backend — entirely private, no internet exposure. This enables SaaS providers to offer private connectivity to their services within customer VPCs.

3.1 Longest Prefix Match

AWS route tables use longest prefix match (LPM) to determine the route for each packet — the most specific matching route wins.

hcl
Route Table Example: Destination Target 10.0.0.0/8 → Transit Gateway (least specific) 10.1.0.0/16 → VPC Peering (pcx) (more specific — overrides TGW for this range) 10.1.5.0/24 → VPC Endpoint (most specific — overrides peering for this subnet) 0.0.0.0/0 → NAT Gateway (default route — catches everything else) Packet to 10.1.5.15: Matches 10.1.5.0/24 (/24 is longest prefix) → VPC Endpoint wins Packet to 10.1.99.5: Matches 10.1.0.0/16 (/16 is longest prefix for this address) → Peering wins Packet to 172.16.0.1: Matches 0.0.0.0/0 only → NAT Gateway

3.3 East-West vs North-South Traffic

hcl
North-South traffic: ingress/egress between internet and VPC Internet → IGW → ALB → EC2 (inbound) EC2 → NAT GW → IGW → Internet (outbound) Security perimeter: IGW, WAF, ALB, Security Groups East-West traffic: lateral traffic between resources within AWS EC2 → EC2 (within VPC): local route, only Security Groups evaluated EC2 → EC2 (cross-VPC): peering/TGW + Security Groups EC2 → RDS: within VPC or peered VPC, Security Groups on both Security concern: no default traffic inspection between VPCs Solution: centralized inspection VPC via TGW + Gateway LB (GWLB)

4.1 VPC DNS — The Resolver

hcl
Every VPC has a built-in DNS resolver at VPC_CIDR+2: VPC 10.0.0.0/16 → DNS resolver at 10.0.0.2 (also 169.254.169.253) EC2 /etc/resolv.conf: nameserver 10.0.0.2 search ec2.internal (us-east-1 default domain) us-east-1.compute.internal DNS resolution path for private resources: EC2 → 10.0.0.2 (VPC Resolver) → Route 53 Private Hosted Zone (for internal hostnames like web.internal.example.com) DNS resolution path for public resources: EC2 → 10.0.0.2 (VPC Resolver) → Route 53 Public Hosted Zone (or authoritative nameservers for external domains)

4.3 Alias Records vs CNAME

hcl
CNAME: - Standard DNS record pointing to another hostname - Works at non-apex (sub.example.com → otherdomain.com) - Cannot be at zone apex (example.com cannot be a CNAME — RFC violation) - Incurs an additional DNS lookup - NOT free for Route 53 queries Alias Record (Route 53 proprietary): - Virtual record type — resolves directly to target's IP (no extra lookup) - CAN be at zone apex (example.com → my-alb.us-east-1.elb.amazonaws.com) - FREE for queries to AWS resources (ALB, CloudFront, S3 website, TGW, etc.) - Automatically follows IP changes of the target (ALB IPs change) - Supports health checks Always use Alias records for: ALB, NLB, CloudFront, API Gateway, S3 websites

4.4 Route 53 Health Checks

hcl
Types: HTTP/HTTPS: checks returns 2xx within 4 seconds, every 10 or 30 seconds TCP: checks TCP connection established within 10 seconds HTTP with string match: response body contains specific string (first 5,120 bytes) Calculated: combines results of multiple health checks (AND/OR) CloudWatch Alarm: healthy if alarm state is OK Health checkers: Route 53 operates checkers from multiple global locations (~15 regions) Configurable: threshold of # checkers that must report healthy If 18+ of 15 checkers healthy → record is healthy (configurable %) Integration with routing: Failover routing: R53 stops routing to unhealthy endpoints automatically Weighted routing: 0% traffic to unhealthy; redistributes among healthy

hcl

6.1 Amazon CloudFront

CloudFront is AWS's CDN — a globally distributed network of edge locations (400+) that cache and serve content close to users, reducing origin load and latency. It supports both static content caching and dynamic content acceleration (even uncacheable requests benefit from optimized routing over the AWS backbone).

diagram
CloudFront request flow: User (Sydney) → Route 53 → CloudFront edge PoP (Sydney) │ ├── Cache HIT: return cached content directly (sub-5ms) │ └── Cache MISS: CloudFront → Origin (us-east-1 ALB) Via AWS backbone (faster than internet routing) Cache response for future requests CloudFront components: Distribution: top-level config (domain, origins, behaviors) Origin: where CloudFront fetches content (ALB, S3, API GW, custom HTTP) Behavior: pattern-matched rules (/api/* vs /static/*) Cache Policy: what to cache, TTL, cache key components Origin Request Policy: what headers/cookies/querystrings to forward to origin Response Headers Policy: security headers to add (CORS, HSTS, etc.) SSL/TLS at CloudFront: Client → CloudFront: TLS terminates at edge (must use ACM cert in us-east-1) CloudFront → Origin: can re-establish TLS (origin protocol policy: HTTPS only) Minimum TLS 1.2 enforced; TLS 1.3 supported

6.2 AWS Global Accelerator

Global Accelerator is NOT a CDN — it does not cache content. It provides two static anycast IP addresses (IPv4) that serve as the entry point for your application globally. Traffic from any client is ingested at the nearest AWS edge location and routed over the private AWS backbone to your regional endpoints (ALB, NLB, EC2, EIP).

7.2 AWS Network Firewall

AWS Network Firewall is a managed stateful network firewall service for VPCs, providing deep packet inspection, intrusion detection/prevention (IDS/IPS), and stateful firewall rules at layer 3-7 (including domain/SNI filtering, HTTP/S inspection).

hcl

hcl

Flow logs capture metadata about IP traffic (NOT packet content) at: VPC level: all traffic in/out of VPC Subnet level: all traffic in/out of subnet ENI level: specific instance traffic Fields in flow log records: version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status ACCEPT: traffic allowed by Security Group/NACL REJECT: traffic blocked Destination options: CloudWatch Logs: real-time analysis, CW Insights queries S3: batch analysis, Athena queries, cost-effective for high volume Kinesis Data Firehose: stream to Splunk, OpenSearch, S3 Flow logs do NOT capture: DNS queries to 169.254.169.253 or VPC+2 DHCP traffic Windows license activation traffic Instance metadata (169.254.169.254) Troubleshooting with flow logs: REJECT on SG port → add SG inbound rule ACCEPT then REJECT → NACL blocking (NACL evaluated after SG) No flow log entry → packet never reached ENI (routing issue)

17.1 CIDR Planning Rules

  • Never use 10.0.0.0/8 as your entire VPC CIDR — it's too broad and wastes address space and makes routing ambiguous
  • Use /16 per VPC (/20 minimum for EKS to accommodate pod IP allocation)
  • Plan for growth: a /16 gives 65,536 addresses; a /20 gives 4,096 — production workloads can exhaust smaller ranges
  • Never overlap CIDRs between VPCs that will ever need to communicate (peering/TGW requires non-overlapping)
  • Reserve dedicated large subnets (/20 or /18) for EKS pods (VPC CNI allocates VPC IPs to pods)
  • Use RFC 6598 (100.64.0.0/10) for EKS pods (custom networking) to avoid consuming RFC 1918 space

17.2 Security Hardening

  • Never use 0.0.0.0/0 as a Security Group source for management ports (22, 3389) — use specific IPs or bastion SG
  • Reference Security Group IDs (not CIDRs) between AWS resources for precise control
  • Use VPC Endpoints (Gateway for S3/DynamoDB, Interface for SSM/Secrets Manager) to avoid NAT Gateway costs and prevent internet exposure
  • Enable VPC Flow Logs on all VPCs to S3 for security audit trail (don't rely on CW Logs alone — S3 is cheaper for long retention)
  • Enforce IMDSv2 on all EC2 instances (prevents SSRF-based metadata service attacks)
  • Enable GuardDuty for threat detection (analyzes VPC Flow Logs, CloudTrail, DNS logs automatically)
  • For EKS: enable AWS VPC CNI with Security Groups for Pods to get pod-level network isolation

17.3 Cost Optimization

  • Deploy NAT Gateways per AZ (not per subnet) — one NAT GW per AZ avoids cross-AZ data transfer charges
  • Use Gateway VPC Endpoints for S3 and DynamoDB (free — eliminates NAT GW processing cost for these services)
  • Use CloudFront for content caching to reduce origin ALB traffic and data transfer costs
  • For high-volume S3 access: Interface Endpoint to S3 costs less than NAT GW at >30TB/month
  • Review VPC Flow Logs volume — filtering to only REJECT traffic dramatically reduces CW Logs ingestion costs
  • Right-size NAT Gateway — it costs $0.045/hr per NAT GW + $0.045/GB; consider if workload truly needs NAT

20 Section 20: Interview Preparation — 150 Questions Interviews ▾

20.1 Fundamentals (Q1–Q20)

Q1: What is a VPC and what problem does it solve?

A VPC (Virtual Private Cloud) is a logically isolated virtual network in AWS, implemented via software-defined networking in the Nitro hypervisor. It solves the need for network isolation in a shared cloud environment — without VPCs, all AWS customers' resources would be on the same flat network. VPCs provide IP address space control, routing control, network segmentation, and security boundaries in a multi-tenant environment.

Q2: Explain the difference between public and private subnets.

Public subnets have a route table entry pointing 0.0.0.0/0 to an Internet Gateway (IGW). Resources in public subnets with a public/Elastic IP are directly reachable from the internet. Private subnets have no direct IGW route — their 0.0.0.0/0 points to a NAT Gateway in a public subnet. Resources in private subnets can initiate outbound internet connections (via NAT) but are not directly reachable from the internet inbound.

Q3: Why does AWS reserve 5 IP addresses in every subnet, and which are they?

AWS reserves: .0 (network address), .1 (VPC router — the default gateway for all instances), .2 (DNS resolver — the VPC CIDR+2 address used for DNS queries), .3 (reserved for future use), and .255 (broadcast — not used in AWS but reserved). A /24 subnet has 256 total IPs minus 5 reserved = 251 usable IPs.

Q4: What is the difference between Security Groups and Network ACLs?

Security Groups are stateful ENI-level firewalls: return traffic is automatically allowed regardless of outbound rules; they have only Allow rules. NACLs are stateless subnet-level firewalls: you must explicitly allow both inbound and outbound (including ephemeral port return traffic); they have both Allow and Deny rules evaluated in numbered order. Security Groups are the primary control for instance-level traffic; NACLs are a secondary defense for subnet-level blocking.

Q5: Explain longest prefix match in VPC routing.

When a packet matches multiple entries in a route table, AWS forwards it according to the most specific route — the one with the longest subnet mask. A /24 route (256 addresses) is more specific than a /16 (65,536 addresses) for the same prefix. This allows you to override a broad route (TGW for 10.0.0.0/8) with a more specific one (VPC Peering for 10.1.0.0/16), ensuring traffic to 10.1.x.x uses the peering while all other 10.x.x.x traffic goes through TGW.

Q6: What is an ENI and when would you use a secondary ENI?

An Elastic Network Interface (ENI) is a virtual NIC attached to an EC2 instance. Secondary ENIs are used for: high-availability failover (detach from failed instance, attach to replacement — preserving IP and MAC for licensing), dual-homing (EC2 with one ENI in a management subnet and another in an app subnet), segregation of traffic (different SGs per ENI), and network appliance configurations.

Q7: Explain the difference between a Gateway Endpoint and Interface Endpoint for S3.

Gateway Endpoint: a route table entry using an AWS-managed prefix list targeting S3 or DynamoDB — completely free, no ENI, no DNS changes needed. Traffic stays on AWS network via the route table entry. Interface Endpoint: provisions an ENI with a private IP in your subnet using AWS PrivateLink — costs ~$0.01/hr + data processing. Supports on-prem access (via DX/VPN), FIPS endpoints, and S3 Access Points. Use Gateway Endpoint unless you have a specific reason for Interface Endpoint (on-prem access, FIPS compliance).

Q8: What is VPC Peering and what are its limitations?

VPC Peering connects two VPCs privately (same or different account/region) via AWS backbone. Limitations: non-transitive (A peers B, B peers C, A cannot reach C through B); requires non-overlapping CIDRs; max 125 peering connections per VPC; requires manual route table updates in both VPCs and SG rules using the peer's CIDR. For transitive multi-VPC routing, use Transit Gateway.

Q9: Explain Transit Gateway and how it differs from VPC Peering.

Transit Gateway is a regional hub that enables transitive routing between VPCs, VPNs, and Direct Connect. It eliminates the N×(N-1)/2 peering mesh — with 10 VPCs, TGW uses 10 attachments vs 45 peering connections. TGW supports: multiple route tables for traffic isolation, BGP route propagation from VPN/DX, multicast, inter-region TGW peering, and bandwidths up to 50 Gbps per attachment. TGW costs more than peering ($0.05/hr per attachment + $0.02/GB); peering is free beyond data transfer costs.

Q10: How does a NAT Gateway work? What's the difference from a NAT Instance?

NAT Gateway is an AWS-managed service: receives packets from private subnets, replaces source IP with its Elastic IP, records the 5-tuple mapping for return traffic, forwards to IGW. Managed: auto-scaling (5→100 Gbps), multi-AZ HA within its AZ, no patching. NAT Instance: an EC2 instance with source/destination check disabled, running iptables/NAT rules. More flexible (can be used as bastion, run custom software) but requires manual HA, patching, scaling, and management. In production always use NAT Gateway.

Q11: What is AWS PrivateLink and how does it work?

PrivateLink allows accessing services hosted in another VPC (or AWS service) through a private IP in your VPC, without peering, TGW, or internet exposure. Provider exposes service behind an NLB. Consumer creates an Interface VPC Endpoint — AWS provisions an ENI with a private IP in the consumer's subnet. DNS for the service resolves to this private ENI IP. Traffic flows: consumer ENI → AWS PrivateLink → NLB → backend service. Neither VPC needs to know the other's CIDR; no routing between VPCs needed.

Q12: How does the Internet Gateway's NAT work for instances with public IPs?

The IGW maintains a one-to-one NAT mapping table: private IP → Elastic/Public IP. When a packet from an instance (10.0.1.10) with Elastic IP 54.x.x.x exits through the IGW, the IGW replaces the source IP to 54.x.x.x. When a response arrives destined for 54.x.x.x, IGW translates to 10.0.1.10 and delivers it to the subnet. Unlike NAT Gateway, this is 1-to-1 (not many-to-one), and inbound connections are allowed (the Elastic IP is reachable from the internet).

Q13: Explain Route 53 Alias records and why they're preferred over CNAMEs for AWS resources.

Alias records are a Route 53 extension: they appear as A or AAAA records but resolve internally by following the target's DNS name to its current IP addresses. Benefits over CNAME: can be used at the zone apex (example.com cannot be a CNAME per RFC 1035), queries to AWS targets are free, automatically track IP changes of ALBs/CloudFront/S3, and support health checks. Always use Alias records for: ALB, NLB, CloudFront, API Gateway, Global Accelerator, S3 website endpoints.

Q14: What is split-horizon DNS and when would you use it?

Split-horizon DNS returns different IP addresses for the same domain name depending on whether the query originates inside or outside the VPC. Configure: a Public Hosted Zone returning the internet-facing ALB IP, and a Private Hosted Zone (associated with your VPC) returning an internal ALB IP for the same domain. Use case: service-to-service calls within AWS should route internally (cheaper, lower latency) while internet clients reach the internet-facing endpoint for the same URL.

Q15: Explain the difference between ALB and NLB — when to use each.

ALB (Layer 7): HTTP/HTTPS-aware; supports content-based routing (path/host/header), TLS termination, WebSocket, HTTP/2, gRPC, WAF integration, Lambda targets, OIDC auth. DNS-based (no static IP). Choose for: REST APIs, microservices, any HTTP workload needing content-based routing. NLB (Layer 4): TCP/UDP-level; static IP per AZ (can be EIPs); preserves source client IP natively; ultra-low latency (~100μs); millions of connections/sec; supports UDP. Choose for: non-HTTP protocols, gaming, IoT, VoIP, applications requiring client IP, whitelisting-friendly static IPs.

Q16: How does CloudFront differ from Global Accelerator?

CloudFront is an HTTP/HTTPS CDN — caches content at edge, reduces origin load, supports Lambda@Edge. Works at Layer 7 only. DNS-based (IP can change). Global Accelerator is a network-layer (L3/4) accelerator — no caching, routes TCP/UDP traffic optimally to regional endpoints over AWS backbone. Provides two static anycast IPs. Faster failover than DNS (seconds vs minutes). Use CloudFront for HTTP with caching needs; use Global Accelerator for non-HTTP, need for static IPs, faster failover, or UDP.

Q17: What is the difference between Route 53 Failover and Latency routing policies?

Failover routing: Active-passive — all traffic goes to the primary endpoint unless its health check fails, then switches to secondary. Designed for DR scenarios. Latency routing: Active-active — multiple endpoints across regions; Route 53 routes each query to the region with the lowest measured network latency for that client's resolver location. Designed for performance optimization across multiple active regions. Can combine them: Latency routing as the primary policy, with health checks on each record to fail over to the other region if the latency-selected one is unhealthy.

Q18: Explain how AWS Shield Standard and Shield Advanced differ.

Shield Standard: free, automatic, protects all AWS resources against common Layer 3/4 DDoS attacks (SYN floods, UDP amplification, reflection attacks). No configuration needed. Shield Advanced: $3,000/month/org + data transfer; adds: 24/7 DRT access, real-time attack visibility, cost protection (credits for DDoS-caused scaling), Layer 7 HTTP flood protection, automatic WAF rule deployment during attacks, and proactive engagement for critical infrastructure.

Q19: What is Site-to-Site VPN and what are its bandwidth limitations?

Site-to-Site VPN creates IPsec-encrypted tunnels over the public internet between an on-prem Customer Gateway device and an AWS Virtual Private Gateway or Transit Gateway. AWS provisions two tunnels per VPN connection for redundancy (each can carry up to 1.25 Gbps). With ECMP (Equal Cost Multi-Path), traffic can be distributed across both tunnels for up to 2.5 Gbps total. For higher bandwidth with private connectivity, use Direct Connect.

Q20: What is Direct Connect and what types of connections exist?

Direct Connect provides a dedicated private physical circuit between on-premises and AWS (not over the internet). Types: Dedicated Connection (1G, 10G, 100G port directly at a DX location); Hosted Connection (50Mbps–10Gbps via an APN partner sharing a dedicated port). Logical interfaces: Private VIF (connect to VPC via VGW), Public VIF (access AWS public services like S3 with public IPs without internet), Transit VIF (connect to Transit Gateway for multi-VPC access). Direct Connect provides consistent bandwidth, lower latency, and potentially lower data transfer costs vs internet.

20.2 Routing and Packet Flow (Q21–Q50)

Q21: Trace the packet flow from an internet browser to an EC2 instance behind an ALB.

DNS resolves domain to ALB DNS name to ALB public IP. TCP handshake to ALB node in public subnet. TLS handshake (ALB presents ACM cert). ALB evaluates listener rules and WAF ACL. Selects target from target group (health-checked). Creates new TCP connection from ALB private IP to EC2 on container port. EC2 Security Group evaluated (ALB SG → EC2 SG allowed). EC2 processes request, responds to ALB. ALB sends response to browser via existing TLS connection.

Q22: Why should NAT Gateways be deployed one per AZ, not one per VPC?

A single NAT Gateway in AZ-1a serving EC2 instances in AZ-1b requires cross-AZ traffic, which AWS charges at $0.01/GB. With a NAT Gateway per AZ, private subnet route tables in each AZ point to that AZ's own NAT Gateway, eliminating cross-AZ transfer costs. Also improves availability: if AZ-1a NAT Gateway fails, only AZ-1a workloads lose internet access; AZ-1b's NAT Gateway is unaffected.

Q23: How does VPC route table conflict resolution work — static vs propagated routes?

For same prefix and prefix length, static routes always take priority over propagated (BGP) routes. A manually added static route for 192.168.0.0/24 → VPC Peering always overrides a BGP-propagated route for the same prefix from a VPN. Among same-priority same-prefix routes, AWS uses longest prefix match; ties are broken by internal AWS priority rules.

Q24: Explain how the VPC router works — is it a physical device?

There is no physical VPC router. Routing in a VPC is implemented by the Nitro hypervisor on every EC2 host. When an EC2 instance sends a packet, the hypervisor intercepts it, consults the subnet's route table (programmed into the hypervisor from the VPC control plane), and forwards accordingly. The "VPC router" at VPC_CIDR+1 (e.g., 10.0.0.1) is a virtual abstraction — it is the default gateway address but no actual router process runs at that IP; the hypervisor handles all forwarding decisions.

Q25: How does Traffic Mirroring work and what are its use cases?

Traffic Mirroring copies inbound and outbound traffic from a source ENI (Nitro-based EC2 only) to a target (NLB or ENI) for analysis. The mirror copy uses VXLAN encapsulation to carry the original packet to the analysis destination. Use cases: IDS/IPS (send copies to a Suricata cluster), network forensics, debugging production traffic issues without impacting the source, compliance monitoring. Key limitation: only Nitro-based instances, can significantly increase bandwidth usage (every byte is duplicated).

Q26: What happens to traffic when a VPN tunnel goes down with two tunnels configured?

Site-to-Site VPN provides two tunnels with different AWS endpoint IPs. If configured with BGP (dynamic routing), each tunnel establishes a BGP session with the VGW. If one tunnel fails, its BGP session drops, routes are withdrawn, and the BGP routing algorithm converges traffic to the healthy tunnel. With static routing, you must configure your on-prem router to detect the dead tunnel (via DPD — Dead Peer Detection) and switch routes to the second tunnel. BGP is always preferred for automatic failover.

Q27: Explain east-west vs north-south traffic and the security implications of each.

North-South: traffic between internet and your VPC (ingress/egress). Security perimeter: IGW, WAF, ALB, Shield, NACLs, Security Groups. Easier to control — all internet traffic enters through a known choke point. East-West: lateral traffic between resources within AWS (EC2 to EC2, EC2 to RDS, VPC to VPC). Security risk: by default, no inspection between VPCs using TGW or Peering. Traffic flows directly between resources without passing a firewall. Solution: centralized inspection VPC with GWLB and virtual network appliances, inserting inspection inline for all east-west TGW traffic.

Q28: How does an Egress-Only Internet Gateway differ from a regular Internet Gateway?

Egress-Only IGW is specifically for IPv6 traffic only — it allows outbound IPv6 connections from VPC resources to the internet but blocks inbound IPv6 connections (no public IPv4 NAT). For IPv4, NAT Gateway serves the same purpose (outbound only from private subnets). Egress-Only IGW is stateful like regular IGW but IPv6-specific. Route table: ::/0 → eigw-xxxxx (for IPv6 outbound from private subnets).

Q29: A packet is being sent from EC2 in VPC-A (10.0.0.0/16) to EC2 in VPC-B (10.1.0.0/16) via TGW. Describe every routing decision made.

1. EC2 in VPC-A route table: 10.1.0.0/16 → tgw-attachment-A. 2. Packet arrives at TGW via VPC-A attachment. 3. TGW consults VPC-A attachment's associated route table: looks up 10.1.0.0/16 → finds entry pointing to VPC-B TGW attachment. 4. Packet forwarded to VPC-B attachment. 5. Delivered to VPC-B subnet. 6. EC2-B's route table: 10.0.0.0/16 → tgw-attachment-B (for return traffic to work). 7. EC2-B Security Group: must allow inbound from 10.0.0.0/16 on the relevant port.

Q30: How does Route 53 Geolocation routing differ from Latency routing?

Geolocation routing: routes based on the geographic location of the DNS query's source (resolver IP), regardless of actual network latency. Use for regulatory compliance (EU users must hit EU endpoints), localization (language/currency), or geo-blocking. Latency routing: routes based on actual measured network latency from the resolver's region to your AWS regions. Routes to the region that will give the lowest response time, regardless of geographic proximity. For performance optimization, always use Latency routing; use Geolocation only for regulatory or business-driven geographic requirements.

20.3 Security (Q31–Q60)

Q31: Why should Security Groups reference other SG IDs instead of CIDR blocks for intra-VPC traffic?

Referencing SG IDs is more precise: "allow traffic from ALB SG" means only the ALB can reach your EC2 — not anything else in the VPC CIDR. Using the VPC CIDR (e.g., 10.0.0.0/16) allows any resource in the VPC with the same port to reach EC2, which violates least-privilege. Additionally, SG references automatically follow the source — if the ALB's IPs change (they do for ALBs), the SG reference still works without any rule updates.

Q32: A NACL with allow rules still shows REJECT in flow logs — why?

NACLs are stateless — return traffic must be explicitly allowed. If inbound TCP 443 is allowed but outbound ephemeral ports (1024-65535) are not, the TCP response from your server cannot reach the client. The client's TCP RST or timeout triggers the REJECT log entry for the return packet. Always add outbound rules for ephemeral ports (1024-65535 to 0.0.0.0/0) in custom NACLs. This is the most common NACL mistake.

Q33: Explain the defense-in-depth networking security model for an internet-facing application on AWS.

Layer 1 — AWS Shield (automatic DDoS at infrastructure level). Layer 2 — CloudFront with WAF (edge protection, L7 DDoS, OWASP rules). Layer 3 — Route 53 Health Checks (route away from compromised endpoints). Layer 4 — IGW + Network ACLs (subnet-level blocking of known bad IPs). Layer 5 — ALB with WAF ACL (L7 request filtering, rate limiting, geo-blocking). Layer 6 — Security Groups (allow only ALB SG to EC2; deny all other inbound). Layer 7 — VPC Endpoints + no public IPs on EC2 (attack surface reduction). Layer 8 — AWS Network Firewall (for egress and east-west). Layer 9 — GuardDuty (threat detection from VPC Flow Logs + CloudTrail).

Q34: What is IMDSv2 and why does it matter for networking security?

IMDSv2 (Instance Metadata Service v2) requires a session token for all metadata API requests (PUT request to get token, then GET with token). IMDSv1 was vulnerable to SSRF attacks: a malicious request could trick an application into fetching http://169.254.169.254/latest/meta-data/iam/security-credentials/ and leaking EC2 instance role credentials. IMDSv2 prevents this: the attacker's SSRF request cannot include the PUT token-fetch step due to server-side restrictions on SSRF. Always enforce IMDSv2: aws ec2 modify-instance-metadata-options --http-tokens required.

Q35: How would you configure AWS WAF to rate-limit API abuse?

Create a rate-based rule in the WAF Web ACL: set the rate limit (e.g., 2000 requests per 5 minutes per IP), set action to Block (or CAPTCHA for challenges). Scope to specific paths (/api/*) using a scope-down statement to avoid counting static asset requests. Combine with IP reputation managed rule group to block known malicious IPs before they even hit rate limits. Add a geo-blocking rule to deny traffic from countries you don't operate in. Configure CloudWatch metrics to alert when block rate exceeds threshold.

Q36: Explain how VPC Flow Logs help troubleshoot security incidents.

Flow logs capture ACCEPT/REJECT decisions at ENI level with 5-tuple (src IP, dst IP, src port, dst port, protocol). For security: identify REJECT entries for your EC2's ENI — what's being blocked by SG/NACL? Identify unexpected ACCEPT entries — what's reaching your instances that shouldn't? Track lateral movement by observing which VPC resources are talking to each other unexpectedly. Identify data exfiltration by finding large data transfers from EC2 to unexpected external IPs. Query in Athena (S3-stored logs) with SQL: SELECT * FROM vpc_flow_logs WHERE action='REJECT' AND dstaddr='10.0.10.5' ORDER BY start;

Q37: What is AWS Network Firewall and how does it differ from Security Groups and NACLs?

Security Groups and NACLs provide basic Layer 3/4 (IP/port) filtering. AWS Network Firewall adds: stateful Layer 4 connection tracking with IPS (Suricata-compatible rules), Layer 7 deep packet inspection (HTTP domain filtering, TLS SNI inspection for HTTPS), managed threat intelligence rule groups, and structured logging of allowed/blocked traffic. Network Firewall requires routing traffic through a firewall endpoint in a dedicated subnet. Security Groups/NACLs are simpler and sufficient for basic perimeter control; Network Firewall adds IDS/IPS capabilities, domain filtering, and compliance-grade logging.

Q38: How does Direct Connect improve security compared to Site-to-Site VPN?

Site-to-Site VPN traffic traverses the public internet — even though it's encrypted with IPsec, it's visible at the network layer to ISPs and potential eavesdroppers. Direct Connect provides a private physical connection: traffic never touches the public internet. This reduces the attack surface (no man-in-the-middle at the IP layer, no internet DDoS against VPN endpoints). However, Direct Connect itself is not encrypted — for defense-in-depth, run IPsec encryption over Direct Connect using MACsec or by running an encrypted VPN tunnel inside the DX connection.

20.4 Load Balancing and DNS (Q39–Q70)

Q39: An ALB is returning 503 errors. Walk through your debugging process.

1. Check target health: aws elbv2 describe-target-health for the target group. 2. If all targets unhealthy: check EC2/ECS task health (running?), SG allows ALB to reach target port, health check path returns 200. 3. If health check path returns 404: update ALB health check path to correct endpoint. 4. If health check succeeds but app returns 503: application logic issue, check app logs. 5. Check ALB access logs in S3 for target_status_code to see what backend returns. 6. Check ALB target group threshold — is the failure_threshold correct? 7. Check ECS task count — did autoscaling stop tasks?

Q40: Why might an NLB be preferred over an ALB for certain workloads even though ALB has more features?

NLB is preferred when: (1) Static IP per AZ needed (clients/firewalls whitelist specific IPs — ALB has dynamic IPs); (2) UDP protocol required (ALB is TCP/HTTP only); (3) Extreme performance needed (NLB handles millions of requests/sec with ~100μs latency vs ALB's millisecond latency); (4) Very long-lived TCP connections (NLB has no connection timeout limit; ALB has 4000s max idle timeout); (5) Source client IP preservation needed natively at the TCP level without X-Forwarded-For parsing; (6) TLS passthrough required (ALB always terminates TLS).

Q41: Explain session stickiness on ALB — how does it work and when should you use it?

Stickiness uses a cookie (AWSALB) set by ALB. The cookie contains an encrypted identifier pointing to a specific target. Subsequent requests from the same client with that cookie are routed to the same target. Two types: duration-based (ALB-managed cookie, configurable TTL) and application-based (ALB reads an existing app cookie to determine stickiness). Use stickiness only for legacy stateful applications that store session state locally. Modern applications should store session state in an external store (Redis/ElastiCache) and be fully stateless — then stickiness is unnecessary and reduces load distribution quality.

Q42: How does Gateway Load Balancer enable transparent network inspection?

GWLB uses GENEVE (Generic Network Virtualization Encapsulation) on port 6081 to tunnel packets to virtual appliances while preserving the original packet headers. Traffic path: source → GWLB Endpoint (GWLBE) → GWLB → appliance (packet inspected, modified, or dropped) → GWLB → GWLBE → destination. The appliance sees the full original packet (GENEVE header preserves metadata) and can implement any packet-level logic. AWS handles scaling the appliance fleet and health checking — failed appliances are removed from rotation automatically.

Q43: What is Route 53 Resolver and when would you need it?

Route 53 Resolver is the VPC's built-in DNS resolver (at VPC CIDR+2 or 169.254.169.253). It handles resolution of public DNS and Route 53 hosted zones. Resolver endpoints extend this for hybrid scenarios: Inbound Endpoints (ENIs in your VPC) allow on-prem DNS servers to resolve AWS Private Hosted Zone names by forwarding queries to the endpoint IPs. Outbound Endpoints with Forwarding Rules allow VPC EC2 instances to resolve on-prem domain names (corp.internal → forward to on-prem DNS 192.168.1.53) by sending queries out through the outbound endpoint to the specified DNS server.

Q44: What are GWLB health check considerations compared to ALB health checks?

GWLB health checks target the virtual appliance fleet. Appliances must respond to health checks (HTTP GET on a configured path returning 200) — if an appliance fails, it's removed from the rotation. Unlike ALB/NLB where health check failure means less capacity, a GWLB appliance failure means traffic might be black-holed if the appliance drops packets without cleaning up connections. Minimum recommended fleet size is 2 instances across AZs for HA. Health check port and path must match what the appliance's management interface serves.

Q45: Explain the difference between geoproximity routing and geolocation routing in Route 53.

Geolocation: strictly maps geographic regions/countries to specific endpoints — a US user always hits the US endpoint regardless of physical distance to other endpoints. Has no concept of which endpoint is physically closest to the user. Geoproximity: routes to the geographically closest endpoint based on coordinates, with an adjustable bias. Positive bias for an endpoint expands its coverage area (routes users from farther away to it). Negative bias shrinks its area. Use geolocation for regulatory requirements; use geoproximity for geographic load distribution with tunable bias.

20.5 Advanced Architecture Scenarios (Q46–Q80)

Q46: Design a network architecture for a globally distributed application with RTO < 5 minutes.

Active-active multi-region: Route 53 latency routing with health checks on each region's ALB. Both regions serve live traffic simultaneously. Aurora Global Database (RTO < 1 min for planned failover; up to 1min for unplanned — less than 1min in practice with Global Database). Automated failover: CloudWatch alarm detects primary region degradation → EventBridge rule → Lambda promotes Aurora secondary → updates Route 53 weights to reduce primary region traffic. Seconds-level DNS failover with Route 53 health checks (evaluate_target_health=true). Add Global Accelerator for sub-second failover at network layer independent of DNS TTL.

Q47: A company's compliance requirement states all traffic between AWS services must never traverse the public internet. How do you implement this?

S3/DynamoDB: Gateway VPC Endpoints (free, traffic via AWS backbone only). All other AWS services (SSM, Secrets Manager, KMS, ECR, CloudWatch, STS): Interface VPC Endpoints (PrivateLink). For cross-region: AWS backbone connects regions — enable VPC Peering or TGW inter-region peering (traffic stays on backbone). For on-prem: Direct Connect (dedicated private circuit). For cross-account: TGW + RAM sharing, or VPC Peering. Use VPC Endpoint Policies to restrict access to only your account's resources. S3 bucket policy with aws:sourceVpce condition to enforce endpoint-only access. Disable public access on all S3 buckets.

Q48: Explain the centralized inspection model using Gateway Load Balancer and Transit Gateway.

TGW route tables segregate traffic flows: Spoke VPCs → TGW → Inspection route table → Inspection VPC attachment. GWLB in Inspection VPC receives traffic via GWLB Endpoint. GWLB distributes to appliance fleet (Palo Alto/Fortinet). Appliances inspect/allow/block. Allowed traffic returns to GWLB → GWLBE → TGW → destination VPC. This provides centralized, scalable L7 inspection without per-VPC appliance deployment. East-west and north-south traffic can both be routed through the inspection VPC. GWLB auto-scales the appliance fleet based on traffic; TGW handles routing without per-flow configuration.

Q49: Why does VPC Peering require non-overlapping CIDRs and what's your approach when two VPCs have the same CIDR?

Peering requires non-overlapping CIDRs because the route tables on both sides need a unique prefix to route traffic to the peer VPC — if both are 10.0.0.0/16, the route table cannot distinguish which packets should go to the peer vs stay local. Solutions when CIDRs overlap: (1) Re-number one VPC (painful, requires migration). (2) Use Private Link instead of VPC Peering — consumer creates an endpoint connecting to a service in the overlapping VPC via NLB without needing routing between VPCs. (3) Use NAT in the middle (place a NATting appliance that translates one VPC's addresses to a non-overlapping range — complex). PrivateLink is the clean solution.

Q50: How does AWS Cloud WAN simplify multi-region/multi-account networking?

Cloud WAN creates a fully managed global network as a graph policy. You define segments (production, development) and the policy determines connectivity between them — Cloud WAN automatically provisions TGWs per region, TGW peerings between regions, and route tables implementing the policy. Without Cloud WAN: manually provision TGW per region, manually configure inter-region peering, manually manage route tables across regions. Cloud WAN abstracts this into a JSON Network Policy, provides a global network topology visualization dashboard, and monitors the global network health. It integrates with Direct Connect and VPNs natively.

Q51–Q150: Quick Reference Answers

Q51 What is VPC CIDR secondary association? — Allows adding additional CIDR blocks to an existing VPC (up to 5 total), enabling address space expansion without recreating the VPC.

Q52 What is a Transit VIF in Direct Connect? — A logical interface connecting a Direct Connect connection to a Transit Gateway, enabling access to multiple VPCs across regions from a single DX connection.

Q53 What are VPC Reachability Analyzer and Network Access Analyzer? — Reachability Analyzer: validates if two endpoints can communicate without sending traffic (automated path analysis). Network Access Analyzer: finds unintended network access across VPCs/accounts at scale.

Q54 Explain Accelerated Site-to-Site VPN — Uses Global Accelerator to route VPN traffic: on-prem traffic enters AWS at nearest edge PoP and traverses AWS backbone to VPN endpoint, reducing latency vs standard VPN routing through the internet.

Q55 What is a Direct Connect Gateway? — Global resource connecting a single DX connection to multiple VPCs across multiple AWS Regions via Private VIFs. Does not enable transitive routing between VPCs.

Q56 How do you restrict an S3 bucket to only be accessible from a specific VPC? — Bucket policy with Condition: StringEquals: aws:sourceVpc: vpc-xxx. All access from outside the VPC (including AWS console) will be denied.

Q57 What causes "black hole routes" in Transit Gateway? — A TGW route that points to a deleted or non-operational attachment. Traffic matching the route is silently dropped. Fix: remove the stale route or point it to a working attachment.

Q58 Explain ALB Listener Rule priority and default actions — Rules evaluated lowest-number-first (priority 1-50000). First matching rule's action is executed. Default rule (last, no conditions) applies when no rule matches — must be a forward, redirect, or fixed-response action.

Q59 What is CloudFront Origin Shield? — An additional CloudFront caching layer (specific AWS region) between edge locations and origin. Consolidates origin fetches: multiple edge PoPs miss → all request from Origin Shield → Origin Shield requests once from origin. Reduces origin load by up to 60%.

Q60 How does AWS EKS use VPC CNI differently from other CNIs? — VPC CNI assigns real VPC IP addresses (from your subnet IP space) to pods, unlike overlay CNIs that create a virtual network. Pod IPs are routable within the VPC, across peering, and via TGW — no overlay encapsulation overhead.

Q61 What is the AWS VPC default security? — New VPC: one default route table (local only), one default SG (all outbound allowed, inbound from same SG only), one default NACL (allow all in/out). Default VPC has public subnets, IGW, and auto-assign public IPs — not recommended for production.
