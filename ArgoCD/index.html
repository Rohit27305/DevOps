1. Fundamentals: What ArgoCD Is and Why GitOps Exists

1.1 What Is ArgoCD?

ArgoCD is a declarative, GitOps continuous delivery tool for Kubernetes. It runs as a controller inside a Kubernetes cluster, continuously compares the desired state (defined in a Git repository) against the live state of the cluster, and reconciles any difference. Instead of a pipeline pushing changes into a cluster, ArgoCD pulls changes from Git and applies them — Git becomes the single source of truth for what should be running.

ArgoCD itself is a Kubernetes-native application: it is installed as a set of Custom Resource Definitions (CRDs) and controllers running in your cluster. You declare 'Applications' as Kubernetes objects, and ArgoCD's controllers watch them, diff them against Git, and sync them.

1.2 Why GitOps Exists

Before GitOps, the common deployment model was push-based CI/CD: a pipeline (Jenkins, GitLab CI, GitHub Actions) builds an artifact, then runs kubectl apply or helm upgrade directly against the cluster using credentials stored in the CI system. This works, but creates several structural problems at scale:

  • CI systems need broad cluster credentials: Every pipeline that deploys needs kubeconfig or service account tokens with write access to production. This is a large attack surface.
  • No single source of truth: The actual state of the cluster lives only in the cluster itself. You can't easily answer 'what is running right now and why' without querying the cluster directly.
  • Configuration drift goes undetected: Someone runs kubectl edit in production to fix something urgently. That change is now invisible to Git and to your next deployment, which will silently overwrite or conflict with it.
  • Difficult audit trail: Correlating 'who changed what, when, and why' requires correlating CI logs, kubectl audit logs, and Slack messages.
  • Multi-cluster fan-out is hard: Pushing the same change to 20 clusters from a single pipeline run is fragile — partial failures leave clusters inconsistent.
  • Rollback is manual and pipeline-dependent: Reverting requires re-running a pipeline with an old artifact reference, assuming the pipeline and artifact still exist.

GitOps inverts the model: instead of CI pushing into the cluster, an in-cluster agent pulls the desired state from Git and reconciles continuously. Git history becomes your deployment history, audit log, and rollback mechanism, all in one place — because it's literally just git revert.

1.3 Problems ArgoCD Specifically Solves

Disaster recoveryBecause the cluster's desired state is fully described in Git, a destroyed cluster can be rebuilt by pointing a fresh ArgoCD instance at the same Git repos.

1.7 The Reconciliation Loop

Understanding the reconciliation loop is fundamental to debugging ArgoCD. It is a continuous, level-triggered control loop, the same pattern used by every Kubernetes controller.

  1. ArgoCD polls the Git repository (default every 3 minutes, or instantly via a webhook) for the configured path/branch/tag of an Application.
  1. The repo-server clones/fetches the repo, then renders manifests (plain YAML pass-through, helm template, kustomize build, or a plugin).
  1. The application controller fetches the live state of every resource owned by the Application from the Kubernetes API.
  1. The controller performs a three-way diff: Git-desired state vs last-applied state vs live state (similar to kubectl apply's diffing logic).
  1. If a difference exists, the Application is marked OutOfSync. If everything matches, it's Synced.
  1. Depending on sync policy: if automated sync is enabled, the controller immediately applies the diff. If manual, it waits for a human (or external trigger) to click/run Sync.
  1. After applying, the controller continuously checks resource Health (e.g., Deployment rollout completed, Pods Running and Ready) using built-in or custom health checks.
  1. The loop repeats indefinitely — this is what enables both auto-sync (apply new Git changes) and self-heal (revert manual drift).

The Helm chart is the standard production installation method because it makes upgrades, custom values, and GitOps-managing-ArgoCD-itself (the 'app of apps for ArgoCD itself' pattern) much easier.

2.6 Production Installation Considerations

ConsiderationDetail
High Availability (HA)Use the ha/install.yaml manifest or set replica counts >1 in Helm values. Run multiple argocd-server and argocd-repo-server replicas. The application-controller uses internal sharding (ARGOCD_CONTROLLER_REPLICAS) instead of a simple HPA since it owns cluster state per shard.
Redis HASingle-instance Redis is a single point of failure for caching. Use the redis-ha subchart (Sentinel-based) in production to avoid cache-loss-induced API slowdowns.
TLS terminationDecide whether to terminate TLS at the Ingress/LoadBalancer or pass through to argocd-server (which can serve its own cert). Passthrough is more secure end-to-end but requires more ingress controller config (ssl-passthrough).
Resource sizingrepo-server is usually the bottleneck (Git clone + Helm/Kustomize render is CPU/memory intensive). Size repo-server generously and enable HPA. application-controller needs enough memory to hold full cluster state in memory.
Repo-server cachingMount a persistent volume or use a larger ephemeral disk for /tmp on repo-server to speed up repeated Helm/Kustomize renders across many Applications.
Network policiesRestrict egress from repo-server to only required Git/Helm/OCI registry endpoints. Restrict ingress to argocd-server from the rest of the cluster.
External database avoidanceArgoCD doesn't use an external DB — state lives in Kubernetes CRs + Redis cache. This simplifies HA but means etcd performance directly affects ArgoCD performance at scale.
Namespace isolationDecide between cluster-scoped (one ArgoCD manages many clusters/namespaces) vs namespace-scoped installs (restricted via --application-namespaces) for multi-tenant platforms.
BackupBack up the argocd namespace's CRs (Applications, AppProjects, Secrets) regularly, even though Git is the real source of truth — repo connection secrets and RBAC config live only in-cluster.

3. ArgoCD Core Concepts

3.1 Applications

An Application is the central ArgoCD custom resource. It defines: where the source manifests live (Git repo, path, revision), what tool renders them (plain YAML, Helm, Kustomize, plugin), and where they should be deployed (destination cluster + namespace). It is the unit of deployment and the unit of sync/health tracking.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

The finalizer resources-finalizer.argocd.argoproj.io is important: without it, deleting the Application object leaves the deployed Kubernetes resources orphaned in the cluster. With it, deleting the Application also cascades to delete the resources it manages.

3.2 Projects (AppProjects)

An AppProject groups Applications and restricts what they're allowed to do: which Git repos they may pull from, which clusters/namespaces they may deploy to, and which Kubernetes resource kinds they may create. This is ArgoCD's multi-tenancy boundary.

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-payments
  namespace: argocd
spec:
  description: 'Payments team applications'
  sourceRepos:
    - 'https://github.com/myorg/payments-*'
  destinations:
    - server: https://kubernetes.default.svc
      namespace: 'payments-*'
    - server: https://prod-cluster.example.com
      namespace: 'payments-prod'
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
  namespaceResourceBlacklist:
    - group: ''
      kind: ResourceQuota
  roles:
    - name: payments-deployer
      policies:
        - p, proj:team-payments:payments-deployer, applications, sync, team-payments/*, allow
      groups:
        - myorg:payments-team

Without AppProjects, every Application by default lives in the default project, which has no restrictions — any team could (in theory) deploy to any cluster/namespace from any repo. In multi-team production clusters, AppProjects are mandatory for safe self-service.

3.3 Repositories

ArgoCD must be granted access to the Git (or Helm/OCI) repositories it pulls manifests from. Repository credentials are stored as Kubernetes Secrets labeled for ArgoCD, or registered via the CLI/UI which creates those secrets for you.

# Register a repo via CLI (HTTPS with token)
argocd repo add https://github.com/myorg/myapp-manifests.git \
  --username myuser \
  --password $GITHUB_TOKEN

# Register via SSH
argocd repo add git@github.com:myorg/myapp-manifests.git \
  --ssh-private-key-path ~/.ssh/id_rsa

# Register a Helm chart repo
argocd repo add https://charts.bitnami.com/bitnami \
  --type helm --name bitnami

# Register declaratively (preferred for production - GitOps managing itself)
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: myapp-manifests-repo
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  type: git
  url: https://github.com/myorg/myapp-manifests.git
  password: $GITHUB_TOKEN
  username: not-used
EOF

3.4 Sync Policies

Sync policy controls how and when ArgoCD reconciles an Application's live state to match Git. There are two top-level modes: manual (default) and automated.

SettingBehavior
Manual syncArgoCD detects drift/changes and marks the Application OutOfSync, but takes no action until a human (or external automation) explicitly runs argocd app sync or clicks Sync in the UI.
Automated syncArgoCD automatically applies any detected diff between Git and the live cluster, without human intervention, as soon as it's detected (subject to the polling/webhook interval).
prune (within automated)When enabled, resources that were removed from Git are deleted from the cluster. Without it, deleted-from-Git resources are left orphaned in the cluster forever.
selfHeal (within automated)When enabled, any manual change made directly to the cluster (kubectl edit, kubectl scale, etc.) that diverges from Git is automatically reverted back to match Git on the next reconciliation.
syncOptionsAdditional fine-grained behaviors: CreateNamespace=true, PrunePropagationPolicy, Replace=true (use kubectl replace instead of apply), ApplyOutOfSyncOnly=true, Validate=false (skip kubectl validation), etc.
Retryautomated.retry can configure backoff/retry behavior for failed syncs (limit, backoff.duration, backoff.factor, backoff.maxDuration).
# Full sync policy example with all options
syncPolicy:
  automated:
    prune: true
    selfHeal: true
    allowEmpty: false
  syncOptions:
    - CreateNamespace=true
    - PrunePropagationPolicy=foreground
    - PruneLast=true
    - ApplyOutOfSyncOnly=true
  retry:
    limit: 5
    backoff:
      duration: 5s
      factor: 2
      maxDuration: 3m
PRODUCTION GUIDANCE: Enable auto-sync + selfHeal for lower environments (dev/qa) for fast feedback. For production, many teams keep auto-sync ON but require a manual approval gate upstream (e.g., a PR merge to a 'prod' branch/folder) rather than disabling ArgoCD automation itself — this keeps the GitOps guarantee (cluster always matches Git) while still requiring human sign-off via the PR process.

3.5 Pruning

Pruning is the deletion of cluster resources that are no longer present in Git. Without prune: true, if you delete a Deployment manifest from your Git repo, ArgoCD will simply report the Application as Synced (since 'nothing in Git' has nothing to compare against for that resource) and the orphaned Deployment keeps running in the cluster forever. With pruning enabled, ArgoCD detects the resource is 'tracked but no longer desired' and deletes it.

# Manual prune (no automated policy)
argocd app sync myapp --prune

# See what would be pruned without doing it
argocd app diff myapp

# Resources can opt out of pruning individually
metadata:
  annotations:
    argocd.argoproj.io/sync-options: Prune=false

3.6 Health Checks

ArgoCD evaluates Health status for every resource type it manages, separate from Sync status. A resource can be Synced (matches Git) but Degraded (unhealthy) — for example, a Deployment manifest applied successfully but the pods are CrashLoopBackOff.

Health StateMeaning
HealthyResource is in its desired running state (Deployment fully rolled out, Pod Running and Ready, PVC Bound, etc.)
ProgressingResource is in the process of reaching Healthy (rollout in progress, PVC pending).
DegradedResource has failed to reach Healthy (CrashLoopBackOff, failed Job, Deployment with unavailable replicas past deadline).
SuspendedResource is intentionally paused (e.g., a suspended CronJob or a paused Argo Rollout).
MissingResource is defined in Git but does not exist in the live cluster.
UnknownArgoCD has no built-in health check logic for this resource Kind (common for CRDs without a custom health check defined).
# Custom health check for a CRD (in argocd-cm ConfigMap)
resource.customizations.health.cert-manager.io_Certificate: |
  hs = {}
  if obj.status ~= nil and obj.status.conditions ~= nil then
    for i, condition in ipairs(obj.status.conditions) do
      if condition.type == 'Ready' and condition.status == 'True' then
        hs.status = 'Healthy'
        hs.message = 'Certificate is ready'
        return hs
      end
    end
  end
  hs.status = 'Progressing'
  hs.message = 'Waiting for certificate'
  return hs

3.7 Resource Tracking

ArgoCD needs to know which live cluster resources 'belong to' which Application, so it knows what to diff, prune, and report health for. This is resource tracking.

MethodDescription
Label-based (legacy default)Adds the label app.kubernetes.io/instance: <app-name> to every managed resource. Simple but can collide with your own use of that label, or get stripped by some tools/admission webhooks.
Annotation-based (recommended)Uses the annotation argocd.argoproj.io/tracking-id instead, which encodes app name + group/kind/namespace/name. Avoids collisions with the commonly-used app.kubernetes.io/instance label. Set via application.resourceTrackingMethod: annotation in argocd-cm.

5.1 Managing Multiple Environments (Dev, QA, Prod)

5.4 Secrets Management

ArgoCD intentionally does NOT manage secret material directly inside Git in plaintext. Several patterns exist to solve this; choosing the right one depends on your existing secret infrastructure.

ApproachHow It Works
Sealed Secrets (Bitnami)Secrets are encrypted client-side with a public key before committing to Git. A controller in-cluster holds the private key and decrypts into a normal Secret at apply time. Git only ever stores ciphertext.
External Secrets Operator (ESO)Git stores a lightweight ExternalSecret CR referencing a path in Vault/AWS Secrets Manager/etc. The ESO controller fetches the real value at runtime and creates a native Kubernetes Secret. No secret material in Git at all.
Argo CD Vault Plugin (AVP)A config management plugin that ArgoCD invokes during manifest rendering; it substitutes <path:secret/data/db#password> placeholders in manifests with live values fetched from Vault at sync time.
SOPS (Mozilla)Encrypts individual values within YAML/JSON files using KMS/PGP/age. Decrypted via a Kustomize/Helm plugin during ArgoCD's render step (commonly via the argocd-vault-plugin or a custom sidecar).
# Example: External Secrets Operator pattern (most common in production)
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: db-credentials   # the Kubernetes Secret that gets created
  data:
    - secretKey: password
      remoteRef:
        key: secret/data/payments/db
        property: password
# This ExternalSecret manifest is what lives in Git - zero actual secret data

5.5 Progressive Delivery

Progressive delivery (canary, blue-green, automated rollback based on metrics) is not built into ArgoCD's Application controller itself — it's delivered via Argo Rollouts, a sibling project that replaces the standard Deployment object with a Rollout CRD that ArgoCD deploys and watches exactly like any other resource.

Blue-Green Deployment

apiVersion: argoproj.io/v1alpha1

      activeService: myapp-active
      previewService: myapp-preview
      autoPromotionEnabled: false   # require manual promotion
      scaleDownDelaySeconds: 30
  selector:
    matchLabels: { app: myapp }
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: myapp
          image: myregistry/myapp:v2

kubectl argo rollouts promote myapp

5.6 Disaster Recovery

Because every Application's desired state is fully described in Git, disaster recovery for application state is largely 'point a fresh ArgoCD install at the same Git repos.' The harder part is recovering ArgoCD's own configuration (clusters, projects, RBAC, notification settings) and any data not in Git (like manually-created secrets).

  1. Recreate the cluster (or use a standby cluster) and re-install ArgoCD via the same Helm values used in production (kept in Git — 'ArgoCD managing itself').
  1. Restore repository credentials and cluster secrets — these should be backed up separately (e.g., via Velero, or re-provisioned from a secrets manager via External Secrets) since they don't live in the app manifests repo.
  1. Re-apply the App-of-Apps root Application — this single object bootstraps every other Application, Project, and ApplicationSet from Git automatically.
  1. ArgoCD reconciles every Application from scratch, recreating the entire desired state across all managed namespaces/clusters with no manual kubectl required.
DR BEST PRACTICE: Treat ArgoCD's own installation as a GitOps-managed Application too (the 'App of Apps for ArgoCD' or 'argocd-autopilot' pattern). This means even ArgoCD's own configuration is recoverable by Git alone, not tribal knowledge.

6.1 ApplicationSets

An ApplicationSet generates many Application resources from a single template, driven by 'generators' — list, cluster, Git directory, Git file, matrix, pull request, SCM provider, and more. This is the standard way to handle multi-environment and multi-cluster fan-out without hand-writing dozens of near-identical Application YAMLs.

# Cluster generator: deploy the same app to every registered cluster
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: monitoring-stack
  namespace: argocd
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            env: production
  template:
    metadata:
      name: '{{name}}-monitoring'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/monitoring-manifests.git
        targetRevision: HEAD
        path: base
      destination:
        server: '{{server}}'
        namespace: monitoring
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
# Git directory generator: one Application per folder under apps/
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
spec:
  generators:
    - git:
        repoURL: https://github.com/myorg/manifests.git
        revision: HEAD
        directories:
          - path: apps/*

    metadata:
      name: '{{path.basename}}'

6.3 RBAC

ArgoCD's RBAC model is policy-based (similar to Casbin), defined in the argocd-rbac-cm ConfigMap. Policies map subjects (users, groups from SSO) to permissions on resources (applications, projects, clusters, repositories) and actions (get, sync, create, delete, override, etc).

# argocd-rbac-cm ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: role:readonly
  policy.csv: |
    p, role:org-admin, applications, *, */*, allow
    p, role:org-admin, clusters, *, *, allow
    p, role:org-admin, repositories, *, *, allow
    p, role:org-admin, projects, *, *, allow

    p, role:dev-team, applications, get, team-payments/*, allow
    p, role:dev-team, applications, sync, team-payments/*, allow
    p, role:dev-team, applications, action/*, team-payments/*, allow
    p, role:dev-team, applications, delete, team-payments/*, deny

    g, myorg:platform-admins, role:org-admin
    g, myorg:payments-team, role:dev-team
  scopes: '[groups]'

Note the pattern team-payments/* — this is project/application-name, meaning RBAC integrates directly with AppProjects to scope permissions per-team, per-environment.

Argo CD Image Updater is a separate controller that watches container registries for new image tags and automatically updates the Application's manifests (or Git repo) to use the new tag, closing the loop for fully automated CD without a separate CI step bumping tags.

metadata:
  annotations:
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry/myapp
    argocd-image-updater.argoproj.io/myapp.update-strategy: semver

6.7 Argo Rollouts Deep Dive

Covered functionally in Section 5.5; architecturally, Argo Rollouts installs its own controller plus an optional kubectl plugin. 8.4 Cluster Topology Patterns

9. Common Mistakes

9.1 Beginner Mistakes

MistakeConsequence / Fix
Using kubectl directly on ArgoCD-managed resourcesManual kubectl edit/scale/delete on resources owned by an Application either gets reverted (if selfHeal is on) or creates silent drift (if it's off) that confuses everyone. Always change Git, never the cluster, for managed resources.
Forgetting the resources-finalizerWithout resources-finalizer.argocd.argoproj.io, deleting an Application object leaves all its Kubernetes resources orphaned in the cluster, silently consuming resources forever.
Mixing app source code and manifests in one repo with auto-syncEvery commit to application code (even README changes) triggers ArgoCD to re-evaluate the Application, causing noisy syncs and slower repo-server performance. Keep manifests in a separate path or repo from source code.
Not understanding Sync vs Health are separateBeginners assume Synced means 'working.' A Deployment can be perfectly Synced (manifest matches Git) yet Degraded (CrashLoopBackOff). Always check both statuses.
Relying on argocd app rollback instead of git revertAs covered in Lab 5, rollback-without-Git-revert is immediately undone by the next auto-sync, confusing engineers who don't realize Git still has the bad version as HEAD.
Using :latest image tagsArgoCD has no way to detect that :latest changed underneath it without Image Updater or polling the registry. Drift detection becomes meaningless. Always use immutable tags (SHA or semver).

9.2 Scaling Issues

IssueFix
Too many Applications on one repo-server replicaGit clone + Helm/Kustomize render for hundreds of Applications saturates a single repo-server. Symptom: slow syncs, 'context deadline exceeded' errors. Fix: scale repo-server replicas and enable HPA; consider repo-server caching tuning.
Application controller running out of memoryThe controller holds the live state of every managed resource in memory. At thousands of Applications across many clusters, this can OOM a single controller instance. Fix: enable application controller sharding (ARGOCD_CONTROLLER_REPLICAS) to split cluster ownership across multiple controller pods.
Polling interval too aggressiveSetting timeout.reconciliation very low (e.g., 10s) across thousands of Applications creates constant Git API and Kubernetes API load. Fix: keep the default ~3m polling and rely on webhooks for instant updates instead.
Single shared Redis as a bottleneckDefault single-instance Redis becomes a hot spot at scale, and its loss causes cache-miss storms hitting the Kubernetes API directly. Fix: deploy Redis HA (Sentinel) subchart in production.
Giant App-of-Apps treeA single root Application managing thousands of child Applications can make the root itself slow to diff/sync. Fix: use ApplicationSets with generators instead of an enormous flat App-of-Apps list, and consider per-team root Applications.

9.3 Security Issues

IssueRisk
Leaving local admin enabled with SSO configuredCreates a parallel, often-forgotten privileged credential outside your SSO/MFA policy. Disable admin.enabled after SSO setup and onboarding org-admin groups.
Overly broad AppProject defaultLeaving teams on the default project (no repo/destination restrictions) means any compromised Git credential or pipeline could deploy anywhere. Always scope teams to dedicated AppProjects.
Storing real secrets in plain Kubernetes Secret manifests in GitDefeats the entire purpose of secret management; anyone with repo read access (and full Git history) has the secret forever, even after rotation/deletion from HEAD. Use ESO/Sealed Secrets/Vault plugin.
Granting repo-server unrestricted network egressA compromised repo-server (or a malicious plugin/hook) with full outbound access can exfiltrate data anywhere. Restrict egress with NetworkPolicy to known Git/registry endpoints.
Not reviewing PreSync/PostSync resource hooks in PRsHooks run arbitrary Jobs with the same cluster credentials as ArgoCD itself — a malicious hook in an unreviewed PR is effectively RCE in your cluster.

9.4 GitOps Anti-Patterns

Anti-PatternWhy It's a Problem
CI tool both builds AND deploysDefeats the entire pull-based security model — CI still needs cluster credentials, exactly the problem GitOps was meant to remove. Keep CI's job ending at 'update the manifest repo.'
Mutable image tags + manual cluster restarts to pick up new imagesArgoCD reports Synced even though a new image was actually deployed via kubectl rollout restart outside of Git tracking — the Application status lies about what's truly running. Always pin manifests to immutable tags/digests.
Templating secrets directly into plain YAML committed to GitSee above — same root cause, repeated as a workflow habit rather than a one-off mistake.
No AppProject boundaries between teamsEvery team using the default project means there is no real multi-tenancy; one team's mistake (or compromised credential) can affect every other team's Applications.
Treating ArgoCD UI clicks as the source of truth for changesManually editing values via the UI 'Edit' button instead of committing to Git creates the exact drift-without-traceability problem GitOps exists to prevent. UI/CLI should be used for visibility and sync triggers, not for making permanent config changes.

10. Interview Preparation

10.1 Top 30 ArgoCD Interview Questions

QuestionModel Answer
What is ArgoCD and what problem does it solve?A declarative GitOps continuous delivery tool for Kubernetes that continuously reconciles cluster state to match a Git repository, solving drift, credential sprawl, and audit-trail problems inherent to push-based CI/CD.
Explain the pull vs push deployment model.Push: CI pushes changes into the cluster, requiring CI to hold cluster credentials. Pull: an in-cluster agent (ArgoCD) pulls desired state from Git and applies it, so only the agent needs cluster credentials.
What are the core ArgoCD components?API server, repo-server, application controller, ApplicationSet controller, notifications controller, Redis, and optionally Dex for SSO.
What is the difference between Sync status and Health status?Sync status compares Git-desired state to live state (Synced/OutOfSync). Health status evaluates whether the resource is actually functioning correctly (Healthy/Progressing/Degraded/Missing), independent of whether it's synced.
What does selfHeal do?Automatically reverts manual/out-of-band changes made directly to the cluster back to match Git, on the next reconciliation cycle.
What does prune do, and what happens without it?Deletes cluster resources that were removed from Git. Without it, deleted-from-Git resources remain orphaned in the cluster indefinitely.
What is an AppProject and why is it needed?A grouping/restriction boundary for Applications: limits allowed source repos, destination clusters/namespaces, and resource kinds. Needed for safe multi-tenancy so one team can't deploy to another team's namespace or use unapproved resource kinds.
Explain the App of Apps pattern.A root Application whose Git source contains other Application manifests; syncing the root creates/updates all child Applications, enabling one-command bootstrap of an entire platform.
What is an ApplicationSet and when would you use one over App of Apps?A controller that generates Applications dynamically from generators (list, cluster, git, matrix, etc). Preferred over a static App of Apps tree when Applications need to be generated programmatically across many clusters/environments rather than hand-listed.
How does ArgoCD know which cluster resources belong to which Application?Resource tracking, via either the app.kubernetes.io/instance label (legacy) or the argocd.argoproj.io/tracking-id annotation (recommended, avoids label collisions).
How do you safely roll back a bad deployment in a GitOps model?git revert the offending commit and let ArgoCD auto-sync the reverted state, rather than using argocd app rollback alone (which doesn't update Git and gets overwritten by the next auto-sync).
What's the difference between manual and automated sync policy?Manual: drift is detected and shown, but requires explicit human/API trigger to apply. Automated: detected drift is applied immediately without intervention.
How does ArgoCD render Helm charts without Tiller or helm install?The repo-server runs helm template internally to produce final manifests; ArgoCD's own controller handles the apply/diff/prune lifecycle instead of Helm's release management.
What is the resources-finalizer for?Ensures that deleting an Application object cascades to delete the Kubernetes resources it manages, preventing orphaned resources.
How would you manage secrets in a GitOps workflow?Never commit plaintext secrets to Git. Use External Secrets Operator (fetch from Vault/cloud secret managers at runtime), Sealed Secrets (client-side encryption), or the Argo CD Vault Plugin to inject secrets at render time.
Explain progressive delivery and how ArgoCD relates to Argo Rollouts.Progressive delivery (canary, blue-green) is implemented by Argo Rollouts, a separate controller that replaces Deployment with a Rollout CRD. ArgoCD deploys and tracks Rollout objects exactly like any other resource — it doesn't implement traffic-shifting itself.
How do you handle multi-cluster deployments?Register external clusters via argocd cluster add (creates a Secret with cluster credentials), then reference them via Application destination.server, often automated with an ApplicationSet cluster generator.
What causes an Application to be stuck in Progressing?The deployed resource (e.g., Deployment) hasn't satisfied its health check criteria — commonly failing readiness probes, insufficient replicas available, or a stuck rollout.
How does ArgoCD detect drift?The application controller continuously performs a three-way diff (Git-desired vs last-applied vs live state) on every managed resource during each reconciliation loop.
What's the purpose of the repo-server, specifically?Clones/caches Git repositories and renders final Kubernetes manifests (via plain YAML, Helm template, Kustomize build, or a config management plugin) — it never talks to the destination cluster directly.
How would you scale ArgoCD for hundreds of Applications across many clusters?Scale repo-server replicas (HPA), enable application controller sharding across multiple replicas, deploy Redis HA, and consider splitting into multiple ArgoCD instances per team/cluster region if a single instance becomes a bottleneck.
How do you integrate ArgoCD with SSO?Via the bundled Dex component (supports many connectors: GitHub, GitLab, LDAP, SAML) or direct OIDC configuration in argocd-cm, then mapping IdP groups to RBAC roles in argocd-rbac-cm.
What is the Argo CD Image Updater and what risk does it introduce?A controller that watches registries for new tags and writes updated image references back to manifests/Git automatically. Risk: if used on production paths, it can bypass PR-based approval gates, undermining change control.
Explain ArgoCD's RBAC model.Casbin-style policy CSV mapping subjects (users/SSO groups) to permissions (actions like get/sync/delete) on resources (applications, projects, clusters, repositories), often scoped per-project (e.g., team-payments/*).
What's the difference between label-based and annotation-based resource tracking?Label-based uses app.kubernetes.io/instance, which can collide with the same label used for other purposes (e.g., Helm's own instance label). Annotation-based uses a dedicated tracking-id annotation, avoiding that collision — recommended for new installs.
How do PreSync/PostSync hooks work?Resource hooks (Kubernetes Jobs/Pods annotated with argocd.argoproj.io/hook: PreSync|Sync|PostSync) run at specific points in the sync lifecycle, useful for DB migrations or smoke tests before/after the main sync.
What happens if Git becomes unavailable?ArgoCD continues serving its last-cached manifests/state from repo-server's local clone and Redis cache; new commits simply can't be picked up until Git access is restored. Existing Applications keep running unaffected.
How would you design disaster recovery for an ArgoCD-managed platform?Treat ArgoCD's own install as GitOps-managed (App of Apps for ArgoCD itself); back up cluster/repo credential secrets separately (e.g., via Velero or a secrets manager); on DR, reinstall ArgoCD from Git and re-apply the root Application to reconcile everything else automatically.
What's the difference between Sync Waves and Sync Phases?Sync Phases are PreSync/Sync/PostSync (broad ordering). Sync Waves (via argocd.argoproj.io/sync-wave annotation) provide fine-grained ordering within the Sync phase, letting you sequence resource application (e.g., CRDs before the operators that use them).
Why might two engineers see different ArgoCD UI states for the same Application?Caching/propagation delay between repo-server, Redis, and the application controller, or different users have RBAC-scoped visibility limiting what they can see; a hard refresh (--hard-refresh) forces re-evaluation bypassing cache.
