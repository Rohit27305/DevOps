Chapter 1: Grafana Fundamentals & Visual Observability

Grafana is an open-source visualization tool designed to display metrics, logs, and traces. Unlike other dashboards that copy data into local storage, Grafana acts as a stateless query proxy. When you open a dashboard, Grafana sends queries directly to the data source (like Prometheus or Loki) and renders charts on-the-fly. This keeps the Grafana backend lightweight and easy to operate.

The stateless design means that Grafana does not store your metric data. Instead, it securely stores dashboard configurations, user profiles, and organization permissions in a metadata database (like PostgreSQL). This architecture allows you to scale Grafana horizontally by running multiple stateless pods behind a load balancer.

Grafana supports a wide variety of data sources, allowing you to combine metrics, logs, and traces in a single dashboard. This unified visualization model helps SRE teams correlate performance indicators across different systems during incident response.

# Example of Grafana server configuration section [server] protocol = http http_addr = 0.0.0.0 http_port = 3000 domain = grafana.corp.internal enforce_domain = true
SRE OPERATIONAL RUNBOOK NOTE

Stateless horizontal scaling requires a shared session store (like Redis) and a shared database (like PostgreSQL) to prevent user logout loops when requests are routed across different pods.

CRITICAL SRE WARNING

Do not store production dashboard configurations in the default SQLite database. SQLite does not support concurrent writes from multiple replicas, which can lead to database corruption.

Chapter 2: Complete Component Architecture & Blueprint

The Grafana server process consists of several key components working together:

• Frontend Canvas: A React-based web application that runs in the browser. It handles dashboard rendering, user interactions, and query construction. It uses Canvas and SVG to draw high-performance charts.

• HTTP API Server: A Go-based backend that exposes REST endpoints for dashboard management, authentication, and user administration.

• Datasource Proxy: A secure backend service that routes queries from the browser to the data sources. It decrypts credentials, appends authentication headers, and proxies query requests.

• Alerting Engine: Evaluates alert rules against configured data sources, tracks alert states, and forwards notifications to contact points.

• Plugin Manager: Loads and manages panels, data sources, and applications that extend Grafana's functionality.

Chapter 3: Unified Data Source Integration (Prometheus, Loki, Tempo)

Grafana's primary strength is its ability to query data from many different sources. Data sources are configured in the backend and can be added via the UI or declarative configuration files. Grafana supports core open-source monitoring systems natively:

• Prometheus: Used for querying and visualizing metric time-series data using PromQL.

• Loki: Used for querying and visualizing log streams using LogQL.

• Tempo: Used for querying and visualizing distributed traces.

Grafana allows you to link these data sources together. For example, you can click on a spike in a Prometheus metric chart to open the corresponding logs in Loki, and then click on a log entry to view the trace in Tempo. This correlation speeds up incident investigation.

# Datasource provisioning configuration example apiVersion: 1 datasources: - name: Prometheus-Prod type: prometheus access: proxy url: http://prometheus-k8s.monitoring.svc:9090 isDefault: true jsonData: httpMethod: POST timeInterval: 15s
SRE OPERATIONAL RUNBOOK NOTE

Use provisioning configurations (YAML files) to manage data sources. This allows you to treat configurations as code (GitOps) and ensures consistency across environments.

CRITICAL SRE WARNING

When configuring data sources, always select 'Server' access (Proxy mode). 'Browser' access forces clients to connect directly to the database, exposing database credentials to the browser.

Chapter 4: Panel Types & Visualization Best Practices

Grafana provides a variety of panel types to represent data effectively:

• Time Series: The default panel for visualizing metrics over time. It supports multiple display modes, overrides, and thresholds.

• Stat: Displays a single aggregate value (e.g., current CPU usage) with optional sparklines and color thresholds.

• Bar Gauge: Displays progress bars representing resource utilization.

• Table: Displays raw data in tabular format, useful for listing active alerts or pod statuses.

Use visualization best practices to design clear dashboards. Avoid cluttered charts with too many lines, use color thresholds consistently (e.g., red for critical status), and keep dashboards organized using collapsible rows.

# Example of panel JSON structure within a dashboard model { "type": "timeseries", "title": "API Latency", "gridPos": { "h": 8, "w": 12, "x": 0, "y": 0 }, "targets": [ { "expr": "histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))", "refId": "A" } ] }
SRE OPERATIONAL RUNBOOK NOTE

Limit the number of panels on a single dashboard to 15-20. Large dashboards with many panels load slowly, consume client CPU, and generate high query load on backend databases.

CRITICAL SRE WARNING

Do not use absolute color values on your panels without considering users with color vision deficiencies. Use Grafana's built-in accessible color palettes.

Chapter 5: Query Lifecycle, Backend-Sourced vs Client-Sourced Queries

Understanding the lifecycle of a query helps SREs optimize dashboard performance. When a user opens a dashboard, the React frontend issues query requests. These queries can be processed in two ways:

1. Client-Sourced Queries: The browser sends queries directly to the data source endpoint. This requires CORS (Cross-Origin Resource Sharing) to be configured on the database, and exposes the database directly to the network.

2. Backend-Sourced Queries: The browser sends queries to the Grafana HTTP API. The Grafana server decrypts the database credentials, executes the query on behalf of the user, and returns the result. This proxying secures credentials and simplifies network routing.

# Conceptual query proxy request path [Browser User] -> GET /api/datasources/proxy/1/api/v1/query?query=up -> [Grafana Server (Decrypts Auth)] -> POST /api/v1/query (to Prometheus Backend) -> Returns data to Grafana -> returns to User
SRE OPERATIONAL RUNBOOK NOTE

Enable query caching in Grafana (available in Grafana Enterprise or via plugins) to reduce query volume. This caches data source responses, preventing duplicate queries from overloading databases during incident reviews.

CRITICAL SRE WARNING

Backend-sourced queries increase memory and CPU usage on the Grafana server. Ensure the server has sufficient network bandwidth to handle proxied data streams.

Chapter 6: Dashboard JSON Model & Version Control (GitOps)

Every Grafana dashboard is represented internally as a JSON document. This document contains all panel configurations, queries, layout coordinates, variables, and styling settings. By managing these JSON files in version control, you can apply GitOps practices to dashboard configurations.

With a GitOps workflow, changes to dashboards are proposed via pull requests, reviewed by team members, and deployed automatically using CI/CD pipelines. You can use tools like Terraform, Grizzly, or the Grafana REST API to automate dashboard deployments, ensuring configurations are consistent across staging and production environments.

# Bash script to deploy a dashboard JSON via Grafana API curl -X POST \ -H "Authorization: Bearer glsa_xxx" \ -H "Content-Type: application/json" \ -d @dashboard.json \ http://grafana.prod.internal:3000/api/dashboards/db
SRE OPERATIONAL RUNBOOK NOTE

Configure dashboard folders with appropriate permissions. Maintain a clear separation between 'System Dashboards' (managed via GitOps, read-only to users) and 'Playground Folders' (where developers can create custom panels).

CRITICAL SRE WARNING

Manual edits to provisioned dashboards (deployed via YAML/GitOps) will be overwritten when the Grafana server restarts or re-scans the configuration directory. Ensure you edit the source JSON in Git.

Chapter 7: Dashboard Variables, Dynamic Rows & Multi-Cluster Filtering

Dashboard Variables make dashboards dynamic. Instead of hardcoding values (like a specific pod name or region), you define variables that users can select from drop-down menus at the top of the dashboard.

Types of variables include:

• Query: Dynamically queries a data source for values (e.g., retrieving all active namespaces).

• Custom: A hardcoded list of values.

• Textbox: Allows users to input free-form text.

Variables can be nested, where selecting a value in the first variable (e.g., `Region`) filters the options available in the second (e.g., `Cluster`). SREs can also use variables to dynamically repeat rows or panels for each selected value, simplifying multi-environment monitoring.

# PromQL target query utilizing variables sum(rate(container_cpu_usage_seconds_total{cluster="$cluster", namespace="$namespace"}[5m]))
SRE OPERATIONAL RUNBOOK NOTE

Use variables to create single, reusable dashboards for multi-cluster environments. This avoids dashboard fragmentation and simplifies maintenance.

CRITICAL SRE WARNING

If a query variable retrieves too many values (e.g., 5,000 pod names), the dropdown menu will load slowly and degrade browser performance. Limit variable query results using regex filters.

Chapter 8: Metadata DB & SQLite Migrations

Grafana requires a SQL database to store user profiles, organizations, dashboards, alert rules, and session data. By default, it uses SQLite, which is stored as a single file on the local disk. SQLite is suitable for development and testing, but it is not designed for production scaling.

SQLite locks the database file during write operations. If you run multiple Grafana replicas or have many concurrent users saving dashboards, SQLite write contention will cause database locked errors and corruption.

For production environments, migrate Grafana to an external database like PostgreSQL or MySQL. This allows you to run multiple stateless Grafana replicas, enables high availability, and supports database backups.

# Configuration to migrate database from SQLite to PostgreSQL [database] type = postgres host = postgres-ha.infra.svc.cluster.local:5432 name = grafana_metadata user = grafana_app password = SEC_PASS_REPLACED ssl_mode = require max_open_conn = 30 max_idle_conn = 10
SRE OPERATIONAL RUNBOOK NOTE

Run database migrations during scheduled maintenance. Grafana automatically runs migrations on startup when upgrading versions, which can temporarily lock tables in large databases.

CRITICAL SRE WARNING

Always perform a database backup before upgrading Grafana. If a database migration fails during upgrade, the metadata can become corrupted, requiring a restore.

Chapter 9: Shared Caching, Sessions, & Redis Cluster Integration

When running multiple replicas of Grafana behind a load balancer, users will face sudden logouts if session data is stored locally in the pod's memory. To prevent this, configure a shared session provider like Redis.

Redis acts as a centralized store for session states, user permissions, and login states. When a user requests a dashboard, any Grafana pod can validate the session ID against Redis. Redis can also cache data source query responses, reducing the load on backend databases during high-traffic incidents.

# Configuration to enable Redis session storage [session] provider = redis provider_config = addr=redis-cluster.infra.svc:6379,password=SEC_REDIS_REPLACED,pool_size=100,ssl=true cookie_secure = true session_life_time = 86400
SRE OPERATIONAL RUNBOOK NOTE

Monitor Redis replication lag and memory usage. If Redis runs out of memory, active users will be logged out, and dashboard configurations may fail to load.

CRITICAL SRE WARNING

Ensure session cookies are secure (`cookie_secure = true`) when running Grafana behind SSL/TLS proxies to prevent session interception.

Chapter 10: High Availability & Clustering (Grafana stateless scaling)

To deploy Grafana in a High Availability (HA) configuration, you must scale the server stateless replicas horizontally behind a Load Balancer (like AWS ALB or Nginx). The stateless replicas do not share local storage; instead, they coordinate using a shared database (PostgreSQL) and session store (Redis).

This setup allows pods to be terminated or rescheduled without affecting user sessions. SREs can perform rolling updates to Grafana deployments with zero downtime, and the load balancer distributes traffic evenly across active nodes, improving performance during high-traffic events.

# Nginx load balancer configuration for Grafana HA cluster upstream grafana_servers { server grafana-1.monitoring.svc:3000; server grafana-2.monitoring.svc:3000; keepalive 32; } server { listen 80; location / { proxy_pass http://grafana_servers; proxy_http_version 1.1; proxy_set_header Connection ""; } }
SRE OPERATIONAL RUNBOOK NOTE

Configure a unified secret key (`secret_key`) across all Grafana replica pods. Mismatched keys will prevent replicas from decrypting session cookies, leading to login loops.

CRITICAL SRE WARNING

Do not configure sticky sessions on your load balancer as a substitute for a shared session store. Sticky sessions are fragile and do not support true high availability.

Chapter 11: Authentication & Single Sign-On (OAuth2, OIDC, SAML, LDAP)

Securing access to dashboards is critical for SRE teams. Grafana supports multiple authentication methods, including Single Sign-On (SSO) protocols like OAuth2, OpenID Connect (OIDC), SAML, and LDAP. This allows you to integrate Grafana with your identity provider (e.g., Okta, Keycloak, Auth0, Active Directory) to manage access centrally.

Once authenticated, users are assigned to roles based on group memberships in the identity provider, simplifying user provisioning.

# Generic OAuth2 integration with Keycloak [auth.generic_oauth] enabled = true name = Keycloak client_id = grafana client_secret = SEC_SECRET_REPLACED scopes = openid profile email auth_url = https://keycloak.corp.com/realms/infra/protocol/openid-connect/auth token_url = https://keycloak.corp.com/realms/infra/protocol/openid-connect/token api_url = https://keycloak.corp.com/realms/infra/protocol/openid-connect/userinfo role_attribute_path = contains(roles, 'admin') && 'Admin' || contains(roles, 'editor') && 'Editor' || 'Viewer'
SRE OPERATIONAL RUNBOOK NOTE

Use role mapping to assign user permissions dynamically based on active directory groups, ensuring that only SRE team members have admin access.

CRITICAL SRE WARNING

Disable local password login (`disable_login_form = true`) once SSO is enabled to prevent users from bypassing your identity provider.

Chapter 12: Authorization, RBAC, & Multi-Org Access Policies

Grafana supports a multi-tenant authorization model. SREs can organize users and dashboards into separate Organizations. Organizations act as hard security boundaries; dashboards, data sources, and users cannot be shared across organizations without explicit configuration.

Within an organization, access is managed using Role-Based Access Control (RBAC). The default roles are Admin, Editor, and Viewer. In Grafana Enterprise, you can define fine-grained permissions to restrict access to specific folders, dashboards, or data sources, helping teams meet compliance requirements.

# Provisioning configuration mapping teams to folders # Note: Enforced via external API or Terraform configurations resource "grafana_folder_permission" "sre_folder_perms" { folder_uid = "sre_dashboards" permissions { team_id = 1 # SRE Team permission = "Admin" } permissions { team_id = 2 # Dev Team permission = "View" } }
SRE OPERATIONAL RUNBOOK NOTE

Use Organizations to separate multi-tenant environments (e.g., separating internal infrastructure monitoring from external customer dashboards).

CRITICAL SRE WARNING

Users with Admin access to an organization can create or modify data sources, exposing database access. Restrict Admin roles to trusted SRE members.

Chapter 13: Alerting Engine (Unified Alerting, Evaluators, Mute Timings)

Grafana Unified Alerting allows SREs to define alert rules that query data sources, evaluate thresholds, and send notifications. Alert rules are evaluated by a background scheduler in the Grafana server.

The alerting engine tracks alert states: Normal, Pending, and Firing. If an alert threshold is met, the alert enters the Pending state for a configured duration before transitioning to Firing. This delay reduces alert noise from temporary spikes. SREs can also configure Mute Timings to suppress alerts during planned maintenance windows.

# Alert rule definition in Grafana provisioning format groups: - orgId: 1 name: SRE-Alert-Group rules: - uid: api_latency_alert title: High API Latency condition: A data: - refId: A relativeTimeRange: from: 300 to: 0 datasourceUid: prometheus-prod model: expr: "histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) > 2.0"
SRE OPERATIONAL RUNBOOK NOTE

Align alert evaluation intervals with your database scrape intervals. Evaluating alerts too frequently generates redundant query load on databases.

CRITICAL SRE WARNING

If the alerting scheduler falls behind because of slow queries, Grafana will record alert execution errors, which can result in missed notifications.

Chapter 14: Contact Points & Custom Notification Templates

Contact Points define where alerts are sent when they trigger. Grafana supports integrations with Slack, PagerDuty, email, and Webhook destinations.

SREs can customize notifications using the Go Template Engine. Templates allow you to format alert messages, include dynamic data (like actual metric values), and add links to dashboards and runbooks, helping teams respond quickly to incidents.

# Custom notification template example {{ define "slack.title" }} [{{ .Status | toUpper }}] {{ .CommonAnnotations.summary }} {{ end }} {{ define "slack.message" }} *Details:* {{ .CommonAnnotations.description }} *Runbook:* {{ .CommonAnnotations.runbook_url }} {{ end }}
SRE OPERATIONAL RUNBOOK NOTE

Include links to relevant dashboards and runbooks in all alert templates. This gives on-call engineers immediate access to diagnostic tools and procedures.

CRITICAL SRE WARNING

Make sure your templates handle unresolved alerts. Failing to test templates for recovery states can lead to confusing notifications.

Chapter 15: Grafana Plugins Architecture (Panel, Data Source, App Plugins)

Grafana's extensible architecture is built around Plugins, which fall into three categories:

• Panel Plugins: Add new visualizations (e.g., specialized graphs or gauges).

• Data Source Plugins: Allow Grafana to query new databases.

• App Plugins: Package dashboards, data sources, and panels into a single application.

Plugins run in a sandboxed environment. Grafana enforces signing requirements on all plugins to prevent execution of unauthorized code. SREs can configure allowed plugins in the server configuration file.

# Allow installation of unsigned plugins (for development only) [plugins] allow_loading_unsigned_plugins = custom-datasource-plugin,internal-panel-plugin
SRE OPERATIONAL RUNBOOK NOTE

Verify plugin signatures before deploying them in production. Unsigned or unverified plugins can introduce security vulnerabilities and performance bottlenecks.

CRITICAL SRE WARNING

Unsigned plugins will fail to load in Grafana by default. Do not disable signature verification in production environments.

Chapter 16: Enterprise Features (Reporting, Audit Logs, Usage Analytics)

Grafana Enterprise offers advanced capabilities for large organizations:

• PDF Reporting: Automatically generates and emails PDF copies of dashboards.

• Audit Logs: Records user actions (dashboard saves, login attempts, permission changes) for compliance.

• Usage Analytics: Tracks dashboard views and query execution times to locate unused panels and optimize slow queries.

These features help SRE teams manage large Grafana deployments, track user activity, and maintain compliance standards.

# Enterprise audit logging configuration [enterprise.auditing] enabled = true log_filters = action=dashboard-save,action=login-attempt writer = file file_path = /var/log/grafana/audit.log
SRE OPERATIONAL RUNBOOK NOTE

Review usage analytics regularly. Delete unused dashboards to clean up your metadata database and reduce background query load.

CRITICAL SRE WARNING

Audit logs can generate significant log volume. Configure log rotation and retention policies to prevent disk space exhaustion.

Chapter 17: High Cardinality Queries, Query Cache & Limit Policies

High cardinality queries can cause performance issues in Grafana. When a dashboard requests data with millions of points, it can overload the frontend and crash the user's browser.

To prevent this, configure Query Limits. SREs can limit the maximum number of data points per panel and set query timeouts. Grafana also supports Query Caching, which stores database responses to speed up repeated queries.

# Configuration to cache data source queries [query_caching] enabled = true ttl = 5m max_size_mb = 100
SRE OPERATIONAL RUNBOOK NOTE

Enable query limits on public-facing dashboards. Set `max_data_points` to match the screen width (typically 1500 points) to optimize rendering.

CRITICAL SRE WARNING

High cardinality queries can cause OOM crashes on the Grafana server if the backend proxy runs out of memory processing results.

Chapter 18: Grafana Provisioning (Dashboards, Datasources, Alerting via YAML)

Grafana Provisioning allows SREs to manage configurations declaratively. Instead of creating data sources and dashboards manually in the UI, you define them in YAML and JSON files.

Grafana scans a provisioning directory on startup and applies the configurations. This supports a GitOps workflow, where configurations are managed in version control and deployed automatically.

# Provisioning configuration mapping datasources apiVersion: 1 datasources: - name: Prometheus-Demo type: prometheus url: http://localhost:9090 access: proxy
SRE OPERATIONAL RUNBOOK NOTE

Use provisioning to ensure configurations are consistent across environments. This prevents configuration drift and simplifies disaster recovery.

CRITICAL SRE WARNING

Manual edits to provisioned dashboards in the UI will be lost on server restart. Make all dashboard changes in your version control repository.

Chapter 19: SRE Troubleshooting & Diagnostics (Deadlocks, OOM, Latency)

When troubleshooting Grafana incidents, SREs typically encounter three main scenarios:

1. Database Locked Errors: Caused by SQLite write contention. SREs can resolve this by migrating the metadata database to PostgreSQL.

2. User Logout Loops: Triggered by mismatched secret keys across replica pods. SREs can fix this by setting a unified key.

3. Slow Dashboard Loading: Caused by slow data source queries. SREs can debug this by checking the query logs and configuring query caches.

# Command to check Grafana logs for database deadlocks # 1. Inspect logs for locking messages: kubectl logs deployment/grafana -n monitoring | grep -E -i "database locked|deadlock"
SRE OPERATIONAL RUNBOOK NOTE

Configure a health check endpoint for Grafana (`/api/health`). Use this endpoint in your load balancer configuration to route traffic away from unhealthy pods.

CRITICAL SRE WARNING

Restarting the database during active migrations can corrupt the metadata schema. Wait for migrations to complete before performing maintenance.

Chapter 20: Performance Tuning & Resource Sizing (Go GC settings, DB Pools)

Tuning the Grafana server parameters improves performance under heavy load:

• Go Garbage Collection: Tune the `GOGC` environment variable to control memory usage. Setting `GOGC=80` increases collection frequency, reducing memory usage at the cost of slight CPU overhead.

• Database Connection Pools: Configure connection pool limits (`max_open_conn` and `max_idle_conn`) to match your database capacity, preventing connection exhaustion under peak load.

# Docker compose environment variables for Grafana performance tuning environment: - GOGC=80 - GOMAXPROCS=4 - GF_DATABASE_MAX_OPEN_CONN=40 - GF_DATABASE_MAX_IDLE_CONN=15
SRE OPERATIONAL RUNBOOK NOTE

Monitor database connection pool metrics. Alert when active connections reach 80% of your maximum pool size to prevent connection failures.

CRITICAL SRE WARNING

Setting connection pool limits too high can overload your external database, while setting them too low will cause query latency for users.

Chapter 21: Grafana vs Competitors (Kibana, Datadog, CloudWatch)

Selecting a visualization platform depends on your monitoring requirements:

• Kibana: Designed specifically for visualizing Elasticsearch data. While powerful for log analysis, it is less suited for multi-datasource metrics and tracing.

• Datadog: A comprehensive SaaS platform. It offers advanced features but introduces high subscription costs and vendor lock-in.

• AWS CloudWatch: A managed monitoring service for AWS. It is simple to use but lacks the advanced layout and multi-datasource features of Grafana.

Grafana remains the default choice for SRE teams due to its open-source model, extensive plugin ecosystem, and support for multi-datasource correlation.

Chapter 22: Real-World Startup & Enterprise Architectures

Grafana deployments scale with your infrastructure requirements:

• Startup Architecture: A single Grafana container running with a local SQLite database, querying a local Prometheus instance. This is simple and cost-effective.

• Enterprise Architecture: A stateless Grafana cluster deployed in Kubernetes. Pods run behind an ALB load balancer, using an external PostgreSQL instance for metadata and a Redis cluster for sessions. This configuration supports high availability, zero-downtime updates, and global queries.

# Enterprise helm chart values snippet for Grafana HA replicas: 3 env: GF_SESSION_PROVIDER: redis GF_SESSION_PROVIDER_CONFIG: "addr=redis-cluster:6379,pool_size=100" database: type: postgres host: pg-master.infra.svc:5432 name: grafana
SRE OPERATIONAL RUNBOOK NOTE

Use automated pipelines to backup your metadata database regularly. A loss of the PostgreSQL database will delete all user-created dashboards and permissions.

CRITICAL SRE WARNING

Ensure that your Grafana replica pods have identical config files. Configuration drift across replicas can cause erratic session behavior.

Chapter 23: SRE Interview Prep & 75 Core Q&A Bank

Here are key technical questions and answers for SRE interviews covering Grafana architecture and operations:

Q1: What are database locked errors in Grafana and how do you resolve them? A1: Database locked errors occur when SQLite is subjected to concurrent writes from multiple replicas. SREs can resolve this by migrating the metadata database to PostgreSQL.

Q2: How do you scale Grafana horizontally for high availability? A2: SREs can scale Grafana horizontally by running multiple stateless replica pods behind a load balancer, using a shared database (PostgreSQL) and session store (Redis).

Q3: What is the difference between direct and proxy datasource access in Grafana? A3: Direct access forces the browser to query the database directly (exposing credentials). Proxy access routes queries through the Grafana server, securing credentials.

Q4: What are dashboard variables and how do they work? A4: Dashboard variables are dynamic fields that allow users to filter dashboard data (e.g. by region or namespace) using dropdown menus at the top of the panel.

Q5: How do you manage Grafana configurations declaratively? A5: SREs can manage configurations declaratively using the Provisioning directory, where data sources, dashboards, and alerts are defined in YAML and JSON files.

# API request to verify active sessions curl -s -H "Authorization: Bearer glsa_xxx" http://localhost:3000/api/admin/users
SRE OPERATIONAL RUNBOOK NOTE

Prepare for interview questions by understanding the details of OAuth2 role mapping and the SQL database schema used by Grafana.

CRITICAL SRE WARNING

Make sure you can explain the security implications of direct vs proxy access modes in interview scenarios.

Chapter 24: Comprehensive Glossary Reference

• **Provisioning**: The declarative configuration of Grafana data sources and dashboards using files.

• **SSO (Single Sign-On)**: An authentication scheme that allows users to log in with a single set of credentials across multiple applications.

• **RBAC (Role-Based Access Control)**: An authorization scheme that manages permissions based on user roles (Admin, Editor, Viewer).

• **Query Proxy**: The Go backend layer that routes database queries from the browser, securing credentials.

• **Image Renderer**: A stateless microservice that captures PNG snapshots of dashboard panels.

• **Datasource**: A database connection (e.g., Prometheus, Loki) configured in Grafana to retrieve metrics.

• **Dashboard JSON**: The internal JSON representation of a Grafana dashboard.

• **Alerting Engine**: The backend scheduler that evaluates alert rules and routes notifications.

• **Mute Timing**: A schedule used to suppress alert notifications during maintenance windows.

• **Redis**: A shared session store used to synchronize user logins across stateless replicas.
