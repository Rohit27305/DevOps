01 Section 1: Kubernetes Fundamentals Fundamentals ▾

1.1 Why Kubernetes Was Created

Before Kubernetes, large-scale containerized applications at Google (and the broader industry) suffered from the same fundamental problems: containers needed to be scheduled across a fleet of machines, failures needed to be detected and healed automatically, load had to be distributed, rolling updates required careful orchestration, and all of this had to happen consistently across thousands of nodes. Google had been running containers in production for over a decade using internal systems (Borg, then Omega), and in 2014 they open-sourced a reimagining of those systems as Kubernetes (from the Greek for "helmsman"). The CNCF accepted it in 2016 and it has since become the de facto standard for container orchestration.

Declarative config via YAML — the same manifest works in any compliant cluster 7. Resource requests/limits enable tight bin-packing without starvation

1.2 Container Orchestration — What It Means

Container orchestration is the automated management of the full lifecycle of containerized workloads across a cluster of machines: scheduling (where does this container run?), scaling (how many copies are needed?), networking (how do containers find and talk to each other?), storage (how does data persist across container restarts?), health monitoring (how is failure detected and recovered?), and configuration injection (how do containers get their configuration without it being baked into the image?).

1.3 Desired State and Reconciliation

Kubernetes' entire operational model is built on one idea: you declare what you want (desired state), and Kubernetes continuously works to make reality match it. You never tell Kubernetes "create a pod now" as an imperative step — you tell it "I want 3 replicas of this pod to always be running." The controller manager's reconciliation loop then ensures that if any of those 3 pods die, fail health checks, or the node runs out of resources, new pods are immediately created elsewhere to maintain the declared count.

02 Section 2: Kubernetes Architecture Architecture ▾

2.1 kube-apiserver

The API server is the single gateway for all cluster operations — the only component that directly reads from and writes to etcd. Every other component (kubelet, scheduler, controllers, kubectl) communicates exclusively through the API server, never touching etcd directly.

Internal Workflow

AuthN: Who are you? │ │ (client cert, bearer token, OIDC, webhook) │ │ 2. AuthZ: Are you allowed to do this? │ │ (RBAC, ABAC, Node authorizer, Webhook) │ │ 3. Admission Control: Should this be allowed/mutated? │ │ (MutatingWebhook → ValidatingWebhook) │ │ 4. Validation: Is this object schema-valid? │ │ 5. Persist to etcd │ │ 6. Return 201 Created to caller │ │ 7. Event: other controllers watching this resource are notified │ └────────────────────────────────────────────────────────────────┘

Key Features

  • Horizontally scalable — in HA setups, multiple API server replicas behind a load balancer (only stateless component in the control plane)
  • Watch API: clients establish persistent connections receiving a stream of events when objects change — foundational for the controller pattern
  • Aggregation Layer: allows extending the API server with custom API groups (e.g., metrics-server, custom CRDs via aggregated API servers)
  • Audit logging: every request can be logged for compliance/forensics

2.2 etcd

etcd is a distributed key-value store (based on the Raft consensus algorithm) that serves as Kubernetes' backing store for all cluster state. It stores all API objects: nodes, pods, deployments, services, secrets, ConfigMaps, RBAC policies — everything. etcd is the single source of truth; if etcd is lost and has no backup, the entire cluster's state is unrecoverable (the workloads still run until they fail, but Kubernetes cannot manage them).

etcd storage organization: /registry/pods/default/my-pod /registry/deployments/production/web-deployment /registry/services/kube-system/kube-dns /registry/secrets/default/my-secret (may be encrypted with EncryptionConfig) /registry/nodes/worker-node-1

2.3 kube-scheduler

The scheduler watches for newly created pods that have no assigned node (spec.nodeName is empty) and selects the best node for each pod using a multi-phase scoring algorithm.

2.5 cloud-controller-manager

The cloud-controller-manager implements cloud-provider-specific control loops that were historically embedded in the core kube-controller-manager. It runs as a separate binary, maintained by cloud providers, and handles: Node lifecycle (syncing cloud provider node metadata), Route management (configuring cloud network routes for pod CIDRs), and Service load balancer management (provisioning cloud LBs for Service type=LoadBalancer).

2.6 kubelet

The kubelet is the primary node agent, running on every worker node. It is responsible for ensuring that the containers described in PodSpecs are running and healthy on its node. The kubelet does NOT manage containers not created by Kubernetes.

kubelet Workflow

2.7 kube-proxy

kube-proxy runs on every node and implements the Service abstraction at the network level — translating a Service's stable ClusterIP into the actual pod IP endpoints behind it. It maintains a set of network rules (iptables or IPVS) that intercept traffic destined for a Service IP and forward it to one of the backing pods.

yaml
Modes: iptables mode (default): - Watches Services/Endpoints, writes iptables PREROUTING/NAT rules - Random pod selection via iptables statistic module - O(n) rule count grows with cluster size; can be slow for very large clusters IPVS mode (performance-oriented): - Uses Linux kernel's IP Virtual Server module - O(1) lookup vs O(n) for iptables - Supports additional load balancing algorithms (rr, lc, dh, sh, sed, nq) - Recommended for clusters with >1000 services Note: With Cilium CNI (eBPF mode), kube-proxy can be completely replaced — Cilium handles all service routing in eBPF programs without kube-proxy overhead.

2.8 Container Runtime and CRI

The Container Runtime Interface (CRI) is a gRPC API that allows kubelet to communicate with any compliant container runtime without coupling to a specific implementation. The kubelet calls CRI operations: RunPodSandbox, CreateContainer, StartContainer, StopContainer, RemoveContainer, ListContainers, etc.

2.9 CNI (Container Network Interface)

CNI is a specification and set of libraries for configuring network interfaces in Linux containers. When kubelet creates a pod sandbox, it calls the configured CNI plugin binary, which sets up the veth pair, assigns a pod IP from the node's pod CIDR, and configures routes. CNI plugins implement the cluster-wide flat networking model (all pods can reach all other pods without NAT). Detailed in Section 6.

2.10 CSI (Container Storage Interface)

CSI is a specification that allows storage vendors to write plugins that work with any container orchestrator supporting the standard. A CSI driver runs as pods in the cluster and responds to gRPC calls from the kubelet and the kube-controller-manager to provision/attach/mount/unmount/detach/delete volumes. Detailed in Section 7.

3.4 Spec vs Status — The Core of Kubernetes Objects

Every Kubernetes object has a spec (the desired state, written by users/controllers) and a status (the actual state, written by the system). The reconciliation loop's job is to drive status toward spec. Never manually modify an object's status field — that is the system's responsibility and changes are ignored or overwritten.

3.5 Finalizers

Finalizers are string keys set in metadata.finalizers. When you delete an object with finalizers, Kubernetes does NOT immediately delete it — it sets a deletionTimestamp and waits for all finalizers to be removed. The controller watching that object type must perform cleanup work then remove its finalizer key, at which point Kubernetes proceeds with deletion. This prevents orphaned resources (e.g., a PV finalizer prevents deletion while a PVC is still using it).

yaml
metadata: name: my-pvc finalizers: - kubernetes.io/pvc-protection # prevents deletion while pod is using it

3.6 Owner References and Garbage Collection

Owner references create parent-child relationships between objects, enabling cascading garbage collection. When a Deployment owns a ReplicaSet, and the ReplicaSet owns Pods — deleting the Deployment triggers the garbage collector to delete the ReplicaSet and its Pods. Background GC (default): owner deleted first, then orphan children collected asynchronously. Foreground GC: deletion blocks until all owned objects are also deleted.

yaml
ownerReferences: - apiVersion: apps/v1 kind: ReplicaSet name: web-84c5c6f49b uid: abc123-... controller: true # marks this as the controlling owner blockOwnerDeletion: true

3.7 ResourceVersion and Optimistic Concurrency

Every Kubernetes object has a resourceVersion — a string token (backed by the etcd revision number) that changes whenever the object is modified. It acts as an optimistic concurrency lock: when you update an object, you must include its current resourceVersion in your request. If another writer modified the object since you read it, your resourceVersion is stale, the update is rejected, and you must re-read and retry — preventing lost-update races between controllers.

4.1 Pod

A Pod is the smallest deployable unit in Kubernetes — a group of one or more containers sharing the same Linux network namespace (IP, ports), IPC namespace, and optionally PID namespace. Containers in a pod communicate over localhost and share mounted volumes. The "pause container" (sandbox) is the first container started in any pod; it holds the network/IPC namespaces so other containers can join/leave without disrupting the network configuration.

yaml
apiVersion: v1 kind: Pod metadata: name: web labels: { app: web } spec: initContainers: # Run sequentially, all must complete before app containers start - name: init-db-check image: busybox command: ["sh", "-c", "until nc -z postgres 5432; do sleep 2; done"] containers: - name: web image: nginx:1.25 ports: - containerPort: 80 resources: requests: { cpu: "100m", memory: "128Mi" } limits: { cpu: "500m", memory: "256Mi" } livenessProbe: httpGet: { path: /healthz, port: 80 } initialDelaySeconds: 10 periodSeconds: 10 failureThreshold: 3 readinessProbe: httpGet: { path: /ready, port: 80 } initialDelaySeconds: 5 periodSeconds: 5 startupProbe: # Disables liveness until app is ready (slow-starting apps) httpGet: { path: /healthz, port: 80 } failureThreshold: 30 periodSeconds: 10 env: - name: DB_HOST valueFrom: secretKeyRef: { name: db-secret, key: host } restartPolicy: Always # Always (default), OnFailure, Never terminationGracePeriodSeconds: 30

4.2 ReplicaSet

A ReplicaSet ensures that a specified number of pod replicas are running at any given time. It uses a label selector to identify "its" pods and creates/deletes pods to match the desired replica count. Do not use ReplicaSets directly — use Deployments, which manage ReplicaSets and add rolling update and rollback capabilities on top.

4.3 Deployment

Deployments are the standard mechanism for deploying stateless applications. A Deployment manages a set of identical pods via a ReplicaSet and provides declarative, automated rolling updates (zero-downtime by default) and instant rollbacks.

bash
apiVersion: apps/v1 kind: Deployment metadata: name: web spec: replicas: 5 selector: matchLabels: { app: web } strategy: type: RollingUpdate rollingUpdate: maxSurge: 1 # At most N extra pods above desired count during update maxUnavailable: 0 # At most N pods below desired count during update # (maxUnavailable=0 + maxSurge=1 = zero-downtime rolling update) template: metadata: labels: { app: web } spec: containers: - name: web image: myapp:v3 # Update: change image tag in spec, Kubernetes creates new RS, scales up new, scales down old # Rollback: kubectl rollout undo deployment/web --to-revision=2

4.4 DaemonSet

A DaemonSet ensures exactly one pod runs on every node (or every node matching a node selector). Used for node-level infrastructure: log collectors (Fluentd, Fluent Bit), monitoring agents (node-exporter, Datadog agent), CNI plugins, storage daemons, security agents (Falco). When nodes are added to the cluster, DaemonSet pods are automatically created on them; when nodes are removed, those pods are garbage-collected.

yaml
spec: selector: matchLabels: { app: node-exporter } updateStrategy: type: RollingUpdate rollingUpdate: maxUnavailable: 1 # How many pods can be unavailable during update

4.5 StatefulSet

StatefulSets manage stateful applications where each instance is unique and must maintain its identity across rescheduling — databases, message brokers (Kafka, Zookeeper), distributed caches. Key guarantees: stable network identity (pod-0, pod-1, pod-2; each gets a predictable DNS name: pod-name.service-name.namespace.svc.cluster.local), stable persistent storage (each pod gets its own PVC via volumeClaimTemplates, reattached to the same pod even after rescheduling), and ordered startup/shutdown (pods created 0→N, deleted N→0 by default).

yaml
apiVersion: apps/v1 kind: StatefulSet metadata: name: postgres spec: serviceName: postgres-headless # REQUIRED: must exist; provides DNS identity replicas: 3 selector: matchLabels: { app: postgres } template: metadata: labels: { app: postgres } spec: containers: - name: postgres image: postgres:16 volumeMounts: - name: data mountPath: /var/lib/postgresql/data volumeClaimTemplates: - metadata: name: data spec: accessModes: [ReadWriteOnce] storageClassName: gp3 resources: requests: storage: 100Gi # Creates PVCs: data-postgres-0, data-postgres-1, data-postgres-2 # Each pod ALWAYS reattaches to ITS OWN PVC even after rescheduling

4.7 Static Pods

Static pods are created directly by the kubelet from manifest files on the node filesystem (typically /etc/kubernetes/manifests/), without going through the API server. They exist outside normal Kubernetes management — the API server displays "mirror pod" objects for visibility but cannot delete them (killing the manifest file on disk is the only way to stop them). Static pods are used for the control plane components themselves (etcd, kube-apiserver, kube-scheduler, kube-controller-manager) when using kubeadm-based installations — a cleverly self-hosting design.

6.1 The Kubernetes Networking Model

Kubernetes requires a flat networking model with three rules:

  1. Every pod gets a unique IP address within the cluster
  2. All pods can communicate with all other pods without NAT
  3. Agents on a node can communicate with all pods on that node

This is implemented by CNI plugins, which configure a virtual network (vxlan overlay, BGP underlay, eBPF, etc.) satisfying these constraints across physical nodes.

10.3 Cluster Autoscaler

The Cluster Autoscaler (CA) watches for pods in Pending state due to insufficient cluster resources, and adds nodes to the underlying autoscaling group (AWS ASG, GCP MIG) to accommodate them. It also removes under-utilized nodes (below a configurable threshold, default 50% for CPU and memory) by safely draining and terminating them.

bash

Yes → trigger ASG to increase desired capacity New node joins → kubelet registers → pod scheduled Scale-in flow: Node utilization < 50% for 10 minutes (default) No pod on the node prevents eviction (PDB, local storage, non-mirrored SA) CA drains node (kubectl drain) → triggers pod rescheduling elsewhere CA terminates node via cloud provider API # Important: CA respects PodDisruptionBudgets during scale-in # Configure: --scale-down-utilization-threshold=0.5 # --scale-down-delay-after-add=10m # --max-node-provision-time=15m

12.2 Informers and Watch Caching

An Informer is a per-resource-type client-side cache within a controller. Instead of querying the API server on every reconciliation loop (expensive), an Informer establishes a single persistent Watch connection to the API server, receives all change events (ADDED/MODIFIED/DELETED), and maintains a fully consistent local in-memory cache. Reconcile calls then read from this cache rather than making API calls, with the cache always reflecting the latest etcd state.

13.1 Architecture and Raft Consensus

yaml
etcd is a distributed, strongly consistent key-value store. It uses the Raft consensus algorithm to guarantee that all replicas agree on the same data, even in the presence of node failures. Raft roles: LEADER: receives all writes, replicates to followers, manages log FOLLOWER: accepts replicated log entries from leader, serves reads CANDIDATE: competes for leadership during election Write flow: 1. Client sends write to any node 2. If not leader: redirect to leader (or leader proxy) 3. Leader appends entry to its log 4. Leader sends AppendEntries RPCs to all followers in parallel 5. Once majority (quorum = n/2 + 1) acknowledges: entry is committed 6. Leader applies entry to state machine (key-value store) 7. Leader responds success to client 8. Followers also apply entry asynchronously etcd cluster sizing: 1 node: no HA, no quorum 3 nodes: survives 1 failure (quorum = 2) 5 nodes: survives 2 failures (quorum = 3) — production recommendation 7 nodes: survives 3 failures — only needed for very large, critical clusters

13.3 etcd Performance Considerations

  • etcd is latency-sensitive; co-locate on SSD NVMe storage with <1ms write latency
  • etcd should run on dedicated nodes, not shared with worker workloads
  • Default db size limit is 2GB; increase with --quota-backend-bytes=8589934592 (8GB max recommended)
  • Compact the revision history and defragment periodically to reclaim space: etcdctl compact <revision> + etcdctl defrag
  • Monitor etcd_disk_wal_fsync_duration_seconds (should be <10ms) and etcd_server_leader_changes_seen_total (frequent leadership changes indicate instability)

20 Section 20: Kubernetes vs Alternatives Comparison ▾

20.1 Kubernetes vs Docker Swarm

Docker Swarm is Kubernetes' closest functional equivalent — also container-native, cluster-wide scheduling, service discovery — but is dramatically simpler and correspondingly less capable. No built-in auto-scaling, no rolling updates with fine-grained control, no native support for StatefulSets, no extensible CRD model, no rich policy engine, no namespace-based multi-tenancy. Swarm saw minimal adoption after Kubernetes emerged and is now in maintenance mode. Choose Swarm only for the smallest, simplest deployments where Kubernetes's learning curve is genuinely prohibitive.

20.2 Kubernetes vs AWS ECS

ECS is AWS's native container orchestration service — fully managed control plane with no customer-facing Kubernetes API, deep AWS integration (IAM task roles, ALB/NLB native integration, CloudWatch native logging), and Fargate (serverless containers, no node management). Trade-offs: AWS-only (multi-cloud ruled out), no standard API (vendor lock-in to ECS task definitions), no native CRD-based extension model, no rich scheduling or policy ecosystem. ECS+Fargate is excellent for AWS-committed teams wanting minimal operational overhead; Kubernetes is better for portability, extensibility, and large complex platforms.

20.3 Kubernetes vs HashiCorp Nomad

Nomad is unique in handling both container and non-container workloads: raw binaries, JVM applications, VMs, batch jobs — all scheduled by the same Nomad cluster. It's simpler to operate than Kubernetes (a single binary, simpler data model) but has a much smaller ecosystem, no native StatefulSet equivalent, weaker storage abstractions, and requires the Consul service mesh for service discovery/mTLS. Nomad is excellent for polyglot organizations that run non-containerized workloads alongside containers and want one scheduler for everything.

20.4 Kubernetes vs OpenShift

OpenShift (Red Hat) is Kubernetes with an extensive enterprise-grade overlay: a built-in developer portal (console), integrated CI/CD (Pipelines, based on Tekton), mandatory SecurityContextConstraints (now replaced by PSS in OKD/upstream), a built-in image registry, stricter security defaults (non-root enforcement), operator lifecycle management (OLM), and commercial Red Hat support. Trade-offs: significantly more complex and opinionated, more expensive, and heavier than vanilla Kubernetes. OpenShift is the right choice for enterprises requiring a supported, opinionated platform with commercial backing and strong compliance defaults.

21 Section 21: Interview Preparation — 150 Questions Interviews ▾

21.1 Fundamentals (Q1–Q20)

Q1: What problem does Kubernetes solve and why was it created?

Kubernetes solves container orchestration at scale: automating placement, scaling, health monitoring, rolling updates, service discovery, and configuration injection for containerized workloads across a cluster of machines. Google created it (open-sourced 2014) based on decade-long experience running production container workloads at Google-scale via Borg and Omega.

Q2: Explain the desired state model.

You declare what you want (a Deployment with 3 replicas), and Kubernetes controllers continuously reconcile actual state toward desired state — if a pod dies, the ReplicaSet controller creates a replacement. You never imperatively issue "create this specific pod" commands; you declare intent and the system ensures it.

Q3: What is a Pod? Why is it the atomic unit rather than a container?

A Pod is one or more containers that share the same Linux network namespace (IP, ports), IPC namespace, and optionally PID namespace. Containers in a pod communicate over localhost. The pod is the atomic unit because some application patterns require tightly-coupled co-scheduled containers (sidecar proxy, log agent, init container) that must share network/storage without the overhead of container-to-container routing.

Q4: What is the difference between a Deployment and a StatefulSet?

Deployments manage stateless pods — all replicas are identical and interchangeable, any pod can be killed and replaced. StatefulSets manage stateful pods that need stable network identity (predictable DNS names: pod-0, pod-1), stable persistent storage (each pod's own PVC always reattached to the same pod), and ordered startup/shutdown. Use StatefulSets for databases, message brokers, and distributed systems where each instance is unique.

Q5: Explain the purpose and behavior of each control plane component.

kube-apiserver: single gateway, AuthN/AuthZ/Admission, persists to etcd, serves Watch API. etcd: distributed KV store, single source of truth for all cluster state. kube-scheduler: watches unscheduled pods, selects best node via filter+score. kube-controller-manager: runs all reconciliation loops (Deployment, ReplicaSet, Node, Endpoint, etc.). cloud-controller-manager: cloud-specific loops (LB, node sync, routes).

Q6: What does the kubelet do?

The kubelet is the node agent that watches for pods assigned to its node, pulls images via CRI, creates pod sandboxes (pause container), invokes CNI for networking, invokes CSI/volume plugins for storage, starts containers, runs health probes, and reports pod status back to the API server.

Q7: What is the difference between a ClusterIP, NodePort, and LoadBalancer service?

ClusterIP: virtual IP reachable only within the cluster; the standard internal service type. NodePort: exposes a static port on every node's IP (30000-32767); traffic forwards to ClusterIP. LoadBalancer: provisions a cloud load balancer (via cloud-controller-manager) with a public IP; routes to NodePort on all nodes. ExternalName: CNAME alias to an external hostname. Headless (clusterIP: None): DNS returns individual pod IPs directly; no virtual IP.

Q8: How does Kubernetes service discovery work?

CoreDNS runs in kube-system and provides DNS resolution for services and pods. Services get stable DNS names: <service>.<namespace>.svc.cluster.local. All pods have search domain entries that allow short names like "web" to resolve to the full DNS name. No service mesh or sidecar is required for basic service discovery.

Q9: What is the pause container and why does it exist?

The pause (infra) container is the first container started in any pod. It holds the pod's network namespace (IP address, port space) and IPC namespace open. Application containers then join the pause container's namespaces. This allows application containers to crash and restart without losing the pod's network identity, and enables sharing of network/IPC between containers without complex coupling.

Q10: Explain labels, selectors, and annotations — what's the difference?

Labels are key-value pairs used for identifying, selecting, and grouping objects — they are the mechanism by which Services select pods and ReplicaSets know which pods they own. Selectors query objects by label (equality-based or set-based). Annotations are key-value pairs for non-identifying metadata not used for selection — larger values allowed, used for tool configurations, human notes, and controller metadata.

Q11: What is a DaemonSet and when would you use it?

A DaemonSet ensures exactly one pod runs on every node (or every node matching a selector). Use it for: log collectors (Fluent Bit), monitoring agents (node-exporter, Datadog), CNI plugins, security agents (Falco), node-level storage daemons — any workload that must run on every node and provides node-scoped functionality.

Q12: Explain init containers and their use cases.

Init containers run sequentially before application containers start, and all must complete successfully before any app container starts. Use cases: wait for a dependency to be ready (database migration check, service availability wait), fetch configuration/secrets from external sources before app starts, run one-time setup tasks (create database schema, configure filesystem permissions). Each init container gets a fresh start on pod restart if it fails.

Q13: What are liveness, readiness, and startup probes? When would each cause different behavior?

Liveness: failing causes kubelet to restart the container. Readiness: failing removes the pod from Service endpoints (traffic stops being sent to it) but does NOT restart it — used for temporarily unready pods (cache warming, config loading). Startup: disables liveness/readiness checks until it passes — prevents liveness from killing a slow-starting container before it's even ready. Use startupProbe for any app that takes more than ~30s to start up.

Q14: What happens when you run kubectl delete pod web-pod on a Running pod?

API server sets pod.metadata.deletionTimestamp. kubelet detects this and: (1) removes pod from Service endpoints immediately, (2) executes preStop hook if defined, (3) sends SIGTERM to container process, (4) waits terminationGracePeriodSeconds (default 30s), (5) sends SIGKILL if process hasn't exited. Meanwhile the owning controller (e.g., ReplicaSet) creates a replacement pod immediately upon seeing the pod's deletion.

Q15: What is ResourceVersion and why does it matter?

Every object has a resourceVersion (etcd revision number) that increments on every update. It enables optimistic concurrency control: if two controllers read the same object and both try to update it, the second writer's resourceVersion is stale and the API server rejects their write with a 409 Conflict — preventing lost-update races in distributed controllers.

Q16: Explain the owner references and garbage collection mechanism.

Owner references create parent-child relationships (Deployment owns ReplicaSet, ReplicaSet owns Pods). The garbage collector watches for objects whose ownerReferences point to non-existent owners and deletes them — cascading cleanup without explicit deletion logic in controllers. Background deletion: delete parent, orphan children temporarily, GC collects them async. Foreground deletion: block until all owned objects are deleted first.

Q17: What is a Headless Service and when would you use it?

A headless service has clusterIP: None, creating no virtual IP. Instead, DNS returns individual pod IPs. Use it with StatefulSets so each pod (postgres-0, postgres-1) gets a stable, individually addressable DNS name for direct replication/clustering connections between pods — used when clients need to know which specific pod they're connecting to, not just any pod behind a load balancer.

Q18: What is a CRD and what is an Operator?

A CRD (Custom Resource Definition) extends the Kubernetes API with a new resource type. An Operator is a CRD plus a custom controller that encodes operational knowledge for managing that resource type — provisioning, scaling, backup, failover, upgrades. Example: a Postgres Operator defines a "PostgresCluster" CRD, and its controller manages StatefulSets, Services, backups, and failover for Postgres instances declared via that CRD.

Q19: What is the difference between kubectl apply and kubectl create?

kubectl create is imperative and fails if the object already exists. kubectl apply is declarative and idempotent: it creates the object if it doesn't exist, or patches it to match the provided spec if it does. apply uses a three-way merge (desired spec, last-applied-configuration annotation, live object) to compute the minimal patch. Always use apply in production and CI/CD workflows.

Q20: What is kube-proxy and what does it actually do at the OS level?

kube-proxy watches Services and Endpoints and writes iptables or IPVS rules on every node that perform destination NAT — translating Service ClusterIPs to actual pod IPs. In iptables mode, it writes PREROUTING/NAT chains that intercept packets to ClusterIPs and DNAT them to a randomly selected pod IP. In IPVS mode, it programs the Linux kernel's IPVS (IP Virtual Server) with the service's backends for faster O(1) lookup.

21.2 Networking (Q21–Q40)

Q21: Describe the three rules of the Kubernetes networking model.

(1) Every pod gets a unique IP address within the cluster. (2) All pods can communicate with all other pods without NAT — a pod on node 1 can reach a pod on node 2 using the pod's IP directly. (3) Agents (kubelet, kube-proxy) on a node can communicate with all pods on that node. CNI plugins implement this flat network model across physical nodes using overlays, BGP, or eBPF.

Q22: Trace the path of a packet from Pod A on Node 1 to Pod B on Node 2.

Pod A sends packet to Pod B's IP. → Kernel routes it out Pod A's eth0 (a veth endpoint) → crosses into the cbr0 (bridge) or similar overlay interface on Node 1 → CNI plugin encapsulates (VXLAN) or routes (BGP) the packet through Node 1's physical NIC → Node 2's physical NIC receives, CNI decapsulates → routes to Pod B's veth endpoint → arrives at Pod B's eth0.

Q23: What is the difference between Calico and Cilium?

Calico uses BGP (or VXLAN) for routing, implements NetworkPolicy at the iptables level, and is the most widely deployed CNI for on-prem and cloud. Cilium uses eBPF programs embedded in the Linux kernel — bypassing iptables entirely — for dramatically better performance and visibility, and supports L7 (HTTP/gRPC) NetworkPolicies that Calico does not. Cilium can also replace kube-proxy with eBPF-based service routing.

Q24: Explain how NetworkPolicies work and what happens without any policies.

Without any NetworkPolicies, all pods in the cluster can communicate with all other pods (open network). When at least one NetworkPolicy selects a pod, only traffic matching the policy's ingress/egress rules is allowed. The standard pattern: apply a default-deny-all policy to every namespace, then add specific allow policies for needed flows (frontend→backend on port 8080, backend→postgres on 5432).

Q25: What is the Gateway API and how does it differ from Ingress?

Gateway API is Kubernetes's next-generation Ingress API with role-oriented design (GatewayClass for infra, HTTPRoute/TCPRoute for apps), richer traffic management (weighted routing, header matching, URL rewriting, mTLS), multi-protocol support, and status propagation. Ingress is limited to HTTP/HTTPS with a single rule structure and relies heavily on controller-specific annotations for advanced features. Gateway API is the future; Ingress remains widely used today but is effectively legacy.

Q26: How does CoreDNS provide DNS resolution within a cluster?

CoreDNS runs as a Deployment (typically 2 replicas) in kube-system. Each pod's /etc/resolv.conf points to CoreDNS's ClusterIP (typically 10.96.0.10) as its nameserver, with search domains set by kubelet. CoreDNS watches Services and Endpoints and serves A records for Services and (for headless services) individual pod A records, SRV records, and CNAME records for ExternalName services.

Q27: A pod is getting a "connection refused" error calling another service. How do you debug?

1. Verify the target service exists and has endpoints: kubectl get svc <name>; kubectl get endpoints <name>. 2. Check pod selector matches pod labels on both objects. 3. Test from inside source pod: kubectl exec <pod> -- curl http://<service>:<port>. 4. Test using ClusterIP directly to isolate DNS from connectivity. 5. Check NetworkPolicies blocking traffic. 6. Check the target pod's actual container port matches the service's targetPort. 7. Check target pod is Running and not in CrashLoopBackOff.

Q28: What is a Service ExternalName type and when would you use it?

ExternalName creates a DNS CNAME record pointing to an external hostname, allowing in-cluster pods to use a stable Kubernetes Service name while the actual target can be an external hostname (e.g., an RDS endpoint). This enables migrating a service from external to internal without changing application configuration — just update the ExternalName to an internal ClusterIP when ready.

Q29: Describe NodePort's behavior and its limitations.

NodePort allocates a static port (30000-32767) on every cluster node's external IP and forwards traffic to the Service's ClusterIP. Limitations: limited port range, unencrypted by default (no TLS at this layer), no hostname-based routing, all nodes exposed (even nodes not running the backend pods — kube-proxy forwards from any node to any pod), direct node IP exposure in firewall rules.

Q30: Explain Topology Spread Constraints and when you'd use them over PodAntiAffinity.

TopologySpreadConstraints spread pods evenly across failure domains (zones, nodes) with a configurable maxSkew (max difference between most-loaded and least-loaded domain). PodAntiAffinity can only express "don't co-locate with pods labeled X on the same node" — it doesn't distribute evenly. Use TopologySpreadConstraints for predictable, even distribution across AZs and nodes; use PodAntiAffinity for strict placement rules.

21.3 Storage and Scheduling (Q31–Q50)

Q31: Explain the difference between PersistentVolume, PersistentVolumeClaim, and StorageClass.

PersistentVolume is the actual storage resource (cluster-scoped, represents an EBS volume, NFS share, etc.). PersistentVolumeClaim is a namespace-scoped request for storage that binds to a matching PV. StorageClass defines a provisioner and parameters for dynamic PV creation — when a PVC references a StorageClass, the CSI driver provisions a new PV automatically. PVs can also be statically pre-provisioned without a StorageClass.

Q32: What is WaitForFirstConsumer volume binding mode and why is it critical for cloud storage?

WaitForFirstConsumer delays PV provisioning until a pod claiming the PVC is actually scheduled. Without it (Immediate mode), the EBS volume is provisioned in a random AZ before the pod is scheduled — and the scheduler might place the pod in a different AZ where the volume is unreachable. WaitForFirstConsumer allows the scheduler to pick a node first, then the CSI driver provisions the volume in that node's AZ.

Q33: What are the access modes and which cloud storage types support ReadWriteMany?

RWO (ReadWriteOnce): one node at a time — block storage like EBS, GCE PD, Azure Disk. ROX (ReadOnlyMany): many nodes read-only — NFS, CephFS. RWX (ReadWriteMany): many nodes read-write — NFS, CephFS, AWS EFS (NFS-based), Azure Files, Lustre, GCS FUSE. Most cloud block storage (EBS) only supports RWO.

Q34: Describe the scheduling process — how does the scheduler select a node?

Filter phase: eliminate all nodes that can't host the pod (insufficient CPU/memory, unmatched node selectors, untolerated taints, missing volumes in required AZ, port conflicts). Score phase: rank remaining nodes on multiple dimensions (resource utilization balance, affinity preferences, image locality). The highest-scoring node wins; the scheduler writes spec.nodeName to the pod via the API server, and the kubelet on that node starts the pod.

Q35: What are taints and tolerations and how do they interact?

A taint on a node repels pods that don't tolerate it. A toleration on a pod allows it to be scheduled onto a tainted node. Taint effects: NoSchedule (new pods rejected), PreferNoSchedule (scheduler avoids but not guaranteed), NoExecute (evicts running pods that don't tolerate). Use case: dedicate GPU nodes to GPU workloads by tainting them and only adding tolerations to pods that actually need a GPU.

Q36: How does PodAntiAffinity help with high availability?

PodAntiAffinity with required rule and topologyKey: kubernetes.io/hostname guarantees no two pods with the specified label run on the same node — if one node fails, not all replicas are lost. With topologyKey: topology.kubernetes.io/zone, replicas are spread across AZs, so a single zone failure doesn't take down the service. Required (requiredDuringScheduling) blocks scheduling if constraint can't be met; preferred (preferredDuringScheduling) is a soft preference.

Q37: What is a PodDisruptionBudget and when does it apply?

A PDB declares the minimum number of available replicas (minAvailable) or maximum unavailable (maxUnavailable) during a voluntary disruption. Voluntary disruptions: kubectl drain, node upgrades via managed node groups, Cluster Autoscaler scale-in. PDBs DO NOT protect against involuntary disruptions (node hardware failure, OOM kill). They ensure availability is maintained during planned operations like cluster upgrades and node rotation.

Q38: A PVC is stuck in Pending state. How do you debug it?

kubectl describe pvc <name> to see events. Common causes: (1) no matching StorageClass — kubectl get storageclass; (2) CSI driver pod crashed — kubectl get pods -n kube-system | grep csi; (3) WaitForFirstConsumer: PVC waits until a pod is scheduled — normal behavior; (4) storage quota exceeded — kubectl describe resourcequota; (5) wrong AZ or zone topology — check StorageClass volumeBindingMode.

Q39: Explain CSI — what problem does it solve?

Before CSI, storage drivers were compiled into the Kubernetes binary (in-tree plugins) — adding a new storage backend required modifying and releasing Kubernetes itself. CSI is a standardized RPC interface allowing any vendor to write a storage driver that works with any CSI-compatible orchestrator. CSI drivers are deployed as pods in the cluster (not in Kubernetes code), independently released, and more easily maintained.

Q40: How does StatefulSet stable storage work — specifically, what happens when pod-0 is rescheduled to a different node?

The StatefulSet controller creates a PVC named data-postgres-0 when pod-0 is first created. If pod-0 is evicted and rescheduled to a different node, the StatefulSet controller creates a new pod named postgres-0 and attaches the SAME existing PVC (data-postgres-0) to it. The CSI driver detaches the volume from the old node and attaches it to the new node. The pod retains all its data even across complete pod replacement.

21.4 Security and RBAC (Q41–Q60)

Q41: Explain RBAC roles, ClusterRoles, RoleBindings, and ClusterRoleBindings.

Role (namespace-scoped) + RoleBinding (namespace-scoped): grant permissions on namespaced resources within a specific namespace. ClusterRole (cluster-scoped) + ClusterRoleBinding (cluster-scoped): grant permissions cluster-wide or on cluster-scoped resources (nodes, PVs, namespaces). A ClusterRole can be bound with a RoleBinding to give cluster-level role permissions only within one namespace.

Q42: Why are Kubernetes Secrets not actually secret by default?

Secrets are stored in etcd as base64-encoded values — base64 is an encoding, not encryption, and is trivially reversible. Anyone with etcd read access or kubectl get secret permissions can decode the values immediately. For real secrecy: enable EncryptionConfiguration in kube-apiserver to AES-encrypt secrets in etcd at rest; use External Secrets Operator to pull from a dedicated secrets store (Vault, AWS Secrets Manager) instead of storing secrets in Kubernetes at all.

Q43: What are admission controllers and give examples of how they're used?

Admission controllers intercept API requests after AuthN/AuthZ and before persistence. Mutating webhooks: modify objects (inject sidecar containers, add default resource limits, inject environment variables). Validating webhooks: approve or reject objects (require team labels, block privileged containers, enforce naming conventions). Built-in: LimitRanger (enforce resource defaults), ResourceQuota (enforce namespace limits), PodSecurity (enforce PSS levels).

Q44: Explain the three Pod Security Standards levels.

Privileged: no restrictions — for system/infrastructure pods that genuinely need host-level access. Baseline: prevents known privilege escalation vectors (no privileged containers, no hostPID/hostNetwork, no host ports, limited capabilities). Restricted: heavily hardened best-practice profile — non-root user required, no privilege escalation, seccomp profile required, all capabilities dropped, read-only root filesystem recommended. Enforce Restricted for all production application namespaces.

Q45: How does IRSA (IAM Roles for Service Accounts) work on EKS?

EKS configures the cluster as an OIDC provider. A ServiceAccount is annotated with an IAM role ARN. When a pod uses that SA, the projected service account token is a short-lived OIDC JWT signed by the cluster's OIDC provider. The pod's application calls AWS STS AssumeRoleWithWebIdentity with this token; STS validates it against the OIDC provider and returns temporary AWS credentials for the specified IAM role. No long-lived secrets stored anywhere — pure federation.

Q46: What is OPA Gatekeeper and how does it differ from Kyverno?

Both are policy engines that use Kubernetes admission webhooks. OPA Gatekeeper uses Rego (a purpose-built policy language) for policy logic — powerful but requires learning Rego. Kyverno uses YAML-native policies with pattern matching — more accessible for Kubernetes operators but less expressive for complex logic. OPA integrates with non-Kubernetes systems too; Kyverno is Kubernetes-only but has richer K8s-specific features (mutating with JMESPath, generate rules, cleanup policies).

Q47: What is a ServiceAccount token and how does it work in Kubernetes 1.24+?

Since 1.21+, projected ServiceAccount tokens are used: short-lived (1h default), audience-bound JWTs projected into pods via a projected volume rather than the legacy long-lived secret-mounted tokens. Since 1.24+, Kubernetes no longer automatically creates long-lived SA token secrets. Applications should use the projected token at /var/run/secrets/kubernetes.io/serviceaccount/token and handle token rotation (Kubernetes refreshes it before expiry).

Q48: How would you detect and prevent privilege escalation in a cluster?

Enforce PSS Restricted level (blocks privileged containers, hostPID/hostNetwork, privilege escalation flag). Use OPA/Gatekeeper or Kyverno to enforce securityContext requirements. Audit cluster-admin bindings regularly: kubectl get clusterrolebindings -o json | jq. Run Falco for runtime threat detection (detects exec in containers, unexpected network connections, privilege escalation syscalls). Enable API server audit logging. Use read-only root filesystems where possible.

Q49: Explain how encryption at rest for Secrets works and how to enable it.

EncryptionConfiguration on the API server intercepts Secret (and optionally ConfigMap/etcd) writes and encrypts them before writing to etcd using AES-CBC, AES-GCM, or KMS-backed envelope encryption. The identity provider must be listed last to decrypt objects written before encryption was enabled. After enabling, existing secrets must be re-written to be encrypted: kubectl get secrets -A -o json | kubectl replace -f -. With KMS provider, the encryption key itself never leaves the KMS service.

Q50: What should you audit on an existing cluster to improve its security posture?

Check: (1) all ClusterRoleBindings to cluster-admin role; (2) pods running as root or with privileged: true; (3) PSS enforcement labels on namespaces; (4) Secrets encryption status; (5) public API server endpoint exposure; (6) default SA token automounting enabled for pods that don't need API access; (7) images without SHA pinning; (8) missing NetworkPolicies (default-allow); (9) no PodDisruptionBudgets for critical services; (10) missing resource requests/limits.

21.5 Autoscaling, Resource Management, etcd (Q51–Q70)

Q51: Explain how HPA makes a scaling decision.

HPA queries the metrics API (or custom metrics adapter) every 15 seconds, computes the desired replica count as: ceil(currentReplicas × currentMetricValue / targetMetricValue), then clamps between minReplicas and maxReplicas, and applies stabilization windows (scaleDown default 5 minutes to prevent thrashing). It then updates the Deployment/StatefulSet's replicas field — the deployment controller handles the actual pod creation.

Q52: What are the three QoS classes and how are eviction priorities determined?

Guaranteed: requests == limits for all containers; evicted last. Burstable: at least one container has requests set, but requests != limits; evicted second. BestEffort: no requests or limits; evicted first. On memory pressure, kubelet evicts pods in BestEffort → Burstable (over their requests) → Burstable (under their requests) → Guaranteed order. Never run critical workloads without resource requests (avoids BestEffort classification).

Q53: What's the difference between CPU throttling and OOMKill?

CPU throttling: when a container exceeds its CPU limit, Linux's CFS scheduler enforces the limit by reducing the container's CPU quota — the process slows down but keeps running. Can cause significant latency in latency-sensitive services. OOMKill: when a container exceeds its memory limit, the Linux OOM killer sends SIGKILL to a process in the container (exit code 137). The kubelet restarts the container per restartPolicy.

Q54: What is KEDA and what can it do that HPA cannot?

KEDA (Kubernetes Event-Driven Autoscaler) can scale to zero replicas (HPA minimum is 1), scale based on external event sources (Kafka lag, SQS depth, Redis queue length, Azure Service Bus, cron expressions — 50+ scalers), and supports non-HTTP-based workloads naturally. HPA only supports CPU/memory metrics and custom metrics from the Kubernetes metrics API. KEDA implements this by creating and managing an HPA object under the hood, extended with its own triggers.

Q55: How does the Cluster Autoscaler decide to scale down a node?

CA evaluates each node for scale-in: if it's been underutilized (below 50% CPU and memory by default) for 10 minutes, has no pods preventing eviction (pods with local storage, system pods, pods not managed by a controller, PDB violations), CA adds a scale-in annotation and calls kubectl drain on the node — migrating pods elsewhere — then terminates the instance via the cloud provider API (ASG desired capacity decrease).

Q56: What is the Raft consensus algorithm and why does etcd use it?

Raft is a distributed consensus algorithm that ensures all replicas in a cluster agree on the same state even when some nodes fail. One node is elected leader; all writes go through the leader, which replicates entries to followers and commits them once a quorum (majority = n/2+1) acknowledges. etcd uses Raft so that a single write is durably committed to a majority of nodes before acknowledging success — preventing data loss even if the leader crashes immediately after committing.

Q57: How would you recover a Kubernetes cluster if etcd is completely lost?

(1) Stop all kube-apiserver instances to prevent partial writes. (2) Restore etcd from a recent snapshot on each control-plane node (etcdctl snapshot restore). (3) Update etcd configuration to point to the restored data directory. (4) Restart etcd and verify cluster health. (5) Restart kube-apiserver. (6) Verify with kubectl get nodes and kubectl get pods -A. (7) Running workloads on worker nodes continue running via container runtime; they'll re-sync state with API server once it's back.

Q58: Why should etcd run on SSD/NVMe storage specifically?

etcd's write-ahead log requires sequential disk writes on the critical path of every API server write operation. Its fsync latency must be consistently below 10ms for healthy cluster operation. HDDs (5-10ms random seek) and even moderate SSDs can cause etcd leader elections during busy periods. NVMe (0.1-0.2ms) provides the consistent low latency etcd requires. The etcd docs specify: "Slow disk, or disk activity from other processes on the machine, may cause etcd to miss heartbeats, causing request timeouts and possible temporary leader loss."

Q59: A pod is OOMKilled repeatedly. What are all the actions you should take?

(1) Confirm via kubectl describe pod — Last State: Terminated, Reason: OOMKilled. (2) Check if it's a memory leak in the application: kubectl exec into a running pod and examine memory usage with top or /proc/self/status. (3) Temporarily increase memory limit as a stopgap. (4) Analyze heap dumps or memory profiles in the application. (5) Use VPA in recommendation mode to see what memory the pod historically needs. (6) Set memory request == memory limit for Guaranteed QoS to prevent eviction before OOM kill.

Q60: Explain the reconciliation loop in a Kubernetes controller.

A controller watches a resource type via an Informer (which maintains a local cache from a persistent Watch connection to the API server). When objects change, events are enqueued in a rate-limited work queue. The reconcile function dequeues work items, reads desired state (from cache) and actual state (from cache or provider API), computes the diff, applies changes (CRUD calls to API server or external systems), updates the status subresource, and requeues with backoff if incomplete. This loop runs forever, continuously driving actual toward desired state.

21.6 Scenarios and Production Questions (Q61–Q80)

Q61: Your Deployment is stuck at 2/3 ready — what steps do you take?

kubectl rollout status deployment/web (see what's blocking). kubectl describe deployment/web (events section). kubectl get pods -l app=web (find the not-ready pod). kubectl describe pod <stuck-pod> (check Events, Conditions, Container statuses). Check: is it Pending (scheduling failure), CrashLoopBackOff (app crash), or Running but not Ready (readiness probe failing)? Follow the appropriate troubleshooting path for each case.

Q62: A production deployment needs zero-downtime. How do you configure it?

In Deployment strategy: type: RollingUpdate, maxUnavailable: 0, maxSurge: 1. This ensures a new pod is created and becomes Ready before any old pod is terminated. Also set: readinessProbe correctly (gates traffic routing), preStop hook with a sleep (allows LB to drain connections), terminationGracePeriodSeconds ≥ connection timeout, PodDisruptionBudget with minAvailable: N-1 to protect during rolling updates and node drains.

Q63: How do you upgrade a StatefulSet without downtime?

For a replicated stateful app (3 replicas), ensure it can survive rolling restarts in the first place (read quorum requires majority up). Use updateStrategy: type: RollingUpdate, rollingUpdate: partition: 2 (only update pod-2 first to test). Verify pod-2 is healthy and the data state is correct. Then partition: 1 (update pod-1), verify, then partition: 0 (update pod-0). This allows canary-style controlled updates rather than updating all pods in succession without an option to stop.

Q64: An engineer just ran kubectl delete namespace production — what happens and how do you recover?

Namespace enters Terminating state and Kubernetes garbage-collects all objects inside it (pods, services, deployments, PVCs, etc.) in the background. PVCs are deleted, potentially triggering volume deletion depending on ReclaimPolicy. If you have Velero backups: velero restore create --from-backup <latest> --include-namespaces production. If not: redeploy from Git (GitOps), restore databases from separate backup (databases should always have independent backups beyond just PVCs). Lesson: enable RBAC preventing namespace deletion except by approved roles.

Q65: How would you implement canary deployments in Kubernetes?

Option A: Two Deployments with the same pod label, one with 9 replicas (stable) and one with 1 replica (canary) — the shared Service routes ~10% of traffic to canary based on pod count. Option B: Argo Rollouts Canary strategy (progressive traffic weight via traffic splitting). Option C: Ingress/Gateway API weight-based routing split (requires a controller that supports weights). Option D: Istio/service mesh VirtualService with explicit percentage weights. Argo Rollouts is the production-recommended approach with automated analysis and rollback.

Q66: Your cluster is running at 95% CPU. What are all the options?

Immediate: check if any single deployment has misconfigured resource limits consuming disproportionate resources (kubectl top pods --sort-by=cpu). Add nodes to the cluster (scale the ASG). Medium-term: review all pods' resource requests vs actual usage — right-size with VPA recommendations. Enable Cluster Autoscaler if not already active. Long-term: implement multi-tenancy ResourceQuotas to prevent single team monopolization. Profile applications for CPU-efficiency improvements.

Q67: How do you safely upgrade all worker nodes without downtime?

Rolling node replacement: for each node — (1) kubectl cordon node to stop new scheduling, (2) kubectl drain node with --ignore-daemonsets --delete-emptydir-data, wait for all pods to reschedule, (3) upgrade kubelet (apt/yum update kubelet kubectl; systemctl restart kubelet), (4) kubectl uncordon node. Managed node groups automate this. PodDisruptionBudgets protect services during drain. Never drain more nodes simultaneously than your PDB can tolerate.

Q68: Describe how you would implement a multi-tenant Kubernetes cluster.

Namespaces as tenant boundaries. RBAC: each tenant team has a Role with full access in their namespace only, no ClusterRole needed. NetworkPolicies: default-deny in each tenant namespace, intra-namespace traffic allowed. ResourceQuotas: cap each namespace's CPU/memory/pod count. LimitRanges: enforce sensible defaults per namespace. PodSecurity: Restricted PSS enforced per namespace. OPA/Kyverno: prevent cross-namespace secret/service access. Node isolation for stronger noisy-neighbor guarantees: dedicated node pools with taints/tolerations.

Q69: A microservice is experiencing high latency. How do you investigate in Kubernetes?

Check pods: kubectl top pods -l app=<service> (CPU/memory). kubectl describe pod (check events for OOMKills, restarts). Check resource requests vs actual usage (are pods CPU-throttled?). Check readiness endpoints — is the service partially degraded? Check Horizontal Pod Autoscaler — did it already scale? If Istio/service mesh: check distributed traces (Jaeger/Tempo) for the slow span. Check downstream dependencies — is the database slow? Is there network policy overhead? Check node pressure on hosting nodes.

Q70: How does GitOps with Argo CD improve production operations?

Git becomes the single source of truth for cluster state; all changes go through PR review with CI validation and plan preview. Argo CD continuously reconciles cluster state with Git — drift (manual kubectl changes) is detected and reverted. Rollbacks are git reverts. Full audit trail of every change (who, what, when, why). Environment promotion is controlled (Dev → Staging → Prod) via Git branch or path promotion. Disaster recovery: re-apply root App of Apps and the entire cluster rebuilds from Git.

21.7 Advanced Architecture (Q71–Q90)

Q71: How would you design a multi-region, highly available Kubernetes deployment?

Separate Kubernetes clusters per region (not multi-region single cluster — Kubernetes is not designed for >20ms API server latency). Global load balancer (Route53/Cloudflare) routes to regional clusters based on health/latency/geolocation. Each regional cluster is independently functional (no inter-cluster data-plane dependencies). Data replication at the database layer (e.g., Aurora Global Database, multi-region Kafka). Argo CD ApplicationSet deploys from Git to all regional clusters simultaneously. Global observability via Thanos/Cortex federation.

Q72: Explain the Operator pattern — design a database operator conceptually.

Define a DatabaseCluster CRD with spec fields: size, replicas, version, backup config. Write a controller that watches DatabaseCluster objects. On reconcile: (1) create a headless Service for stable DNS, (2) create a StatefulSet for the database pods, (3) create a separate Service for the read replica endpoint, (4) register a backup CronJob per the backup config, (5) monitor actual state (StatefulSet readyReplicas, recent backup completion), (6) update DatabaseCluster.status with connection endpoint, ready status, and last backup time. Handle upgrade by orchestrating StatefulSet rolling update with pre/post upgrade hooks.

Q73: What is the federation of Prometheus instances and why is it needed for multi-cluster?

Each cluster runs its own Prometheus (for low-latency in-cluster alerting and scraping). For cross-cluster visibility, Thanos or Cortex provide: (1) Sidecar pattern: Prometheus uploads time series to object storage (S3) every 2h, Thanos Querier deduplicates and federates queries across all clusters. (2) Cortex/Mimir remote-write: each Prometheus remote-writes to a central horizontally scalable TSDB. This avoids a single global Prometheus that would require cross-cluster scraping.

Q74: Explain eBPF and how Cilium uses it for Kubernetes networking.

eBPF (extended Berkeley Packet Filter) allows running sandboxed programs in the Linux kernel without modifying kernel source code or loading kernel modules. Cilium loads eBPF programs into the kernel's networking hooks (TC ingress/egress, XDP, kprobe) that handle every packet path: routing pod-to-pod traffic without going through the overlay stack, enforcing NetworkPolicies at L3/L4/L7 directly in the kernel, load-balancing Service traffic via eBPF sockmap (before packets even go through the full network stack), and replacing kube-proxy entirely — all at kernel speed without context switches to userspace.

Q75: What are the trade-offs of using a service mesh versus native Kubernetes networking?

Service mesh benefits: automatic mTLS between all services, L7 traffic management (retries/timeouts/circuit breaking), distributed tracing integration, golden-signal metrics per service. Service mesh costs: significant CPU/memory overhead (Envoy sidecar per pod), increased request latency (extra network hops through proxy), operational complexity (Istio is infamously complex), harder debugging (traffic goes through proxy, not directly). For most applications, well-configured NetworkPolicies + HTTP retries in the application code + good observability is sufficient without a mesh. Service mesh becomes worth the cost when you need mTLS enforcement at scale, sophisticated traffic management (canary, fault injection), or zero-trust networking between services.

Q76: What is Crossplane and how does it change Kubernetes-native infrastructure provisioning?

Crossplane extends Kubernetes with CRDs representing cloud infrastructure resources (S3Bucket, RDSInstance, ElasticacheCluster) and runs continuous reconciliation controllers that provision/manage those real cloud resources by calling provider APIs. Unlike Terraform's explicit plan/apply cycle, Crossplane reconciles continuously — if someone deletes an S3 bucket outside Kubernetes, Crossplane recreates it to match the declared CRD. This makes it GitOps-native and aligns cloud infrastructure management with how applications are managed.

Q77: How does the leader election mechanism work for kube-scheduler and kube-controller-manager?

Both use a Lease-based leader election: each instance races to acquire a Lease object (in kube-system namespace) by attempting to create it or update its holderIdentity field. The holder renews the lease every 2s (default renewDeadline); if any instance fails to renew within leaseDuration (15s default), other instances attempt to acquire. This ensures only one scheduler/controller instance is active at a time (active-passive HA), preventing duplicate scheduling decisions while allowing a standby to immediately take over if the leader fails.

Q78: What is the purpose and design of a Kubernetes Aggregation Layer?

The API aggregation layer allows extending kube-apiserver with additional API groups served by separate microservices (aggregated API servers). When a request for an extended API (e.g., metrics.k8s.io) arrives at the main API server, it is proxied to the registered extension API server. This is how metrics-server exposes its API, and how cloud providers add custom API groups. It allows extending the Kubernetes API surface without modifying the core API server.

Q79: How would you implement zero-downtime database migrations in Kubernetes?

Key principle: migrations must be backward-compatible with the old application version during the rolling update window. Three-phase deployment: (1) Deploy a migration version that adds columns/tables non-destructively (no renames, no drops) alongside old schema — old app still works. (2) Rolling update application pods to new version that uses new schema. (3) After 100% rollout, deploy cleanup migration removing deprecated columns. This allows rolling back to the old application version at any point without schema incompatibility. Use an init container or a Kubernetes Job for the migration step in a PreSync hook (Argo CD) before the application update.

Q80: Describe your approach to capacity planning for a Kubernetes cluster.

Collect baselines: VPA recommendations give actual resource utilization for all pods, showing gap between requests and actual. Model cluster capacity: total node resources minus system overhead, summed across node pools. Track bin-packing efficiency (allocatable vs requested vs actual). Set ResourceQuotas per namespace with buffer above current usage. Size node groups: over-provisioner DaemonSet keeps a warm spare pod pending that triggers CA scale-out before production workloads need the capacity. Model for failure scenarios: N-1 node capacity (can cluster survive one AZ loss while running full load?). Review quarterly.

21.9 Monitoring, Logging and Operations (Q91–Q110)

Q91: Explain the Kubernetes metrics pipeline — from container to HPA decision.

cAdvisor (embedded in kubelet) collects container CPU/memory metrics every 30s. Metrics Server (Deployment) scrapes all kubelets' /stats/summary endpoint and aggregates current resource usage into the metrics.k8s.io API. HPA queries metrics.k8s.io every 15s to get current pod CPU/memory utilization. For custom metrics: application exposes /metrics endpoint → Prometheus scrapes → Prometheus Adapter translates to custom.metrics.k8s.io → HPA queries. The entire pipeline has ~30-60s latency from metric change to HPA action.

Q92: What is the difference between kube-state-metrics and metrics-server?

metrics-server: real-time resource usage metrics (CPU/memory currently being used by pods/nodes), stored in memory, used by kubectl top and HPA. kube-state-metrics: Kubernetes API object state metrics (number of pods by phase, deployment available replicas, PVC binding status, node conditions) — not resource usage. kube-state-metrics exposes these to Prometheus; metrics-server exposes to the K8s metrics API. Both are needed for full observability.

Q93: How would you debug a pod that starts and immediately exits with exit code 1?

kubectl logs <pod> (shows stderr/stdout before crash). kubectl logs <pod> --previous (if pod already restarted). kubectl describe pod <pod> (check Exit Code, Message in Last State). If no logs (process exits before writing): temporarily add command: ["sleep", "3600"] to override the entrypoint, kubectl exec -it into the pod, and run the original command manually to see the error interactively. Check if required environment variables or mounted secrets/configmaps exist and have correct values.

Q94: What is Loki and how does it integrate with Kubernetes logging?

Loki is Grafana's log aggregation system (like Prometheus but for logs). Fluent Bit runs as a DaemonSet on every node, reading container logs from /var/log/containers/*.log, enriching them with Kubernetes metadata (pod name, namespace, labels, node) via the Kubernetes filter plugin, and shipping them to Loki. Grafana queries Loki using LogQL (similar to PromQL). Unlike Elasticsearch, Loki only indexes log metadata (labels), not full text — dramatically cheaper storage at the cost of slower full-text search.

Q96: Explain what happens to running pods when a node loses network connectivity.

Kubelet heartbeats to the API server every 10s. If not received for 40s (nodeStatusUpdateFrequency * nodeStatusReportFrequency), the Node controller marks the node NotReady. After node-monitor-grace-period (40s default), conditions are set. After pod-eviction-timeout (5 minutes default), all pods on the unreachable node are evicted (marked for deletion). DaemonSet pods are not evicted (new pods are already running on functioning nodes). Controllers (ReplicaSets, Deployments) create replacement pods elsewhere immediately upon seeing their pods Terminating.

Q97: How do you back up a Kubernetes cluster configuration (not workload data)?

All Kubernetes objects can be exported: kubectl get all --all-namespaces -o yaml > cluster-backup.yaml. But this is fragile (includes generated fields, status, resource version). Better: back up etcd directly (etcdctl snapshot save) which contains all objects. Best: use Velero which backs up objects cleanly (strips server-populated fields) to S3/GCS/Azure Blob and handles PVC data snapshots. Use GitOps — if all cluster state is already in Git, the cluster can be rebuilt from Git at any time without needing a separate backup of objects.

Q98: How would you investigate an API server that's responding slowly?

kubectl cluster-info dump --output-directory=/tmp/dump and analyze. Check kube-apiserver metrics: apiserver_request_duration_seconds (latency histogram), apiserver_request_total (error rates). Check etcd latency: etcd_disk_wal_fsync_duration_seconds should be <10ms. Check if any admission webhooks are slow (apiserver_admission_webhook_request_duration_seconds). Check CPU/memory of API server pods. Check number of active watches — too many list-watch operations with no pagination can overload the API server. Enable audit logging to identify which callers are making expensive requests.

Q99: What is the difference between using a Secret as an environment variable vs mounting it as a file?

Environment variable: value is loaded once at pod start; if the Secret is updated, the pod must be restarted to see the new value. Risk: process may dump env vars in logs/crash dumps, exposing secrets. File mount: Kubernetes periodically updates the file when the Secret changes (within kubelet sync period, ~1 minute), enabling dynamic rotation without pod restart (application must re-read the file). More secure: file permissions can restrict access; memory-mapped files don't appear in environment dumps.

Q100: Describe a production Kubernetes runbook for a service outage where pods are Pending.

1. Run kubectl get pods -l app=<service> -o wide to see which pods are Pending and on which nodes. 2. kubectl describe pod <pending-pod> to read scheduler Events. 3. Diagnose: Insufficient resources → check kubectl describe nodes for Available resources; Taint mismatch → check node taints; PVC unbound → check PVC status; Affinity unsatisfiable → check node labels; Quota exceeded → check ResourceQuota. 4. Short-term fix based on root cause: scale node group, remove taint, fix PVC, adjust quotas. 5. Escalate to on-call platform team if node group scaling is needed. 6. Post-incident: add alerts for pending pods > N minutes, review capacity planning.
