01 Section 1: Infrastructure as Code Fundamentals Fundamentals ▾

1.1 What is Infrastructure as Code?

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable definition files rather than manual configuration of hardware or interactive configuration tools. Instead of clicking through a cloud console to create a VPC, subnets, and an EC2 instance, you write a declarative or imperative configuration file that describes the desired infrastructure, and a tool reconciles the real world to match it.

Terraform, created by HashiCorp in 2014, became the dominant multi-cloud IaC tool by introducing a provider-based plugin architecture, a declarative configuration language (HCL), and a state-tracking engine that allows it to compute precise diffs between desired and actual infrastructure.

1.4 Immutable Infrastructure

Terraform encourages an immutable infrastructure philosophy: instead of patching a running server in place, you replace it entirely with a new resource built from updated configuration. Many resource attributes are marked ForceNew in provider schemas — changing them doesn't trigger an in-place update, it triggers destroy-then-create (or create-then-destroy, depending on create_before_destroy).

hcl
# Example: changing an EC2 instance's AMI forces replacement resource "aws_instance" "web" { ami = "ami-0c55b159cbfafe1f0" # changing this = destroy + recreate instance_type = "t3.micro" } # Terraform plan output for this change: # -/+ resource "aws_instance" "web" { # ~ ami = "ami-old" -> "ami-new" # forces replacement # }

1.5 Desired State, Idempotency, and Drift Detection

Desired state is what your .tf files declare should exist. Idempotency means running terraform apply repeatedly with no config changes produces no further changes — the engine only acts on the diff between desired and actual state. Drift is any divergence between Terraform's state file and the real infrastructure (e.g., someone manually changed a security group rule in the AWS console). Terraform detects drift during terraform plan by refreshing state against the real provider APIs before computing the diff.

2.1 Terraform CLI

The CLI is the single static binary (terraform) users interact with. It's the entry point for every command — init, plan, apply, destroy, state, etc. The CLI itself contains the Core Engine; it is not a thin wrapper around a server (unlike Terraform Cloud's remote execution mode, which is optional).

2.2 Core Engine

The Core Engine is responsible for the heavy lifting: parsing HCL into an internal representation, building the dependency graph, walking that graph to determine execution order, diffing state against configuration, and invoking provider plugins via RPC to perform actual CRUD operations. It does not know anything about AWS, Azure, or any specific API — all provider-specific logic lives in plugins.

Internal Workflow

hcl
1. Configuration Loading — parse all .tf/.tf.json files in working dir + modules 2. Graph Construction — build DAG of resources, data sources, modules, outputs 3. Graph Validation — detect cycles, unresolved references 4. State Loading — read current state via backend 5. Refresh (if enabled) — query providers for current real-world attributes 6. Diff Computation — desired (config) vs prior (state) per resource 7. Graph Walk — execute create/update/delete in dependency order, parallelizing independent branches 8. State Persistence — write updated state back through backend (with lock)

2.3 Providers and Provider Plugins

A Provider is a plugin that translates Terraform resource blocks into API calls against a specific platform (AWS, Azure, GCP, Kubernetes, GitHub, Datadog, etc.). Providers are separate binaries, downloaded during terraform init, and communicate with Terraform Core over a documented RPC protocol (currently protocol version 5/6, gRPC-based).

Why a Plugin Architecture?

  • Decouples the Core Engine release cycle from individual provider release cycles
  • Allows third parties to publish their own providers without modifying Terraform itself
  • Enables provider-specific authentication, retries, and rate-limit handling in isolation
  • Plugins crash-isolated from Core — a provider bug doesn't crash the whole CLI process

2.4 Resources and Data Sources (Overview)

A resource block tells Terraform to create and manage an infrastructure object (e.g., aws_instance). A data source block tells Terraform to read information about an existing object that it does not manage (e.g., look up the latest Amazon Linux AMI). Both are deep-dived in Section 6.

2.5 State Engine

The State Engine maintains terraform.tfstate — a JSON document mapping every resource block in your configuration to the real-world object it represents, along with all of that object's current attribute values (including sensitive ones). Without state, Terraform would have no way to know that aws_instance.web in your config corresponds to instance i-0abc123 in AWS, nor would it know what that instance's current attributes are without an expensive full-account scan. Deep-dived in Section 7.

2.6 Dependency Graph

Every plan and apply operation builds a Directed Acyclic Graph (DAG) of all resources, data sources, modules, providers, and outputs. Edges represent dependencies (explicit via depends_on, or implicit via interpolation references like aws_subnet.id used inside an aws_instance block). Terraform walks this graph, executing independent nodes in parallel (default concurrency: 10) and respecting dependency order for connected nodes. Deep-dived in Section 10.

2.7 Backend

The Backend determines where the state file is stored (local disk, S3, Azure Blob, GCS, Terraform Cloud, etc.) and whether/how state locking is implemented. Backends are configured in a terraform { backend "s3" {...} } block and are deep-dived in Section 8.

2.8 Registry

The Terraform Registry (registry.terraform.io) is the public catalog of providers and modules. terraform init resolves required_providers blocks against the registry (or a private registry / mirror) to download the correct provider plugin binaries. Module sources like terraform-aws-modules/vpc/aws are also resolved through the Registry.

2.9 Lock File (.terraform.lock.hcl)

The dependency lock file records the exact provider versions and cryptographic checksums selected during init, ensuring that every team member and every CI run uses identical provider binaries — analogous to a package-lock.json or Gemfile.lock. It should always be committed to version control.

hcl
# .terraform.lock.hcl (excerpt) provider "registry.terraform.io/hashicorp/aws" { version = "5.31.0" constraints = "~> 5.0" hashes = [ "h1:abc123...", "zh:def456...", ] }

2.10 Plugin Cache

By default, every Terraform working directory gets its own copy of provider binaries in .terraform/providers/, which is wasteful across many projects using the same providers. The plugin cache directory (TF_PLUGIN_CACHE_DIR) lets all projects on a machine share a single download of each provider version, dramatically speeding up init.

hcl
# ~/.terraformrc plugin_cache_dir = "$HOME/.terraform.d/plugin-cache"

3.1 terraform init — Deep Dive

bash
terraform init terraform init -upgrade # Upgrade providers to latest matching constraint terraform init -reconfigure # Reconfigure backend, ignore saved config terraform init -migrate-state # Migrate state to a newly configured backend terraform init -backend-config="bucket=my-tf-state" # Pass backend params at init time terraform init -input=false # Non-interactive (for CI)

Init performs three independent jobs: (1) backend initialization — connecting to and validating access to remote state storage, (2) provider installation — resolving version constraints across all required_providers blocks (root + all child modules) and downloading matching binaries, (3) module installation — fetching any module blocks' source code (Git, Registry, local path, S3, etc.) into .terraform/modules/.

3.2 terraform plan — Deep Dive

bash
terraform plan terraform plan -out=tfplan # Save plan to a binary file for later apply terraform plan -var="instance_count=3" # Override a variable terraform plan -var-file="prod.tfvars" # Load variables from file terraform plan -target=aws_instance.web # Plan only a specific resource (use sparingly) terraform plan -destroy # Preview what destroy would do terraform plan -refresh=false # Skip the refresh step (faster, less accurate)

Plan output uses a standard symbol notation: + create, - destroy, ~ update in-place, -/+ destroy and recreate, +/- create then destroy (when create_before_destroy is set).

3.3 terraform apply — Deep Dive

bash
terraform apply # Generates a fresh plan, prompts for approval terraform apply tfplan # Applies a previously saved plan file exactly terraform apply -auto-approve # Skip interactive approval (CI usage) terraform apply -parallelism=20 # Increase graph-walk concurrency (default 10)
⚠️

Production note: Always apply a saved plan file (terraform plan -out=tfplan then terraform apply tfplan) in CI pipelines. Re-running a fresh plan at apply time risks a different outcome than what was reviewed, since real-world state may have changed between the two steps.

3.4 The Graph Walk During Apply

hcl
Example dependency chain: aws_vpc.main → aws_subnet.public → aws_instance.web → aws_eip.web Execution: Step 1: create aws_vpc.main (no dependencies, starts immediately) Step 2: create aws_subnet.public (waits for vpc.id) Step 3: create aws_instance.web (waits for subnet.id) Step 4: create aws_eip.web (waits for instance.id) Independent resources (e.g., aws_s3_bucket.logs with no dependency on the above) execute IN PARALLEL with this chain, up to the parallelism limit (default 10).

4.7 count and for_each

hcl
# count — index-based, good for identical N copies resource "aws_instance" "web" { count = 3 ami = "ami-0c55b159cbfafe1f0" instance_type = "t3.micro" tags = { Name = "web-${count.index}" } } # Referenced as aws_instance.web[0], aws_instance.web[1], aws_instance.web[2] # for_each — key-based, good for distinct named instances (safer for changes) resource "aws_instance" "web" { for_each = toset(["app1", "app2", "app3"]) ami = "ami-0c55b159cbfafe1f0" instance_type = "t3.micro" tags = { Name = each.key } } # Referenced as aws_instance.web["app1"], etc. # for_each over a map for richer per-item config variable "instances" { type = map(object({ instance_type = string ami = string })) } resource "aws_instance" "this" { for_each = var.instances ami = each.value.ami instance_type = each.value.instance_type tags = { Name = each.key } }
💡

count vs for_each: count is index-based — removing the middle item from a list shifts all subsequent indices, forcing Terraform to destroy/recreate resources unnecessarily. for_each is key-based — removing one map key only affects that specific resource. Prefer for_each whenever items are not perfectly interchangeable.

5.5 Provider Lifecycle and Plugin Protocol

During init, Terraform resolves version constraints across the root module and every child module's required_providers, computes a single mutually compatible version, downloads the matching OS/architecture binary from the registry (or local mirror), verifies its checksum against .terraform.lock.hcl, and stores it under .terraform/providers/. At runtime, Core spawns the provider as a child process and communicates over a local gRPC socket using the Terraform Plugin Protocol (current versions support protocol 5 and 6, the newer Plugin Framework SDK).

6.1 Resources

hcl

Every resource has an implicit lifecycle: plan determines the action (create/update/destroy/replace) by diffing config against state; apply invokes the corresponding provider RPC (ApplyResourceChange); the provider calls the underlying cloud API; the returned object attributes are written back into state.

6.2 Data Sources

hcl
data "aws_ami" "amazon_linux" { most_recent = true owners = ["amazon"] filter { name = "name" values = ["amzn2-ami-hvm-*-x86_64-gp2"] } } resource "aws_instance" "web" { ami = data.aws_ami.amazon_linux.id # always resolves to latest at plan time instance_type = "t3.micro" }

Data sources are read-only — Terraform never creates, modifies, or destroys the object a data source refers to. They are re-evaluated on every plan, which means a data source like "most recent AMI" can silently change the planned configuration between runs even with no .tf file changes — a common source of unexpected diffs in production.

6.3 Resource Dependencies — Implicit vs Explicit

7.4 State Refresh

Refresh queries every managed resource's real-world current attributes via the provider's ReadResource RPC and updates the in-memory state representation used for diffing — without modifying actual infrastructure. Since Terraform 0.15+, refresh is automatically embedded into plan and apply (rather than being a required standalone step); it can still be invoked explicitly or skipped with flags.

bash
terraform plan -refresh-only -out=refresh.tfplan # See ONLY drift, no config changes terraform apply -refresh-only # Update state to match real world, # without changing infrastructure terraform plan -refresh=false # Skip refresh entirely (faster, stale)

7.5 Sensitive Values in State

State files store all resource attributes in plaintext JSON, including values marked sensitive = true in your configuration — the sensitive flag only redacts values from CLI/plan output, it does NOT encrypt them within the state file itself. This is why state must always be stored in an encrypted backend (S3 with SSE, GCS with CMEK, Azure Storage with encryption) and access-controlled via IAM, never committed to Git.

7.8 Partial Failures

If apply fails partway through (e.g., resource 3 of 5 fails due to a transient API error), Terraform's state reflects exactly which resources succeeded before the failure. The state is NOT rolled back — this is intentional, since the successfully created resources are real and Terraform must continue tracking them. Simply re-run terraform plan / apply; Terraform will compute a new diff that only addresses the remaining work.

9.1 Root Module vs Child Module

Every Terraform configuration has exactly one root module — the working directory where you run terraform apply. Any module block within it instantiates a child module, which is itself a complete, self-contained set of .tf files with its own variables, resources, and outputs.

9.4 Module Design Best Practices

  • Single responsibility: a module should provision one logical unit (a VPC, an EKS cluster, an RDS instance) — not "all of prod"
  • Expose only necessary outputs; avoid leaking internal implementation details consumers shouldn't depend on
  • Use variable validation blocks to fail fast on invalid input rather than failing deep into apply
  • Pin a default provider version range in the module's own required_providers, but never hardcode a provider block inside a reusable child module (let the root module own provider configuration)
  • Document every variable and output with description fields — this powers both the registry UI and terraform-docs generation
  • Version modules using semantic versioning and Git tags; treat breaking output/variable changes as major version bumps

9.5 Module Anti-Patterns

  • "God modules" that take 50+ input variables and try to provision an entire environment in one block — hard to reason about, hard to test, hard to reuse partially
  • Hardcoding provider blocks or backend configuration inside a child module (breaks composability)
  • Tight coupling between unrelated modules via remote_state data sources when a simple module output would do
  • Using count instead of for_each inside reusable modules where consumers expect to add/remove named items without unrelated resources being recreated

10 Section 10: Dependency Graph (DAG) Dependency Graph ▾

10.1 What is a DAG and Why Terraform Uses One

Terraform builds a Directed Acyclic Graph for every operation: nodes are resources, data sources, providers, modules, and outputs; edges represent "must happen before" relationships. A DAG (as opposed to a generic graph) guarantees no circular dependencies — every node can be ordered into a valid execution sequence. This structure lets Terraform safely parallelize independent work while strictly respecting dependent work's ordering.

10.2 Graph Construction

diagram
terraform graph > graph.dot # Render with Graphviz: dot -Tpng graph.dot -o graph.png # Conceptual graph for a simple 3-tier app: aws_vpc.main ├──> aws_subnet.public[*] │ └──> aws_route_table_association[*] ├──> aws_subnet.private[*] │ └──> aws_nat_gateway.main ├──> aws_security_group.alb │ └──> aws_lb.app ──> aws_lb_target_group.app └──> aws_security_group.app └──> aws_instance.app[*] ──> (registers into) aws_lb_target_group.app

10.3 Parallel Execution

By default, Terraform walks the graph with up to 10 concurrent operations (-parallelism=N to change). Any two nodes with no dependency path between them are eligible to run simultaneously. In a typical VPC + multiple EC2 instances configuration, all instances with identical dependencies (same subnet, same security group) are created in parallel once their shared prerequisites are satisfied.

hcl

10.6 Graph Optimization Techniques

  • Avoid unnecessary depends_on — every explicit dependency removes a potential parallelization opportunity
  • Split very large monolithic configurations into smaller root modules (per logical layer: network, data, compute) so each plan/apply only walks a smaller graph
  • Use -target sparingly for emergency surgical fixes, never as a routine workflow (it produces an incomplete plan and risks state drift from the full configuration)
  • Increase -parallelism for very large flat resource sets (e.g., hundreds of independent for_each S3 buckets) if API rate limits allow

11.3 Best Practice: Directory-per-Environment vs Workspaces

💡

For most production setups, a directory-per-environment structure (separate root modules for dev/staging/prod, each with its own backend key and .tfvars, all calling the same shared child modules) is preferred over CLI workspaces. It provides true isolation of backend configuration and blast radius, at the cost of minor duplication. Workspaces remain useful for ephemeral, identical environments — e.g., one workspace per feature-branch preview environment, or per customer in a single-tenant-per-environment SaaS model.

12.4 Why Provisioners Exist — and Why HashiCorp Discourages Them

Provisioners were Terraform's earliest mechanism for configuration management — running arbitrary commands at create/destroy time when no purpose-built provider resource existed for a task. HashiCorp's own documentation states provisioners should be a "last resort," for several concrete reasons:

  • They break the declarative model — Terraform cannot diff or plan what a shell command will do; it can only re-run it
  • They are not idempotent by default — re-running apply may execute the script again with unpredictable results
  • SSH/WinRM connectivity requirements introduce a hard dependency on network reachability at apply time, which is often unavailable in private subnets without a bastion or VPN
  • Failures are difficult to recover from — a failed provisioner taints the resource by default, forcing a destroy/recreate cycle
  • They mix configuration management concerns into infrastructure provisioning, violating separation of concerns

13.4 IAM Least Privilege for Terraform Execution Roles

  • Never run Terraform with a personal admin IAM user — use a dedicated execution role scoped to exactly the resource types/actions the configuration manages
  • Use separate execution roles per environment (dev-deploy-role, prod-deploy-role) so a compromised CI token for dev cannot touch production
  • Grant write access to the state S3 bucket/DynamoDB lock table as a narrowly scoped policy, separate from the broader infrastructure permissions
  • Use IAM policy conditions (e.g., restrict by source IP / VPC endpoint, MFA-required for destructive actions) where feasible
  • Periodically audit with tools like AWS IAM Access Analyzer to detect overly broad policies attached to Terraform roles

13.5 State Encryption Checklist

  • S3 bucket: SSE-KMS enabled, versioning enabled, public access fully blocked
  • DynamoDB lock table: encryption at rest enabled (default with AWS-owned key, or use a CMK)
  • Bucket policy: deny non-TLS requests (aws:SecureTransport condition)
  • Access logging enabled on the state bucket for audit trail
  • Terraform Cloud: state encrypted at rest by HashiCorp automatically; still scope workspace access via teams

19.4 Platform Engineering

19.5 Kubernetes Provisioning with Terraform

20 Section 20: Terraform vs Alternatives Comparison ▾

20.1 Terraform vs OpenTofu

OpenTofu is a Linux Foundation-governed fork of Terraform created after HashiCorp's August 2023 license change from MPL 2.0 to the Business Source License. OpenTofu remains fully open-source (MPL 2.0), maintains compatibility with the existing HCL syntax and provider ecosystem, and has diverged slightly with community-driven features (e.g., native state encryption added before Terraform). For most teams, the choice comes down to licensing philosophy and vendor relationship preference rather than a meaningful technical capability gap, since both consume the same provider plugins.

20.3 Terraform vs CloudFormation

CloudFormation is AWS-native, free, and requires no separate state file (AWS manages it internally as a CloudFormation Stack) — but it is AWS-only, with comparatively clunkier syntax (YAML/JSON without a real expression language until relatively recent additions like CloudFormation modules and Fn:: intrinsics) and historically slower support for brand-new AWS features versus the Terraform AWS provider's release cadence, though this gap has narrowed.

20.4 Terraform vs AWS CDK

AWS CDK lets you write infrastructure in a general-purpose language which it then synthesizes into a CloudFormation template — combining a familiar programming language with AWS's native deployment engine. It inherits CloudFormation's AWS-only scope and its state/drift model, but gives you full language constructs (loops, classes, package management) that HCL lacks. Choose CDK if you're fully AWS-committed and want a real programming language; choose Terraform/OpenTofu for multi-cloud portability and the broader provider ecosystem.

20.5 Terraform vs Ansible

Ansible is fundamentally a configuration management and orchestration tool (managing the state of software on existing servers) rather than a cloud resource provisioning tool. It has no built-in state file — every run re-queries the live system — which is appropriate for config management (where "current OS package version" is cheap to check) but unsuitable for tracking complex cloud resource graphs at scale. Many teams use both together: Terraform provisions the infrastructure (VMs, networks, clusters), Ansible configures software on top of it.

20.6 Terraform vs Crossplane

Crossplane takes a fundamentally different architectural approach: instead of a CLI-driven plan/apply workflow, it extends the Kubernetes API itself with Custom Resource Definitions representing cloud infrastructure, and runs a continuous in-cluster reconciliation controller (true GitOps-native, no separate "apply" step — closer to how Argo CD/Flux reconcile application state). This makes Crossplane attractive for platform teams who want infrastructure provisioning to live entirely within the Kubernetes control plane and be managed the same way as application workloads, at the cost of a steeper architectural shift and a less mature ecosystem than Terraform's provider catalog.

21.1 Fundamentals (Q1–Q15)

Q1: What is Infrastructure as Code and what problem does it solve?
IaC manages infrastructure through machine-readable definition files rather than manual console operations. It solves the lack of a source of truth, inability to preview changes before applying them, configuration drift with no detection mechanism, and slow/error-prone environment rebuilds.
Q2: Explain declarative vs imperative infrastructure management.
Declarative tools (Terraform, CloudFormation) describe only the desired end-state; the engine computes the steps. Imperative tools (shell scripts, most Ansible playbooks) specify the exact sequence of operations to perform. Declarative tools have built-in idempotency and diffing; imperative tools require that to be manually engineered.
Q3: What is idempotency and why does it matter for Terraform?
Idempotency means repeated execution with no configuration change produces no further effect. Terraform achieves this by always diffing desired config against current state before acting — re-running apply with nothing changed results in "No changes," not redundant API calls.
Q4: What is drift and how does Terraform detect it?
Drift is any divergence between Terraform's state and real infrastructure (e.g., a manual console change). Terraform detects it during the refresh phase of plan/apply, querying live provider APIs and comparing against the state file before computing the diff.
Q5: What is immutable infrastructure and how does Terraform encourage it?
Rather than patching resources in place, immutable infrastructure replaces them entirely on change. Terraform encodes this via provider schema attributes marked ForceNew — changing them triggers destroy-then-create (or create-then-destroy with create_before_destroy) instead of an in-place update.
Q6: Describe the full Terraform workflow from configuration to apply.
Write .tf configuration → terraform init (providers/backend/modules) → fmt/validate → plan (refresh + diff) → review → apply (graph walk, provider RPC calls, state updates) → ongoing iterative plan/apply → eventually destroy when decommissioning.
Q7: How does Terraform differ from CloudFormation architecturally?
Terraform is multi-cloud via a provider plugin architecture and maintains an explicit, user-managed state file. CloudFormation is AWS-only and manages state internally as a Stack with no separate file for users to handle, but offers no multi-cloud portability.
Q8: What is OpenTofu and why does it exist?
OpenTofu is a Linux Foundation-governed, fully open-source (MPL 2.0) fork of Terraform created after HashiCorp changed Terraform's license to the Business Source License in 2023. It maintains compatibility with existing HCL configuration and the Terraform provider ecosystem.
Q9: How does Pulumi's approach differ fundamentally from Terraform's?
Pulumi uses general-purpose programming languages (TypeScript, Python, Go, etc.) instead of a DSL, giving access to native language constructs (loops, classes, packages) but trading away HCL's purpose-built simplicity. State management and the plan/apply concept are conceptually similar between the two tools.
Q10: Why might a team choose Ansible alongside Terraform rather than instead of it?
Terraform provisions cloud infrastructure (VMs, networks, managed services) with full state tracking; Ansible manages configuration of software on already-provisioned servers, querying live state on every run rather than maintaining a state file. They address different layers and are commonly used together.
Q11: What does "desired state" mean in Terraform's model?
The infrastructure configuration as expressed in .tf files — what the engineer wants to exist. Terraform's job on every plan/apply is reconciling real-world and tracked state toward this desired state.
Q12: What is Crossplane and how does its model differ from Terraform's?
Crossplane extends the Kubernetes API with CRDs representing cloud infrastructure and runs continuous in-cluster reconciliation controllers — no separate CLI-driven apply step, much closer to how Argo CD/Flux reconcile applications. Terraform uses an explicit CLI-driven plan/apply cycle outside the cluster.
Q13: What does AWS CDK actually produce under the hood?
CDK code (written in TypeScript/Python/etc.) is synthesized into a CloudFormation template, which AWS CloudFormation then deploys — CDK is a higher-level authoring layer on top of CloudFormation's existing deployment engine, not a separate execution engine.
Q14: What is a common reason teams adopt IaC beyond "automation"?
Auditability and review: every infrastructure change becomes a reviewable, version-controlled diff (a PR), creating an audit trail of who changed what, when, and why — something ClickOps and ad hoc scripting cannot provide.
Q15: What's the practical difference between Terraform's plan output symbols + / - / ~ / -/+?
+ create, - destroy, ~ update in-place, -/+ destroy and recreate (replacement required by a ForceNew attribute change).

21.2 Architecture & HCL (Q16–Q32)

Q16: List Terraform's core architectural components.
CLI, Core Engine (parsing, graph construction, diffing, graph walking), Provider Plugins (RPC-based, platform-specific CRUD), State Engine, Backend (state storage + locking), Registry (provider/module distribution), Lock File (.terraform.lock.hcl), and Plugin Cache.
Q17: Why does Terraform use a separate process (RPC) model for providers instead of linking them directly into the core binary?
It decouples release cycles (providers can ship independently of Core), allows third parties to publish providers without modifying Terraform itself, isolates provider crashes from the main process, and enables a stable versioned protocol contract between Core and any provider.
Q18: What three jobs does terraform init perform?
Backend initialization (connect/validate remote state storage), provider installation (resolve version constraints, download matching binaries, verify checksums against the lock file), and module installation (fetch any module block sources into .terraform/modules/).
Q19: What is the purpose of .terraform.lock.hcl and should it be committed to Git?
It records exact resolved provider versions and cryptographic checksums so every team member and CI run uses identical provider binaries. Yes — always commit it, analogous to package-lock.json.
Q20: Explain count vs for_each and when to prefer one over the other.
count is index-based — removing a middle item from a list shifts subsequent indices, causing unnecessary destroy/recreate of unrelated resources. for_each is key-based, so removing one item only affects that specific resource. Prefer for_each whenever items are individually distinguishable and not perfectly interchangeable.
Q21: What's the difference between implicit and explicit dependencies?
Implicit dependencies are automatically inferred by Terraform from attribute references in expressions (e.g., subnet_id = aws_subnet.public.id). Explicit dependencies are manually declared with depends_on, used only when no attribute reference exists to express a required ordering.
Q22: What does the lifecycle meta-argument's create_before_destroy do, and when would you use it?
It builds the replacement resource before destroying the old one (instead of the default destroy-then-create), avoiding downtime for resources like launch templates or security groups referenced by other resources that must always have at least one valid target.
Q23: What is the difference between a resource and a data source?
A resource is created, updated, and destroyed by Terraform — it owns the object's lifecycle. A data source is read-only — it looks up information about an object Terraform does not manage, and is re-evaluated on every plan.
Q24: Why can data sources cause unexpected plan diffs even with no .tf file changes?
Data sources are re-evaluated on every plan run. A data source like "most recent AMI" can resolve to a different value between two runs if a new AMI was published in the meantime, producing a plan diff even though no configuration changed.
Q25: How do dynamic blocks work and when are they needed?
A dynamic block generates nested configuration blocks (like multiple ingress rules) from a list/map at plan time, useful when the number of nested blocks isn't fixed and must be driven by a variable.
Q26: What does the ignore_changes lifecycle argument do?
It tells Terraform to exclude specific attributes from diff calculation, so changes made to those attributes outside Terraform (e.g., by autoscaling or manual rotation) don't appear as drift to be reverted on the next apply.
Q27: What happens internally when you run terraform plan?
Load current state → refresh (query providers for real attributes) → build the dependency graph → diff configuration against refreshed state per resource → output a human-readable summary of planned create/update/delete/replace actions.
Q28: Why is it best practice to apply a saved plan file (terraform apply tfplan) rather than letting apply generate its own plan?
Real-world infrastructure could change between a review step and the actual apply; applying a saved plan guarantees execution matches exactly what was reviewed and approved, rather than risking a fresh, potentially different plan at apply time.
Q29: How does Terraform decide execution order and parallelism during apply?
It walks the dependency graph (DAG); nodes with no dependency path between them execute in parallel (default concurrency 10, tunable via -parallelism), while dependent nodes wait for their prerequisites to complete first.
Q30: What causes a circular dependency error, and how do you resolve one (e.g., between two security groups referencing each other)?
It occurs when two resources each reference the other directly within their own block, creating a cycle the graph can't order. Resolve by creating both base resources first without the cross-references, then adding separate aws_security_group_rule resources that reference each group's already-existing ID.
Q31: What's the purpose of provider aliases?
They allow multiple configurations of the same provider (e.g., two AWS regions) within one Terraform configuration, referenced per-resource via the provider = aws.alias_name meta-argument.
Q32: Why is a pessimistic version constraint (~> 5.0) generally preferred over an exact pin for provider versions?
It allows automatic patch/minor upgrades (bug fixes, new resource support) within a known-compatible major version range, while the committed lock file still guarantees exact reproducibility across team members and CI runs until someone deliberately runs init -upgrade.

21.3 State Management (Q33–Q50)

Q33: What is stored in terraform.tfstate and why does Terraform need it?
A JSON document mapping every managed resource block to the real-world object it represents, including all current attribute values. Terraform needs it to know which real object corresponds to which configuration block, and to compute diffs without an expensive full-account scan on every run.
Q34: Why is local state unsuitable for team environments?
It lives on one engineer's disk with no locking mechanism beyond OS-level file locks on that same machine — concurrent applies by different team members would race and corrupt each other's view of state.
Q35: Explain how S3 + DynamoDB backend locking works.
Before any state write, Terraform attempts a conditional PutItem to a DynamoDB table keyed by the state file path (LockID). If the conditional write succeeds, the lock is held; if it fails (a record already exists), the apply errors out immediately rather than racing. The lock record is deleted on completion.
Q36: What changed about S3 backend locking in newer Terraform versions?
Terraform 1.10+ supports native S3 locking via conditional writes (the "use_lockfile" feature), removing the hard requirement for a separate DynamoDB table — though DynamoDB locking remains widely used and fully supported.
Q37: Does marking a variable sensitive = true encrypt it within the state file?
No. sensitive only redacts the value from CLI/plan/apply console output. The actual value is still stored in plaintext within the state file's JSON — which is why the backend itself (S3 SSE, GCS CMEK, etc.) must provide encryption at rest.
Q38: What is the purpose of the "serial" and "lineage" fields in state?
serial is a monotonically incrementing counter bumped on every state write, used for conflict detection. lineage is a unique ID generated when state is first created, protecting against accidentally applying a completely unrelated state file to your configuration.
Q39: What is the modern replacement for the standalone terraform refresh command?
Refresh is now embedded automatically into plan and apply since Terraform 0.15+. The modern explicit equivalents are terraform plan -refresh-only (preview drift only) and terraform apply -refresh-only (accept drift into state without changing infrastructure).
Q40: How would you recover from an accidentally corrupted or overwritten state file?
Restore from the backend's version history (e.g., a previous S3 object version, assuming bucket versioning was enabled) rather than attempting to hand-repair the JSON, which risks further corruption.
Q41: What happens to state if terraform apply fails partway through?
State reflects exactly which resources succeeded before the failure point — it is not rolled back, since those resources are genuinely real. Re-running plan/apply computes a new diff addressing only the remaining work.
Q42: Describe the steps to migrate state from local to an S3 backend.
Add/modify the backend "s3" {...} block in configuration, then run terraform init -migrate-state; Terraform detects the backend change and prompts to copy the existing local state into the newly configured remote location.
Q43: What command would you use to safely rename a resource in state after refactoring your configuration (e.g., moving it into a module)?
terraform state mv SOURCE DEST — it updates the resource's address within state without touching real infrastructure, avoiding an unnecessary destroy/recreate that would otherwise occur if the address simply changed in configuration.
Q44: What does terraform state rm do, and when would you use it?
It removes a resource from Terraform's state without destroying the real infrastructure object — used when you want Terraform to stop managing something (e.g., handing it off to another tool or team) while leaving it running.
Q45: Why should you never manually hand-edit the JSON state file?
Manual edits risk producing structurally invalid JSON or internally inconsistent resource/dependency records that the engine can't safely interpret, potentially corrupting state beyond easy recovery. Always use terraform state subcommands instead.
Q46: What's the difference between a "Saved plan is stale" error and a state lock error?
A stale plan error means real-world/state changed between when a plan file was generated and when it was applied — the saved diff no longer matches reality. A lock error means another operation currently holds the write lock on the state — a concurrency, not staleness, issue.
Q47: How does Terraform Cloud's state management differ from a self-managed S3 backend?
TFC manages encryption, locking, and full version history with a web UI for state diffing automatically — no DynamoDB table or bucket policies to configure — at the cost of depending on HashiCorp's managed service (or a self-hosted Terraform Enterprise instance) rather than your own cloud account's primitives.
Q48: Why might you run terraform force-unlock, and what risk does it carry?
It manually releases a stuck lock left behind by a crashed or interrupted run. The risk: if another apply is genuinely still in progress, force-unlocking and starting a second concurrent apply can corrupt state — always verify no real run is active first.
Q49: What's the safest way to inspect remote state without risking a write?
terraform state pull (downloads a read-only copy to stdout/a file) or terraform state list / terraform state show ADDRESS, all of which never write back to the backend.
Q50: Why does state need to track resource dependencies (the "dependencies" field per instance), not just config?
It allows Terraform to compute a correct destroy-order graph directly from state alone (e.g., during terraform destroy) without needing to re-parse the full original configuration, and helps detect orphaned dependency references during refactors.

21.4 Modules, Backends & Workspaces (Q51–Q65)

Q51: What is the difference between a root module and a child module?
The root module is the working directory where you run terraform commands directly. A child module is any module instantiated via a module block within it (or transitively within another module) — a reusable, self-contained set of .tf files with its own variables and outputs.
Q52: List at least four valid module source types.
Terraform Registry (terraform-aws-modules/vpc/aws), local path (../modules/vpc), Git (github.com/org/repo//path?ref=v1.0), and S3 (s3::https://...). Private registries (TFC/TFE) are also supported.
Q53: Why should reusable child modules generally avoid declaring their own provider blocks?
Provider configuration (credentials, region, aliases) is a root-module-level concern; hardcoding it inside a child module breaks composability and prevents the same module from being reused across different provider configurations/accounts/regions.
Q54: What is a "god module" anti-pattern?
A single module that takes dozens of input variables and tries to provision an entire environment (VPC + compute + database + DNS) in one undifferentiated block — hard to reason about, test in isolation, or reuse partially.
Q55: How does an enterprise typically distribute internal Terraform modules?
Via a private module registry (Terraform Cloud/Enterprise private registry, or an Artifactory/JFrog-backed registry) — platform teams publish versioned modules via CI on Git tag push, and application teams consume them with pinned version constraints.
Q56: What does a Terraform backend actually configure?
Where the state file is stored (local disk, S3, Azure Blob, GCS, Terraform Cloud, etc.) and, where supported, how state locking is implemented for that storage location.
Q57: Compare the S3 backend and the Terraform Cloud backend along security and operational dimensions.
S3 backend: you own and configure encryption (SSE-KMS), versioning, IAM policies, and a separate DynamoDB lock table yourself — full control, more setup. Terraform Cloud backend: HashiCorp manages encryption and locking automatically and adds a web UI, run history, and policy-as-code integration out of the box, but introduces a dependency on their managed service.
Q58: What exactly do CLI workspaces isolate, and what do they NOT isolate?
They isolate the state file only — each workspace gets its own state under the same backend. They do NOT isolate backend configuration, provider credentials, or IAM permissions — all environments using workspaces share the same backend setup and (typically) the same credentials.
Q59: Why is directory-per-environment generally preferred over CLI workspaces for production?
It provides true isolation of backend configuration, variable files, and IAM execution roles per environment, eliminating the risk of a conditional-logic mistake in terraform.workspace causing production-sized resources to apply against the wrong environment.
Q60: When are CLI workspaces actually a good fit?
For genuinely identical, ephemeral environments sharing the same configuration and risk profile — e.g., one workspace per feature-branch preview environment, or per-tenant in a single-tenant-per-workspace SaaS pattern.
Q61: What is the difference between provisioners' local-exec and remote-exec?
local-exec runs a command on the machine running Terraform itself; remote-exec runs commands on the newly created remote resource over an SSH/WinRM connection defined in a connection block.
Q62: Why does HashiCorp recommend provisioners only as a last resort?
They break the declarative model (Terraform can't diff what a shell command will do), aren't idempotent by default, introduce a hard network-reachability dependency at apply time, and a failed provisioner taints the resource, forcing an unwanted destroy/recreate cycle.
Q63: What's a better alternative to remote-exec for installing software on a new EC2 instance?
A pre-baked AMI built with Packer, or a cloud-init script passed via the user_data argument — both avoid the SSH connectivity dependency and are idempotent at the image/boot-script level.
Q64: What replaced the legacy terraform taint command, and how does it work?
terraform apply -replace="ADDRESS" — it marks a specific resource for forced destroy-and-recreate during the next apply, achieving the same outcome as the deprecated taint/untaint commands but as a single explicit apply-time flag rather than a persistent state marker.
Q65: What's the difference between the legacy terraform import command and the modern import block?
The legacy CLI command only updates state — it generates no configuration, leaving you to hand-write a matching resource block. The modern import block (1.5+) is declarative and, combined with -generate-config-out, can scaffold a starting .tf resource block matching the imported object's actual attributes.

21.5 Security & CI/CD (Q66–Q80)

Q66: Why is hardcoding a database password directly in a .tf file dangerous, even if the repo is private?
It's stored in plaintext in Git history forever (even if later removed), appears unredacted in terraform plan/apply console output, and is duplicated into the state file — multiplying the exposure surface beyond just "private repo access."
Q67: How does marking a Terraform variable sensitive = true help, and what doesn't it do?
It redacts the value from CLI plan/apply output and UI displays. It does NOT encrypt the value within the state file, and does not prevent the value from being visible to anyone with state file read access.
Q68: How would you integrate HashiCorp Vault to avoid storing static database credentials in Terraform variables at all?
Use Vault's dynamic secrets engine for the database — Terraform's vault provider requests short-TTL, automatically-expiring credentials at apply time via a data source, so no long-lived static secret ever needs to be stored anywhere, including in Terraform variables.
Q69: What is SOPS and how is it used with Terraform?
SOPS (Secrets OPerationS) encrypts structured files (YAML/JSON/.tfvars) at the field level using a key management backend (AWS KMS, GCP KMS, PGP). Encrypted .tfvars files can be safely committed to Git and decrypted at apply time via the sops Terraform provider or a wrapper script in CI.
Q70: What does IAM least privilege mean in the context of a Terraform CI execution role?
The role used by CI to run Terraform should be scoped to exactly the resource types/actions the specific configuration manages — never a broad admin policy — and ideally separated per environment so a compromised dev pipeline credential cannot affect production.
Q71: What is Sentinel and how does it differ from a simple code review?
Sentinel is HashiCorp's policy-as-code framework (Terraform Cloud/Enterprise) that programmatically evaluates a generated plan against organizational rules (mandatory tags, allowed instance types, cost thresholds) and can hard-block an apply automatically — enforcing policy consistently rather than relying on a human reviewer catching every violation.
Q72: How would you enforce "no public S3 buckets" using Open Policy Agent?
Export the plan as JSON (terraform show -json tfplan), then run conftest test plan.json against a Rego policy file that inspects resource_changes for aws_s3_bucket_public_access_block resources and denies the plan if block_public_acls (or similar) is false.
Q73: Describe a secure CI/CD pattern for Terraform using GitHub Actions and AWS.
Use OIDC federation (id-token: write permission + aws-actions/configure-aws-credentials with role-to-assume) so no static AWS keys are stored as GitHub secrets at all; plan on PR with output posted as a comment; apply only on merge to the protected branch, ideally behind a manual approval gate for production.
Q74: What is Atlantis and what workflow does it enable?
Atlantis is a self-hosted tool that listens for PR webhook events, automatically runs terraform plan and posts the output as a PR comment, and executes apply only after an authorized reviewer comments "atlantis apply" — giving GitOps-style review and state locking per project directly through the normal PR review process.
Q75: Why should CI always apply a previously saved plan file rather than re-planning at apply time?
Real-world infrastructure or state can change in the window between the reviewed plan and the apply step; applying the saved plan file guarantees the executed changes exactly match what was reviewed and approved, eliminating "plan/apply drift" risk.
Q76: What encryption settings should a production Terraform state S3 bucket have at minimum?
SSE-KMS server-side encryption enabled, versioning enabled, all four public access block settings enabled (block_public_acls, block_public_policy, ignore_public_acls, restrict_public_buckets), and a bucket policy denying non-TLS (aws:SecureTransport) requests.
Q77: How should secret rotation interact with Terraform-managed resources?
Prefer cloud-native rotation (e.g., RDS managed master password rotation, Secrets Manager rotation Lambdas) over rotating through Terraform applies; if rotation must flow through Terraform-managed attributes, add ignore_changes for the rotated field so external rotation isn't reverted on the next apply.
Q78: What's the difference between Terraform Cloud and Spacelift at a conceptual level?
Both are managed Terraform/OpenTofu automation platforms with policy-as-code, run history, and state management — Terraform Cloud is HashiCorp's own offering (native Sentinel integration), while Spacelift is a third-party platform with deeper native OPA integration and a different stack-dependency/pricing model; many teams choose between them based on policy-engine preference and existing tooling investment.
Q79: What static analysis tools would you add to a Terraform CI pipeline, and what do they catch?
tflint (style/best-practice linting), tfsec or checkov (security misconfiguration scanning — public buckets, missing encryption, overly permissive security groups), each running before plan/apply as a fast, cheap pre-check.
Q80: Why is locking state per-environment important in CI/CD?
It ensures that two CI pipeline runs targeting the same environment can never race — the second run's apply fails fast with a clear lock error rather than silently corrupting state or producing an inconsistent infrastructure outcome.

21.6 AWS Production & Scenario-Based Questions (Q81–Q100)

Q81: Why use one_nat_gateway_per_az = true in a production VPC module instead of a single shared NAT gateway?
A single NAT gateway is a single point of failure and an AZ-crossing data transfer cost driver for cross-AZ traffic; one NAT gateway per AZ keeps egress traffic within the same AZ for each private subnet and removes the single point of failure.
Q82: Why apply create_before_destroy on a launch template or security group referenced by an Auto Scaling Group?
Because other resources (the ASG, the ALB target group) reference the launch template/security group's ID; destroying it before the replacement exists would leave dangling references and likely fail the apply or cause an outage. Building the replacement first avoids this entirely.
Q83: How would you provision an RDS instance's master password securely with Terraform?
Use manage_master_user_password = true so AWS creates and manages the credential in Secrets Manager automatically, combined with lifecycle { ignore_changes = [password] } so Terraform never attempts to manage or revert the AWS-rotated value directly.
Q84: Why would you set cluster_endpoint_public_access = false on an EKS cluster in production?
To prevent the Kubernetes API server endpoint from being reachable over the public internet at all, forcing access through a private network path (VPN, bastion, Direct Connect/VPC peering) — significantly reducing the cluster's external attack surface.
Q85: What's the purpose of an Origin Access Control (OAC) on a CloudFront distribution serving from a private S3 bucket?
It allows CloudFront to authenticate to S3 using SigV4 signing without the bucket needing any public access at all — the bucket policy grants access only to the specific CloudFront distribution via OAC, keeping the origin bucket fully private.
Q86: Why scope a security group's ingress rule to source_security_group_id (another SG) rather than a CIDR block, when restricting app-tier access to only the load balancer?
Security-group-to-security-group references automatically track membership changes (new ALB ENIs, IP changes) without needing manual CIDR updates, and they express intent more precisely ("only things in the ALB security group") than a CIDR range that might be broader or narrower than intended.
Q87: A terraform apply fails midway through provisioning a 5-resource chain — what's your immediate next step?
Run terraform plan to see exactly what Terraform now believes the remaining diff is (state already reflects whatever succeeded); investigate the specific error from the failed resource (often a transient API throttle or a quota limit) before simply re-running apply.
Q88: terraform destroy fails on a VPC with "DependencyViolation" — what's the likely cause and fix?
Likely cause: a resource was created inside the VPC/subnet outside of Terraform (e.g., manually via console, or by another tool) and still has an attached ENI, blocking the VPC's deletion. Fix: identify and manually clean up the out-of-band resource (e.g., via aws ec2 describe-network-interfaces filtered by VPC ID), then retry destroy.
Q89: How would you safely rename a resource from aws_instance.web to module.app.aws_instance.web after refactoring it into a module, without Terraform destroying and recreating it?
terraform state mv aws_instance.web module.app.aws_instance.web — this updates the resource's tracked address in state to match the new configuration location without touching the real infrastructure object at all.
Q90: You see "Error acquiring the state lock" in CI but no other pipeline appears to be running — how do you proceed?
First confirm via the CI dashboard/state backend that no run is genuinely in progress or recently crashed mid-apply; once confirmed stale, run terraform force-unlock with the lock ID shown in the error message, then retry.
Q91: How do you handle a scenario where someone manually changed a security group rule in the AWS console, and you want to detect — but not yet correct — that drift?
Run terraform plan -refresh-only, which shows exactly what changed out-of-band without proposing to revert it; review the diff, then decide whether to accept it into state with apply -refresh-only or to correct it back to the declared configuration with a normal apply.
Q92: Design a multi-region active-active Terraform setup for an application — what's the core pattern?
Define two aliased provider configurations (one per region), then instantiate the same reusable application-stack module twice, once per provider alias, each producing fully independent regional infrastructure; tie the two together at the DNS layer with Route53 latency-based or failover routing.
Q93: In a multi-account AWS Organizations setup, how does Terraform typically authenticate into each target account?
Via cross-account IAM role assumption (assume_role block in the provider configuration), where a central CI identity assumes a dedicated, narrowly-scoped deploy role in each target account rather than holding separate long-lived credentials per account.
Q94: Why is it considered an anti-pattern to manage frequently-changing application Kubernetes manifests directly through the Terraform kubernetes/helm providers at scale?
It conflates the low-frequency infrastructure provisioning layer with the much higher-frequency application deployment cadence, and lacks the continuous in-cluster reconciliation/drift-correction that a GitOps tool like Argo CD or Flux provides natively for application workloads.
Q95: What's the recommended layered responsibility split between Terraform and a GitOps tool when provisioning an EKS-based platform?
Terraform owns the "day 0" infrastructure layer (EKS cluster, node groups, VPC, IAM roles for service accounts, and possibly the initial Argo CD installation itself via the Helm provider); the GitOps tool then owns "day 2" continuous application deployment and reconciliation inside the cluster.
Q96: How would you validate a module's behavior automatically in CI using Terraform's native testing framework?
Write .tftest.hcl files with run blocks specifying command = plan or command = apply and assert blocks checking conditions against outputs or resource attributes (e.g., asserting an output VPC CIDR equals an expected value), then execute with terraform test in the CI pipeline.
Q97: A teammate accidentally ran terraform apply against the production workspace while intending to target staging — what process change would prevent recurrence?
Move from CLI-workspace-based environment switching to directory-per-environment root modules with separate backend configurations and separate IAM execution roles per environment, so there is no shared context in which the wrong environment could be silently selected; additionally require terraform workspace show / explicit directory confirmation as a CI pipeline guard.
Q98: How would you upgrade a large production Terraform codebase from provider major version 4 to 5 safely?
Read the provider's upgrade guide for breaking changes, perform the upgrade first in a non-production environment, update version constraints and run init -upgrade with the updated lock file committed in a dedicated PR separate from any functional change, run a full plan in each environment expecting zero unintended diffs, and roll forward dev → staging → production with a review gate at each stage.
Q99: Walk through diagnosing why an apply consistently shows the same "change" on every single run with no actual drift cause apparent.
Run terraform plan repeatedly and inspect the specific attribute flagged — common causes include a data source resolving non-deterministically (e.g., "most recent AMI" matching a new image), a provider normalizing an attribute differently than what's declared (e.g., case sensitivity or JSON key ordering in a policy document), or a missing ignore_changes for a field actively managed by another controller/process outside Terraform.
Q100: Describe your end-to-end disaster recovery plan if your team's Terraform S3 state bucket were accidentally deleted.
Confirm S3 bucket versioning and a deletion-protection/MFA-delete policy were in place beforehand (the actual prevention); if the bucket is truly gone, recreate the bucket and DynamoDB lock table, then rebuild state using terraform import (or declarative import blocks with -generate-config-out) resource by resource against the still-running real infrastructure — slow but viable since the configuration in Git was never lost, only the state tracking it.

Apply
The Terraform operation that executes a plan, calling provider APIs to create/update/delete real infrastructure and updating state accordingly.
Backend
The component determining where Terraform state is stored and how it's locked (local, S3, Terraform Cloud, etc.).
Child Module
A reusable module instantiated via a module block within a root or other module.
Data Source
A read-only block that looks up information about an object Terraform does not manage.
DAG (Directed Acyclic Graph)
The dependency graph structure Terraform builds for every operation, guaranteeing no circular dependencies and enabling safe parallel execution.
depends_on
A meta-argument declaring an explicit dependency Terraform cannot infer from attribute references.
Desired State
The infrastructure configuration as expressed in .tf files.
Drift
Any divergence between Terraform's tracked state and the real-world infrastructure, typically caused by out-of-band manual changes.
Dynamic Block
HCL syntax for generating repeated nested configuration blocks from a list or map at plan time.
for_each
A meta-argument creating one resource instance per element of a map or set, addressed by key (safer for non-identical, named resources than count).
HCL
HashiCorp Configuration Language — the declarative DSL used to write Terraform configuration.
Idempotency
The property that repeated execution with no configuration change produces no further effect.
Immutable Infrastructure
A philosophy of replacing resources entirely on change rather than patching them in place.
Import
Bringing an existing, unmanaged real-world resource under Terraform's state tracking.
Lifecycle Meta-Argument
A block customizing create/destroy/update behavior for a resource (create_before_destroy, prevent_destroy, ignore_changes, replace_triggered_by).
Lock File (.terraform.lock.hcl)
Records exact resolved provider versions and checksums for reproducible installs across team members and CI.
Module
A reusable, self-contained set of Terraform configuration files, instantiated via a module block.
Plan
The operation that refreshes state, diffs it against configuration, and outputs the proposed set of changes without applying them.
Plugin Cache
A shared local directory of downloaded provider binaries, avoiding redundant downloads across multiple projects.
Provider
A plugin translating Terraform resource blocks into API calls against a specific platform (AWS, Azure, Kubernetes, etc.).
Provisioner
A mechanism for running arbitrary local or remote commands at resource create/destroy time; generally discouraged in favor of native resources.
Registry
The public (or private) catalog from which Terraform resolves and downloads providers and modules.
Resource
A block whose lifecycle (create/update/delete) Terraform fully manages.
Root Module
The working directory where Terraform commands are run directly; the top of the module tree.
Sentinel
HashiCorp's policy-as-code framework for programmatically enforcing organizational rules against a Terraform plan.
State File (terraform.tfstate)
Terraform's JSON record mapping configuration to real-world resource identities and current attribute values.
State Locking
A mechanism preventing concurrent writes to the same state file, avoiding race conditions and corruption.
Workspace
A CLI mechanism allowing multiple distinct state files for the same configuration directory, distinguished by name.
