1. Container Fundamentals

1.1 What Are Containers?

A container is a standard unit of software that packages application code together with all its dependencies — libraries, runtime, configuration files, and environment variables — so that it runs quickly and reliably across different computing environments. Containers are not virtual machines: they do not include a full OS kernel. Instead, they share the host kernel and use Linux kernel features (namespaces and cgroups) to provide isolation.

Formally, a container is a running instance of a container image. An image is an immutable, layered filesystem built from a Dockerfile. When you start a container, the container runtime creates a new writable layer on top of the image and sets up isolated namespaces so the process tree, network interfaces, filesystem mounts, and user IDs inside the container are distinct from the host.

1.2 Why Were Containers Created?

The core problem containers solve is the classic 'works on my machine' failure. Before containers, deploying software meant either shipping the entire OS (VMs) or trusting that the target environment matched the development environment. This led to:

  • Dependency conflicts: Application A needs Python 2.7, Application B needs Python 3.9. On bare metal they clash.
  • Configuration drift: Servers configured manually diverge over time. What runs on staging fails in production.
  • Slow provisioning: VM images are gigabytes; spinning one up takes minutes.
  • Resource waste: A VM running one microservice dedicates an entire kernel, init system, and full OS to that one process.
  • Immutability problems: No way to guarantee what's actually installed in the target environment.

Containers address all of these by making the environment part of the artifact. The Docker image IS the deployment unit. It includes the exact binary, its libraries, its configuration — sealed and versioned. Run it anywhere with a compatible kernel and it behaves identically.

1.5 OCI Standards

The Open Container Initiative (OCI) is a Linux Foundation project that standardizes container formats and runtimes, ensuring interoperability between Docker, containerd, Podman, Kubernetes, and other tools.

OCI Image Specification

Defines the format of a container image: a manifest, a configuration object, and an ordered set of filesystem layers (tarballs). Any OCI-compliant tool can build, push, pull, and run any OCI image.

  • Image Index (fat manifest): Points to platform-specific manifests (linux/amd64, linux/arm64, etc.)
  • Image Manifest: Lists the config and layer SHAs for one platform
  • Image Config: Contains environment variables, entrypoint, working directory, layer diff IDs
  • Layers: Content-addressable gzipped tarballs of filesystem diffs

OCI Runtime Specification

Defines the interface between a container manager (containerd) and a low-level runtime (runc). Specifies the bundle format: a config.json describing namespaces, cgroups, capabilities, mounts, and a rootfs directory. runc reads config.json and creates the container.

OCI Distribution Specification

Defines the HTTP API for pushing and pulling container images to/from registries. Standardizes the /v2/ API endpoints used by Docker Hub, ECR, GCR, GHCR, and Harbor.

ToolOCI Relationship
docker buildProduces OCI-compliant images (was Docker Image Spec v1 historically)
docker push/pullUses OCI Distribution Spec API against any registry
containerdStores and runs OCI images; Docker's internal engine uses containerd
runcOCI Runtime Spec reference implementation; actually creates the container
PodmanFully OCI-compliant; builds and runs OCI images without a daemon

2. Docker Architecture Deep Dive

2.1 Docker Client (CLI)

The Docker CLI (docker) is a Go binary that reads commands from the user, formats them as REST API calls over a Unix socket (/var/run/docker.sock), and displays the responses. The CLI itself does no container work — it is purely a client. This design means you can point the Docker CLI at any Docker daemon, local or remote.

Internal Workflow

  • User runs: docker run nginx
  • CLI parses the command into an API request: POST /v1.41/containers/create + POST /v1.41/containers/{id}/start
  • CLI serializes to JSON and sends via Unix socket
  • Daemon processes request, returns JSON response with container ID
  • CLI prints the container ID to stdout

Remote Docker Daemon

# Connect to remote Docker daemon via TCP (insecure - dev only)
export DOCKER_HOST=tcp://192.168.1.100:2375

# Connect via TLS (production)
export DOCKER_HOST=tcp://192.168.1.100:2376
export DOCKER_TLS_VERIFY=1
export DOCKER_CERT_PATH=~/.docker/certs

# Verify connection
docker info

Failure Scenarios

  • Cannot connect to the Docker daemon: Unix socket /var/run/docker.sock doesn't exist → dockerd not running, or user not in docker group
  • Permission denied: User lacks read/write access to the socket → add user to docker group
  • TLS handshake failed: Certificate mismatch in remote connection → verify DOCKER_CERT_PATH

2.2 Docker REST API

The Docker API is a versioned REST API served over a Unix domain socket (local) or TCP socket (remote). Every CLI command maps to one or more API calls. You can use it directly with curl or any HTTP client.

# Direct API call via curl over Unix socket
curl --unix-socket /var/run/docker.sock http://localhost/v1.41/version

# List containers
curl --unix-socket /var/run/docker.sock http://localhost/v1.41/containers/json

# Create a container
curl --unix-socket /var/run/docker.sock -X POST \
  -H 'Content-Type: application/json' \
  -d '{"Image":"nginx","Cmd":["/bin/bash"]}' \
  http://localhost/v1.41/containers/create

# API version negotiation - always use current or lower
curl --unix-socket /var/run/docker.sock http://localhost/version
SECURITY: The Docker socket gives root-equivalent access to the host. Any process that can write to /var/run/docker.sock can mount the host filesystem, create privileged containers, and escape. Never expose it to untrusted containers or processes.

2.3 Docker Daemon (dockerd)

The Docker daemon (dockerd) is the central server process that manages all Docker objects: images, containers, networks, and volumes. It listens on the Unix socket and handles API requests by orchestrating containerd.

What dockerd Does

  • Receives API calls from clients
  • Image management: pull, build (via BuildKit), push, cache management
  • Container lifecycle: create, start, stop, kill via containerd
  • Network management: creates bridge networks, manages iptables rules
  • Volume management: creates and mounts named volumes
  • Plugin management: volume drivers, network plugins
  • Swarm mode: manages cluster state via Raft consensus

containerd-shim

The containerd-shim is a small process that sits between containerd and runc. One shim process exists per container. Its purpose is critical: after runc creates the container and exits, the shim becomes the parent of PID 1 in the container. This means containerd itself can be restarted without affecting running containers (live-restore). The shim also:

  • Holds the container's stdin/stdout/stderr pipes open
  • Reports container exit status back to containerd
  • Handles PTY allocation for interactive sessions
  • Reaps zombie processes (acts as mini-init)

2.5 runc

runc is the OCI-compliant low-level container runtime. It is a CLI tool that takes a bundle (OCI runtime spec config.json + rootfs/) and creates a container using Linux primitives directly. runc is the reference implementation of the OCI Runtime Specification.

When runc creates a container, it:

  1. Reads config.json for namespaces, capabilities, seccomp profiles, mounts
  1. Forks a new process with CLONE_NEWPID, CLONE_NEWNET, CLONE_NEWNS, CLONE_NEWUTS, CLONE_NEWIPC flags
  1. Sets up cgroup limits (memory, CPU, pids)
  1. Applies seccomp profile to filter syscalls
  1. Drops Linux capabilities to the configured set
  1. Chroots into the rootfs
  1. Executes the container's entrypoint
  1. Exits — the container now lives without runc

2.6 BuildKit

BuildKit is Docker's next-generation build engine, replacing the legacy builder. It provides massively improved build performance through parallelism, better caching, and new features.

# Enable BuildKit (default in Docker 23.0+)
export DOCKER_BUILDKIT=1

# Or set in daemon.json permanently
{ "features": { "buildkit": true } }

# BuildKit-specific Dockerfile features
# syntax=docker/dockerfile:1.4

# Secret mount (never written to image layer)
RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret

# SSH agent forwarding
RUN --mount=type=ssh git clone git@github.com:org/private-repo.git

# Cache mount (persistent across builds)
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# Bind mount (read source without COPY)
RUN --mount=type=bind,source=.,target=/app go build ./...

BuildKit Performance Advantages

  • Parallel layer building: Independent Dockerfile stages run concurrently
  • Better cache invalidation: Content-based, not instruction-order-based
  • Garbage collection: Automatic cleanup of unused build cache
  • Distributed cache: Export/import cache to/from registries
  • No intermediate containers: Build happens in memory, no container commit

3. Linux Internals Behind Docker

Docker is fundamentally a user-space tool that assembles Linux kernel primitives into a coherent runtime. Understanding these primitives is essential for debugging, performance tuning, and security hardening.

3.1 Linux Namespaces

Namespaces are a Linux kernel feature that partitions kernel resources so that processes in different namespaces see different views of the system. Docker creates one set of namespaces per container.

NamespaceClone FlagDocker Usage
pidCLONE_NEWPIDEach container has its own PID numbering. Container's init is PID 1. From inside, can't see host PIDs.
netCLONE_NEWNETIsolated network stack: interfaces, routing tables, iptables rules, sockets. Each container gets its own eth0.
mntCLONE_NEWNSIsolated mount table. Container sees its own filesystem root. Host mounts invisible unless explicitly shared.
utsCLONE_NEWUTSHostname and NIS domain name isolation. Container can set its own hostname without affecting host.
ipcCLONE_NEWIPCIsolated SysV IPC, POSIX message queues. Processes in different containers can't use shared memory between them.
userCLONE_NEWUSERMap container UIDs/GIDs to different host UIDs/GIDs. Enables rootless containers.
cgroupCLONE_NEWCGROUPIsolated cgroup hierarchy view. Container sees its own cgroup root, not host cgroups.
timeCLONE_NEWTIMELinux 5.6+. Per-process clock offsets. Not commonly used by Docker yet.

Inspecting Container Namespaces

# Get container PID on host
CONTAINER_PID=$(docker inspect --format '{{.State.Pid}}' my_container)

# View namespaces of the container process
ls -la /proc/$CONTAINER_PID/ns/

# Enter a namespace (like docker exec but manual)
nsenter -t $CONTAINER_PID --net --pid --mount ip addr show

# View all containers' PIDs
docker inspect --format '{{.Name}} {{.State.Pid}}' $(docker ps -q)

3.2 Control Groups (cgroups)

cgroups (control groups) are a Linux kernel mechanism that limits, accounts for, and isolates the resource usage of collections of processes. Docker uses cgroups to enforce --memory, --cpus, --pids-limit, and other resource constraints.

cgroup SubsystemDocker Usage
cpuCPU time allocation. cpu.shares (relative weight), cpu.cfs_quota_us / cpu.cfs_period_us (hard limits).

3.3 Union Filesystems and OverlayFS

Docker images are composed of layers. The union filesystem merges multiple directory trees into a single coherent view. OverlayFS (overlay2 storage driver) is the modern standard union filesystem used by Docker on Linux.

  OverlayFS Layer Stack
  ┌────────────────────────────────────────────────────┐
  │  Container View (merged)  -- what container sees   │
  └───────────────────────┬────────────────────────────┘
                          │ overlayfs mount
  ┌───────────────────────┼────────────────────────────┐
  │  upperdir (R/W)       │  workdir (temp for atomic) │
  │  /var/lib/docker/     │  /var/lib/docker/          │
  │  overlay2/<id>/diff   │  overlay2/<id>/work        │
  └───────────────────────┼────────────────────────────┘
                          │ lowerdir (R/O, stacked)
  ┌────────────────────────────────────────────────────┐
  │  Layer N (app layer, e.g. COPY . /app)             │
  ├────────────────────────────────────────────────────┤
  │  Layer N-1 (deps layer, e.g. RUN pip install)      │
  ├────────────────────────────────────────────────────┤
  │  Layer 2 (apt packages)                            │
  ├────────────────────────────────────────────────────┤
  │  Layer 1 (base OS, e.g. ubuntu:22.04)              │
  └────────────────────────────────────────────────────┘

Copy-on-Write (CoW) Semantics

When a container writes to a file that exists in a lower (read-only) layer, OverlayFS performs a copy-up: the file is copied from the lower layer to the upper (writable) layer, then modified there. The lower layer is never modified. This has performance implications:

  • First write to a large file is expensive: the entire file is copied to upper before modification.
  • Subsequent writes to the same file are fast: the copy already exists in upper.
  • Reading files never modified is free: served directly from lower layers.
  • Deleting a file creates a whiteout file in upper, masking the lower layer entry.

4. Docker Images Deep Dive

4.1 What Is a Docker Image?

A Docker image is an immutable, read-only, layered filesystem that contains everything needed to run an application: code, runtime, libraries, environment variables, and configuration. Images are identified by a content-addressable SHA256 digest and optionally by a human-readable tag.

An image is NOT a running process. It is a blueprint. When you docker run an image, Docker creates a container: a running instance of the image with an additional writable layer on top.

4.2 Image Layers

Every instruction in a Dockerfile that modifies the filesystem (RUN, COPY, ADD) creates a new immutable layer. Layers are content-addressed (SHA256 of their contents) and stored once per host regardless of how many images or containers use them.

# View image layers
docker history nginx:latest

# Detailed layer information
docker inspect nginx:latest | python3 -m json.tool | grep -A 20 'RootFS'

# View layer sizes
docker history --no-trunc --format 'table {{.Size}}\t{{.CreatedBy}}' nginx:latest

# List layer digests
docker manifest inspect nginx:latest

Layer Sharing - Why It Matters

If two images share the same base (e.g., both FROM ubuntu:22.04), the ubuntu layers are stored once and shared. This dramatically reduces disk usage and pull times. On a host running 20 microservices all based on node:18-alpine, the base Alpine and Node layers are stored once, not 20 times.

4.3 Image Manifest

The image manifest is a JSON document that describes the image: its configuration and its ordered list of layers. When you docker pull an image, Docker first fetches the manifest to discover what to download.

4.4 Multi-Stage Builds

Multi-stage builds allow you to use multiple FROM statements in one Dockerfile. Each FROM starts a new stage with a clean filesystem. You can COPY files from earlier stages, leaving behind all the build tools. This produces tiny production images.

# Multi-stage Go build - from 800MB builder to 15MB final
# syntax=docker/dockerfile:1

# Stage 1: Build
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags='-w -s' -o /app/server .

# Stage 2: Production image
FROM scratch
COPY --from=builder /app/server /server
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
USER 65534:65534
EXPOSE 8080
ENTRYPOINT ["/server"]

# Result: ~5MB image with no shell, no package manager, no attack surface
# Multi-stage Python build with virtual environment
FROM python:3.11-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.11-slim AS production
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /app
COPY --chown=nobody:nogroup . .
USER nobody
CMD ["python", "app.py"]

4.5 Multi-Architecture Images

Multi-arch images (also called fat manifests or image indices) allow a single image tag (e.g., nginx:latest) to serve multiple architectures. When you docker pull nginx on an ARM Mac and on an x86 server, you get the correct binary for each platform.

  --platform linux/amd64,linux/arm64,linux/arm/v7 \
  --tag myrepo/myapp:latest \
  --push \
  .

# Inspect the manifest list
docker manifest inspect myrepo/myapp:latest

# Pull specific platform
docker pull --platform linux/arm64 myrepo/myapp:latest

4.6 Build Cache

Docker's build cache is a critical performance feature. Before executing each Dockerfile instruction, the builder checks whether a cached layer matching the same instruction and inputs exists. If found, it reuses the cache instead of re-executing.

Cache Invalidation Rules

  • Cache miss on any instruction invalidates all subsequent layers (they must be rebuilt)
  • RUN instruction: cache hit only if previous layers match AND the command string is identical
  • COPY/ADD: cache hit only if file contents (checksums) match, not just names
  • ENV, ARG: changing a value invalidates the layer and all following layers

Cache Optimization Pattern

# BAD: Copies ALL source before installing deps
# Any source change invalidates the pip install layer
COPY . /app
RUN pip install -r requirements.txt

# GOOD: Install deps first (rarely changes), then copy source
COPY requirements.txt /app/
RUN pip install -r /app/requirements.txt
COPY . /app
# Now: only source changes force the slow 'pip install' to re-run?  NO
# requirements.txt rarely changes -> pip install is cached
# source changes only invalidate COPY . /app layer (fast)

5. Dockerfile Deep Dive

The Dockerfile is a text file containing a sequence of instructions that Docker reads top-to-bottom to build an image. Each instruction (except FROM in multi-stage, and ARG before FROM) creates a new layer in the image. Understanding each instruction's internal behavior is essential for writing optimal Dockerfiles.

5.1 FROM

# Syntax
FROM [--platform=<platform>] <image>[:<tag>|@<digest>] [AS <name>]

# Examples
FROM ubuntu:22.04
FROM node:18-alpine AS builder
FROM --platform=linux/amd64 nginx:latest
FROM scratch  # empty filesystem - for statically compiled binaries
FROM golang:1.21@sha256:a81bc5...  # pinned by digest

FROM initializes a new build stage and sets the base image. Every Dockerfile must start with FROM (except ARG before FROM). The base image provides the initial filesystem layers.

Best practices: Always pin to a specific version tag or digest. Using :latest means builds break unpredictably when the base image updates. Use platform flag for cross-compilation. Use scratch for minimal attack surface.

5.2 RUN

# Shell form (runs via /bin/sh -c on Linux)
RUN apt-get update && apt-get install -y curl

# Exec form (no shell, no string interpolation, no shell features)
RUN ["/usr/bin/apt-get", "install", "-y", "curl"]

# BuildKit: cache mount (pip cache persists across builds)
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

# BuildKit: secret mount (not stored in any layer)
RUN --mount=type=secret,id=aws,target=/root/.aws/credentials \
    aws s3 cp s3://bucket/config.json /app/

# Production pattern: combine, clean in same layer
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
       curl wget ca-certificates \
    && rm -rf /var/lib/apt/lists/* \
    && apt-get clean

CRITICAL: The rm -rf /var/lib/apt/lists/* MUST be in the same RUN command as apt-get install. If placed in a separate RUN, the apt cache is committed to the lower layer and cannot be removed by a higher layer.

5.3 CMD vs ENTRYPOINT

CMD and ENTRYPOINT are the most confusing Dockerfile instructions. Understanding them together is essential.

  ENTRYPOINT vs CMD interaction:

  ┌─────────────────┬───────────────────┬────────────────────────────────────┐
  │ ENTRYPOINT      │ CMD               │ docker run result                  │
  ├─────────────────┼───────────────────┼────────────────────────────────────┤
  │ (none)          │ ["cmd","args"]    │ cmd args                           │
  │ ["ep"]          │ (none)            │ ep                                 │
  │ ["ep"]          │ ["cmd","args"]   │ ep cmd args  (CMD = default args) │
  │ ["ep"]          │ (none)            │ ep extra     (extra from CLI)      │
  │ ["ep"]          │ ["cmd"]          │ ep extra     (CLI overrides CMD)   │
  └─────────────────┴───────────────────┴────────────────────────────────────┘
# ENTRYPOINT: fixed executable, cannot be overridden without --entrypoint flag
ENTRYPOINT ["nginx", "-g", "daemon off;"]

# CMD: default arguments, overridden by docker run arguments
CMD ["--worker-processes", "auto"]

# Common pattern: wrapper script as ENTRYPOINT
COPY docker-entrypoint.sh /docker-entrypoint.sh
RUN chmod +x /docker-entrypoint.sh
ENTRYPOINT ["/docker-entrypoint.sh"]
CMD ["nginx", "-g", "daemon off;"]

# Anti-pattern: shell form ENTRYPOINT
# ENTRYPOINT nginx -g 'daemon off;'  # BAD: runs as /bin/sh -c, PID 1 is shell
# This breaks signal handling - SIGTERM to PID 1 goes to shell, not nginx

# Correct: exec form for proper signal handling
ENTRYPOINT ["nginx", "-g", "daemon off;"]

5.4 COPY vs ADD

# COPY: simple, predictable - PREFERRED
COPY source.txt /app/source.txt
COPY ./src /app/src
COPY --chown=node:node package*.json ./
COPY --from=builder /app/dist /app/dist  # from build stage

# ADD: superset of COPY with two additional features
# 1. Auto-extracts .tar, .tar.gz, .tar.bz2, .tar.xz, .tgz
ADD archive.tar.gz /app/  # extracts automatically

# 2. Fetches remote URLs (AVOID in production)
ADD https://example.com/file.txt /app/  # BAD: no cache invalidation guarantee

# Best practice: use COPY for everything except tar extraction
# For remote files: use RUN curl/wget in same layer
RUN curl -fsSL https://example.com/file.txt -o /app/file.txt

5.5 WORKDIR

# Sets working directory for subsequent RUN, CMD, ENTRYPOINT, COPY, ADD
WORKDIR /app

# Creates directory if it doesn't exist
# Equivalent to: mkdir -p /app && cd /app

# Can be used multiple times (relative paths compound)
WORKDIR /app
WORKDIR src
# Current dir is now /app/src

# Best practice: always use absolute paths
WORKDIR /app  # NOT: WORKDIR app

5.6 USER

# Switch to non-root user - CRITICAL for security
USER 1000:1000          # numeric UID:GID
USER node               # named user (must exist in container)
USER node:node          # user:group

# Create user in build, then switch
RUN groupadd -r appgroup && useradd -r -g appgroup -u 1000 appuser
USER appuser

# For distroless images: use numeric UID
USER 65534:65534  # nobody:nogroup

# Common mistake: forgetting to chown files before USER switch
COPY --chown=node:node . /app
USER node

6. Container Lifecycle

6.1 Container State Transitions

Every container transitions between states managed by dockerd and containerd. Understanding these transitions helps diagnose restart loops, stuck containers, and unexpected behavior.

CommandLifecycle Action
docker createAllocates a container ID, creates the writable layer, sets up namespaces (but doesn't start them), returns the container ID. Container is in 'created' state. Filesystem exists on disk.
docker startTells containerd to create the OCI bundle, calls runc to fork into namespaces, executes ENTRYPOINT/CMD as PID 1. Container moves to 'running'.
docker runCombines create + start. Also handles -d (detach) or interactive modes. Most commonly used command.
docker stopSends STOPSIGNAL (default SIGTERM) to PID 1 in the container. Waits up to --time seconds (default 10). If process hasn't exited, sends SIGKILL. Container moves to 'stopped/exited'.
docker killSends a signal directly (default SIGKILL, immediate). No grace period. Use for force-stopping hung containers.
docker pauseFreezes all processes via cgroup freezer. Zero CPU usage. All memory retained. Perfect for snapshotting state without stopping.
docker unpauseThaws frozen processes. They resume exactly where they were.
docker restartEquivalent to docker stop followed by docker start. Uses restart policy for retries.
docker rmRemoves the container: deletes the writable layer, removes from Docker state. Container must be stopped first (use -f to force).
docker commitCreates a new image from the container's current state (writable layer merged with base layers). Rarely used in modern workflows.

# Always restart (even on docker stop - only stops on daemon shutdown)

# Restart unless manually stopped

7.1 Networking Architecture Overview

Docker networking is implemented through a combination of Linux virtual interfaces (veth pairs), network namespaces, bridges, iptables/netfilter rules, and optionally overlay networks (VXLAN) for multi-host communication.

7.2 Network Drivers

Bridge (Default)

The bridge driver creates a Linux bridge (docker0 by default) and connects container network namespaces to it via veth pairs. Each container gets a private IP in the bridge subnet.

# Create custom bridge network
docker network create \
  --driver bridge \
  --subnet 192.168.100.0/24 \
  --gateway 192.168.100.1 \
  --opt com.docker.network.bridge.name=docker_br0 \
  my_network

# Connect containers to network
docker run --network my_network --name web nginx
docker run --network my_network --name db postgres

# On custom networks, containers resolve each other by name
# 'web' can ping 'db' by name (embedded DNS)

# Connect existing container to additional network
docker network connect my_network existing_container

# Disconnect
docker network disconnect my_network existing_container

Host Network

Host networking removes network isolation: the container shares the host's network namespace directly. The container's port 80 IS host port 80. No port mapping needed. Best performance but no isolation.

# Container uses host network directly
docker run --network host nginx

# nginx listens on host's port 80 directly
# No -p flag needed or supported

# Use case: performance-critical apps, network monitoring tools
# Security risk: container can sniff all host traffic, bind any port

None Network

No network interface except the loopback (lo). Container is completely isolated from all networks. Useful for batch jobs that need no network access.

Overlay Network

Overlay networks span multiple Docker hosts using VXLAN encapsulation. Required for Docker Swarm. Creates a virtual L2 network across physical hosts. Each container gets an IP in the overlay subnet regardless of which host it's on.

# Overlay requires Swarm mode or standalone overlay setup
docker swarm init

# Create overlay network
docker network create \
  --driver overlay \
  --attachable \
  --subnet 10.20.0.0/16 \
  my_overlay

# Deploy service on overlay
docker service create --network my_overlay nginx

Macvlan and IPvlan

# Macvlan: each container gets a unique MAC address on the physical network
# Container appears as a physical device on the LAN
docker network create \
  --driver macvlan \
  --subnet 192.168.1.0/24 \
  --gateway 192.168.1.1 \
  -o parent=eth0 \
  macvlan_net

docker run --network macvlan_net --ip 192.168.1.200 nginx

# IPvlan L2: similar to macvlan but shares MAC, different IP
docker network create \
  --driver ipvlan \
  --subnet 192.168.1.0/24 \
  -o parent=eth0 \
  ipvlan_net

7.3 Embedded DNS and Service Discovery

Docker includes an embedded DNS server running at 127.0.0.11 inside every container that joins a user-defined network. This server resolves container names, service names (in Swarm), and network aliases to their IPs.

# Containers on the same user-defined network resolve each other by name
docker network create app_net
docker run -d --name database --network app_net postgres
docker run -d --name api --network app_net my_api

# Inside 'api' container:
# ping database      -> resolves to database container IP
# curl http://database:5432  -> connects to postgres

# Add network aliases (multiple names for one container)
docker run -d --name primary_db \
  --network app_net \
  --network-alias database \
  --network-alias db \
  postgres

# DNS resolution order: container name > alias > external DNS

# Check DNS from inside container
docker exec api cat /etc/resolv.conf
# nameserver 127.0.0.11
# options ndots:0

8.2 Named Volumes

Docker-managed volumes are stored in /var/lib/docker/volumes/ (or the data-root path). Docker manages creation, mounting, and cleanup. They are the recommended way to persist data.

# Create a named volume
docker volume create my_data

# Use volume in container
docker run -v my_data:/app/data nginx
docker run --mount type=volume,source=my_data,target=/app/data nginx

# Mount as read-only
docker run -v my_data:/app/data:ro nginx

# Inspect volume
docker volume inspect my_data

# List volumes
docker volume ls

# Volume location on host
ls /var/lib/docker/volumes/my_data/_data/

# Backup volume
docker run --rm -v my_data:/data -v $(pwd):/backup \
  alpine tar czf /backup/data_backup.tar.gz /data

# Restore volume
docker run --rm -v my_data:/data -v $(pwd):/backup \
  alpine tar xzf /backup/data_backup.tar.gz -C /

8.3 Bind Mounts

Bind mounts mount a specific host filesystem path into the container. The host path must exist. Great for development (hot reload) and injecting host configuration, but creates tight coupling to host path structure.

# Bind mount host directory into container
docker run -v /host/path:/container/path nginx
docker run --mount type=bind,source=/host/path,target=/container/path nginx

# Read-only bind mount
docker run -v /etc/nginx/conf.d:/etc/nginx/conf.d:ro nginx

# Development hot reload pattern
docker run -v $(pwd):/app -w /app node:18 npm run dev

# Inject single file
docker run -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro nginx

# SELinux: add :z (shared) or :Z (private) label
docker run -v /host/data:/data:z mycontainer

8.4 tmpfs Mounts

# tmpfs: in-memory filesystem, never written to disk
docker run --tmpfs /run --tmpfs /tmp nginx

# With options (size limit, unix permissions)
docker run --mount type=tmpfs,destination=/tmp,tmpfs-size=100m,tmpfs-mode=1777 \

Docker Compose is a tool for defining and running multi-container applications. Compose reads a compose.yaml file, builds a dependency graph of services, and orchestrates their creation, networking, and lifecycle. Compose V2 (compose plugin) is built into Docker CLI as docker compose.

10.1 Registry Architecture

A container registry is an OCI Distribution Spec-compliant server. It stores image manifests and layer blobs, indexed by repository name and tag. Docker clients interact with registries via the /v2/ HTTP API.

  Registry API Flow (docker push)

  Docker Client                    Registry Server
       │                                │
       │─── GET /v2/ ──────────────────▶│  (Check API version)
       │◀── 200 OK ─────────────────────│
       │                                │
       │─── POST /v2/<name>/blobs/uploads/start ──▶│
       │◀── 202 Accepted (Location: /uploads/{uuid})│
       │                                │
       │─── PATCH /v2/<name>/blobs/uploads/{uuid} ▶│  (Upload layer)
       │◀── 202 Accepted ───────────────│
       │                                │
       │─── PUT /v2/<name>/blobs/uploads/{uuid}?digest=sha256:...  ▶│
       │◀── 201 Created ────────────────│
       │                                │
       │─── (repeat for each layer) ────│
       │                                │
       │─── PUT /v2/<name>/manifests/<tag> ──▶│  (Push manifest)
       │◀── 201 Created ────────────────│

11. Docker Security

11.1 Security Threat Model

Docker security involves multiple layers of defense. The primary threat categories are: container escape (process in container gains host access), privilege escalation (gaining root from non-root), image supply chain attacks (malicious base images), and secrets exposure (credentials in images/envvars).

  Docker Security Layers
  ┌─────────────────────────────────────────────────────────────────┐
  │ 1. Image Supply Chain: signed images, scanning, trusted sources │
  ├─────────────────────────────────────────────────────────────────┤
  │ 2. Dockerfile: non-root USER, minimal base, no secrets in layers│
  ├─────────────────────────────────────────────────────────────────┤
  │ 3. Runtime: --cap-drop ALL, seccomp profile, no --privileged    │
  ├─────────────────────────────────────────────────────────────────┤
  │ 4. Kernel: namespaces, cgroups, user namespace remapping        │
  ├─────────────────────────────────────────────────────────────────┤
  │ 5. MAC: AppArmor / SELinux profiles                            │
  ├─────────────────────────────────────────────────────────────────┤
  │ 6. Network: no unnecessary ports, internal networks             │
  ├─────────────────────────────────────────────────────────────────┤
  │ 7. Secrets: Docker secrets / vault, never in envvars or layers  │
  └─────────────────────────────────────────────────────────────────┘

11.2 Rootless Docker

Rootless Docker runs the Docker daemon itself as a non-root user. Even if an attacker escapes the container, they are limited to the unprivileged user's host permissions.

# Install rootless Docker (run as regular user)
dockerd-rootless-setuptool.sh install

# Configure for current user
export PATH=/usr/bin:$PATH
export DOCKER_HOST=unix:///run/user/1000/docker.sock

# Enable systemd user service
systemctl --user enable docker
systemctl --user start docker

# Limitations of rootless mode:
# - No host port < 1024 binding (use sysctl net.ipv4.ip_unprivileged_port_start=80)
# - No host networking (--network host)
# - No overlay network without additional setup
# - Limited device access

13. Docker in Kubernetes

13.1 Why Kubernetes Deprecated Dockershim

Prior to Kubernetes 1.24, Kubernetes used dockershim — a shim layer that translated the Container Runtime Interface (CRI) calls into Docker API calls. This added unnecessary complexity. Docker itself uses containerd internally, so Kubernetes was calling Docker which called containerd. Kubernetes 1.24 removed dockershim, making containerd (or CRI-O) the direct runtime.

  Before Kubernetes 1.24 (with dockershim):
  kubelet → CRI → dockershim → Docker API → dockerd → containerd → runc

  After Kubernetes 1.24 (direct CRI):
  kubelet → CRI → containerd (with CRI plugin) → runc
  kubelet → CRI → CRI-O → runc

  Docker images still work perfectly - OCI images are OCI images.
  'docker build' still produces OCI-compliant images that Kubernetes runs.

13.2 Container Runtime Interface (CRI)

CRI is a plugin interface in Kubernetes that allows the kubelet to use different container runtimes. It defines a gRPC API with two services: RuntimeService (manage pods/containers) and ImageService (pull/list/remove images).

# Configure containerd as CRI runtime in kubelet
# /var/lib/kubelet/config.yaml:
containerRuntimeEndpoint: unix:///run/containerd/containerd.sock

# Inspect containerd containers from host (bypassing Docker)

# ctr (containerd CLI) - lower level than crictl

19. Interview Preparation

19.1 Top Docker Interview Questions

Fundamentals

QuestionModel Answer
What is the difference between a container and a VM?Containers share host kernel, use namespaces/cgroups for isolation, start in ms, are MBs in size. VMs have full kernel, hardware-level isolation, take minutes to start, are GBs. Containers trade isolation strength for density and speed.
What is the OCI standard and why does it matter?Open Container Initiative defines portable image format (Image Spec), runtime interface (Runtime Spec), and registry API (Distribution Spec). Ensures Docker images run on containerd, Podman, CRI-O — vendor lock-in avoided.
Explain Docker's layered filesystem.Images are built from stacked read-only layers (OverlayFS). Each Dockerfile instruction creates a layer. Layers are content-addressed (SHA256) and shared between images. Containers add a writable layer on top. Copy-on-Write: writes go to upper layer, reads come from first layer that has the file.
What happens when you run 'docker run nginx'?CLI sends POST /containers/create + /containers/start to dockerd. dockerd instructs containerd to pull image if needed, create OCI bundle. containerd-shim spawns runc. runc creates namespaces (pid, net, mnt, uts, ipc), configures cgroups, applies seccomp, chroots into rootfs, execs nginx. runc exits. shim stays as parent of nginx process.
CMD vs ENTRYPOINT?ENTRYPOINT is the fixed executable (can't be overridden without --entrypoint). CMD provides default arguments, overridden by docker run args. Use exec form for both (["executable"]) for proper signal handling. Shell form wraps in /bin/sh -c making it PID 2, not PID 1.
How do Docker networks work?Bridge: veth pairs, Linux bridge, NAT iptables rules. Host: no network namespace isolation. Overlay: VXLAN tunneling across hosts for Swarm. Embedded DNS resolves container names on user-defined networks at 127.0.0.11.
Volumes vs Bind Mounts?Volumes: Docker-managed (/var/lib/docker/volumes/), portable, can use drivers for NFS/EBS. Bind mounts: specific host path, coupled to host, better for dev hot-reload. tmpfs: in-memory, no persistence. Prefer volumes in production.

Advanced / Architecture

QuestionModel Answer
Why did Kubernetes remove Dockershim?kubelet → dockershim → dockerd → containerd → runc was unnecessary indirection. Docker itself just wraps containerd. k8s 1.24+ talks directly to containerd via CRI. Docker images still work (OCI-compliant). Only the runtime path changed.
Explain container escape scenarios.Privileged containers: CAP_SYS_ADMIN + /proc/sys access = host root. Mounted docker.sock: create privileged container from inside. runc CVE (CVE-2019-5736): malicious image overwrites runc binary. Kernel exploits: shared kernel = kernel CVE affects all containers. Defense: drop caps, no --privileged, user namespaces, no socket mount.
How does BuildKit differ from legacy builder?BuildKit: parallel stage execution, content-based cache (not instruction order), --mount=type=secret|cache|ssh support, no intermediate containers, distributed cache export/import, garbage collection. Legacy: sequential, instruction-order cache, secrets in ARG (visible in history).
Design a production Dockerfile for a Python microservice.Multi-stage: builder stage installs all deps including dev; production stage copies only venv/dist. Alpine or slim base. RUN --mount=type=cache for pip. COPY requirements.txt before source. Non-root USER. HEALTHCHECK. exec-form ENTRYPOINT. Read-only FS design.
What is copy-on-write and its performance implications?First write to a file from a lower layer triggers a copy-up: entire file copied to upper layer before modification. Large files (databases, VM disk images) in container FS = huge CoW overhead. Solution: use volumes for heavy I/O paths. Subsequent writes to the same file are fast (already in upper).

Troubleshooting Scenarios

ScenarioDiagnosis Steps
Container keeps restarting. How do you diagnose?docker inspect --format '{{.State.ExitCode}}' container. 137=OOMKill, 1=app error, 143=SIGTERM not handled. docker logs --previous for last run's output. docker events for timeline. Check OOMKilled field. docker stats for memory pressure.
Network connectivity lost after reboot.Check iptables FORWARD policy: iptables -L FORWARD -n. Docker restarts may not restore iptables rules if UFW/firewalld interfered. systemctl restart docker. Check /proc/sys/net/ipv4/ip_forward = 1.
Build is slow despite no code changes.Build context too large (node_modules not in .dockerignore). Layer cache invalidated early (COPY . before dependency install). No BuildKit enabled. Solution: .dockerignore, reorder instructions (deps before source), DOCKER_BUILDKIT=1.
Production container ran out of disk.docker system df to identify usage. Container FS writes (logs to container FS instead of volume). Missing log rotation (json-file without max-size). Build cache accumulation. Solution: volumes for logs, log rotation config, scheduled docker system prune.

19.2 Security Questions

QuestionModel Answer
How would you harden a Docker deployment?Rootless Docker or user namespace remapping. All containers: --cap-drop ALL --cap-add (only needed). --read-only --tmpfs for temp. --security-opt no-new-privileges. --memory --cpus --pids-limit. Non-root USER in Dockerfile. Scan images with Trivy. DOCKER_CONTENT_TRUST=1. Avoid docker.sock mounts. Network segmentation: internal networks for DBs.
What is the Docker socket security risk?/var/run/docker.sock gives root-equivalent host access. Mounting into containers (e.g., CI runners) allows: creating privileged containers, mounting host filesystem, running host commands as root. Defense: avoid socket mounts, use rootless Docker, use dedicated socket proxy (tecnativa/docker-socket-proxy) with limited API access.
How do you manage secrets in Docker?Build time: BuildKit --mount=type=secret (never in layer). Runtime: Docker Swarm secrets (/run/secrets/), Kubernetes secrets, HashiCorp Vault agent. Never: ENV, ARG, COPY of plaintext files, docker inspect-visible envvars. Production pattern: app reads from /run/secrets/ or Vault API at startup.

20. Comprehensive Glossary

Core Container Terms

TermDefinition
ContainerA running instance of an OCI image. An isolated process (or process tree) with its own namespaces, cgroup limits, and layered filesystem view.
ImageAn immutable, layered, content-addressable filesystem snapshot. The blueprint from which containers are created.
LayerAn immutable filesystem diff (added/modified/deleted files) stored as a content-addressed tar archive. Images are ordered stacks of layers.
DockerfileA text recipe that Docker/BuildKit reads to build an image. Each instruction (RUN, COPY, etc.) creates a new image layer.
RegistryAn OCI Distribution Spec-compliant server that stores and distributes container images (Docker Hub, ECR, Harbor, etc.).
ManifestJSON document describing an image: its config JSON SHA and ordered list of layer SHAs.
Manifest list / Image indexA manifest pointing to platform-specific manifests (linux/amd64, linux/arm64). Enables multi-arch images under one tag.
TagA human-readable name for an image version (nginx:1.25.3). Tags are mutable; digests (sha256:...) are immutable.
DigestContent-addressable SHA256 identifier for an image or layer. Immutable: same digest = same content always.
OCIOpen Container Initiative. Defines Image Spec, Runtime Spec, Distribution Spec for container portability.

Docker Architecture Terms

TermDefinition
dockerdThe Docker daemon. Central server managing images, containers, networks, volumes via REST API.
Docker CLIClient binary (docker) that sends REST API calls to dockerd over Unix socket.
Docker APIVersioned REST API (/v1.41/) served over /var/run/docker.sock (local) or TCP 2375/2376 (remote).
containerdCNCF container runtime. Manages image storage, container lifecycle, and snapshots. Used by Docker and Kubernetes.
containerd-shimPer-container process that stays running after runc exits. Holds container's I/O open. Enables live-restore.
runcOCI Runtime Spec reference implementation. Low-level binary that creates container namespaces and execs PID 1. Exits after container starts.
BuildKitDocker's next-gen build engine. Parallel stages, better caching, --mount=type=secret/cache/ssh support.
Docker DesktopCross-platform GUI application (Mac/Windows/Linux) providing Docker within a VM, with UI, Compose, Extensions.
CRIContainer Runtime Interface. Kubernetes gRPC API that kubelet uses to talk to container runtimes.
DockershimRemoved in k8s 1.24. Was a shim translating CRI calls into Docker API calls. Eliminated unnecessary indirection.

Linux Kernel Terms

TermDefinition
NamespaceLinux kernel feature that partitions global resources. Docker uses pid, net, mnt, uts, ipc, user namespaces for isolation.
cgroup (control group)Linux mechanism to limit, account, and isolate resource usage (CPU, memory, I/O, pids) for process groups.
OverlayFS (overlay2)Union filesystem that merges read-only lower layers with a read-write upper layer. Docker's default storage driver.
Copy-on-Write (CoW)Write triggers a copy of the file from lower layer to upper layer before modification. Enables layer sharing.
veth pairVirtual ethernet cable: two virtual interfaces linked together. Docker connects container netns to bridge via veth pair.
Linux capabilitiesFine-grained breakdown of root privileges into ~40 distinct units. Docker drops most by default.
seccompSecure Computing Mode. Filters system calls available to a process. Docker applies default profile blocking ~44 dangerous syscalls.
AppArmorMandatory Access Control via path-based profiles. Ubuntu/Debian Docker applies docker-default AppArmor profile.
SELinuxLabel-based MAC. RHEL/CentOS. Containers run with svirt_lxc_net_t type label.
cgroup freezercgroup subsystem that sends SIGSTOP/SIGCONT to freeze/thaw all processes. Used by docker pause/unpause.

Networking Terms

TermDefinition
Bridge networkDefault Docker network mode. Linux bridge (docker0) connects containers via veth pairs. NAT for external access.
Host networkContainer shares host network namespace. No port mapping. Highest performance, no network isolation.
Overlay networkMulti-host virtual L2 network using VXLAN encapsulation. Required for Docker Swarm services.
MacvlanAssigns unique MAC to each container. Container appears as physical device on LAN.
Embedded DNSDNS server at 127.0.0.11 in every container on user-defined networks. Resolves container/service names.
VXLANVirtual Extensible LAN. L2 tunneling over L3 (UDP/4789). Used for overlay networks.
userland proxyDocker process that proxies traffic for port publishing. Performance overhead. Can disable with userland-proxy=false.

Storage Terms

TermDefinition
Named volumeDocker-managed volume stored in /var/lib/docker/volumes/. Portable, supports drivers. Recommended for persistence.
Bind mountMounts specific host path into container. Tight coupling to host. Good for dev hot-reload.
tmpfs mountIn-memory filesystem. No persistence. Zero disk I/O. Good for secrets and temp data.
Anonymous volumeVolume created without a name (VOLUME instruction, -v /path). Hard to manage. Prefer named volumes.
Volume driverPlugin that backends Docker volumes to external storage (EBS, NFS, Ceph, GlusterFS).
Storage driverManages image layer storage on host (overlay2, aufs, devicemapper, btrfs, zfs).
upperdirThe writable layer in OverlayFS. Container writes go here. Represents the container's changes.
lowerdirThe read-only layers in OverlayFS. Stacked image layers. Never modified.

Operations / Compose Terms

TermDefinition
Docker ComposeTool for defining multi-container apps in compose.yaml. Manages service dependencies, networks, volumes.
ServiceIn Compose/Swarm: a definition of a container including image, ports, volumes, replicas.
ReplicaA running instance of a Swarm service. Multiple replicas provide redundancy and load distribution.
HealthcheckPeriodic command to determine container health (healthy/unhealthy/starting). Affects Compose depends_on and Swarm scheduling.
Docker SwarmDocker's built-in orchestrator. Cluster of Docker nodes, overlay networking, service scheduling, secrets management.
Manager nodeSwarm node that holds cluster state (Raft consensus), schedules services. Minimum 3 for HA.
Worker nodeSwarm node that runs service tasks (containers). No cluster state. Can scale horizontally.
StackDocker Swarm equivalent of a Compose project. Deployed with docker stack deploy -c compose.yaml stackname.
Live restoredaemon.json option: containers continue running if dockerd crashes/restarts. Requires containerd-shim.
Multi-stage buildDockerfile with multiple FROM statements. Earlier stages (builders) provide artifacts COPY'd to final stage.

Security Terms

TermDefinition
Privileged container--privileged: gives container almost all host capabilities and disables seccomp. Major security risk. Avoid.
Rootless DockerDocker daemon runs as non-root user. Requires user namespaces. Container escape has no host root access.

Docker ScoutDocker's vulnerability scanning service. Integrates with Docker Hub and Docker CLI.
no-new-privileges--security-opt no-new-privileges prevents setuid escalation inside container.
Docker BenchCIS Docker Benchmark security audit tool. Checks daemon config, container config, image security.
Container escapeExploitation that moves a process from container namespace to host namespace. Enabled by misconfig or kernel CVEs.
