Q1 You mention HPA and Pod Disruption Budgets. Walk me through how you configured HPA for one of your production services. What metrics did you scale on and why?
Must Know▼
▶ Strong Answer
For our main API service handling user requests, I configured HPA targeting CPU utilization at 70% threshold with minReplicas: 2 and maxReplicas: 10. I chose CPU as the primary metric because the service was compute-bound (JSON processing, encryption). The config looked like:
  • targetCPUUtilizationPercentage: 70 — staying below 80% gives headroom before scale-out latency kicks in

Q2 Explain your blue-green vs rolling deployment strategy. How did you decide which to use for which service?
Must Know▼
▶ Strong Answer
Rolling deployments were the default for stateless services where gradual traffic shift was acceptable — Kubernetes handles this natively via strategy: RollingUpdate with maxSurge and maxUnavailable tuning. For most microservices, this meant zero-downtime with minimal resource overhead.

Blue-Green was reserved for services with breaking API changes or database schema migrations — situations where a gradual rollout would cause version mismatch errors. Implementation via Helm: maintain two Deployments (blue/green), switch the Service selector between them. The inactive environment acts as immediate rollback.

Decision factors: API compatibility, stateful data, blast radius of failure, and rollback time requirements. Blue-green costs 2x compute temporarily but gives instant rollback.

Key concepts for every technology on your resume. These are the "what and why" questions that screen out candidates who only know the "how."

Kubernetes Fundamentals
K1 What happens when you run kubectl apply -f deployment.yaml? Describe every step from API call to running pod.
Must Know▼
▶ Strong Answer
  • 1. kubectl → API Server: kubectl serializes the YAML to JSON, sends HTTP request to kube-apiserver with your kubeconfig credentials. API server authenticates (certificate/token), authorizes (RBAC), and validates the manifest against the OpenAPI schema
  • 2. Admission Control: Mutating admission webhooks can modify the object (e.g., inject sidecar, add default resource limits). Validating admission webhooks reject if policy violated (OPA/Gatekeeper, Pod Security Admission)
  • 3. etcd persistence: The Deployment object is written to etcd as the desired state
  • 4. Deployment Controller (kube-controller-manager): watches for Deployment objects, calculates the diff between desired and current state, creates/updates the underlying ReplicaSet
  • 5. ReplicaSet Controller: ensures correct number of Pods exist, creates Pod specs
  • 6. Scheduler: watches for unscheduled Pods, evaluates nodes using filtering (Taints/Tolerations, NodeAffinity, resource availability) and scoring algorithms, assigns Pod to a Node by writing to etcd
  • 7. kubelet (on the target node): watches for Pods assigned to its node, calls container runtime (containerd/CRI) to pull image and start containers, reports status back to API server
  • 8. CNI plugin: assigns Pod IP, sets up network namespace and routes
  • 9. kube-proxy: updates iptables/IPVS rules if Services are involved
K2 Explain the difference between liveness, readiness, and startup probes. When would misconfiguring one cause a production outage?
Must Know▼
▶ Strong Answer
  • Liveness probe: "Is the container stuck/deadlocked?" Failure → container is restarted. Misconfiguration risk: too aggressive thresholds on a slow-starting app will cause infinite restart loops (CrashLoopBackOff) in production
  • Readiness probe: "Is the container ready to receive traffic?" Failure → pod is removed from Service endpoints (no traffic routed to it) but NOT restarted. Misconfiguration risk: if your readiness probe checks a downstream dependency that's temporarily unavailable, ALL pods fail their readiness probe and the Service routes to zero endpoints — complete outage even though the app itself is healthy
  • Startup probe: "Has the container finished initial startup?" Disables liveness/readiness until startup succeeds. Use for slow-starting apps (JVM, large data loads) to prevent premature liveness failures
Real outage scenario: Readiness probe hitting a database health check endpoint. DB has a transient spike → all pods become unready → 100% traffic drop → users see 503s. Fix: readiness probe should check local app health only, not external dependencies.
K3 What is a Pod Disruption Budget and why is it critical in a production cluster during node maintenance?
Must Know▼
▶ Strong Answer
A PDB defines the minimum number or percentage of pods of an application that must remain available during voluntary disruptions (node drain, cluster upgrade, manual eviction).

Without PDB: kubectl drain node-1 during a cluster upgrade could evict ALL replicas of a service if they happen to be on that node, causing complete downtime.

With PDB (minAvailable: 1): the drain operation will wait/block until at least 1 pod is running elsewhere before evicting the last pod on the draining node.

Important: PDB only applies to voluntary disruptions — not node crashes (involuntary). It does NOT protect against hardware failure. Also, PDB can cause cluster upgrades to hang indefinitely if your cluster is undersized — you must have enough capacity to reschedule pods before draining.
K4 How does Kubernetes networking work? How does a pod on Node A communicate with a pod on Node B?
Must Know▼
▶ Strong Answer
Kubernetes networking follows three rules: every pod gets a unique cluster-wide IP, pods on the same node can communicate without NAT, pods on different nodes can communicate without NAT.

Implementation (e.g., Flannel/Calico/Cilium — CNI plugins):
  • Each node gets a subnet (e.g., Node A: 10.244.0.0/24, Node B: 10.244.1.0/24)
  • Pod on Node A (10.244.0.5) → traffic hits the node's virtual ethernet bridge → routed to the VXLAN overlay tunnel (Flannel) or BGP route (Calico) → arrives at Node B's bridge → delivered to Pod B (10.244.1.8)
  • Services add a virtual IP (ClusterIP) that kube-proxy translates to Pod IPs via iptables/IPVS DNAT rules
In your DOKS cluster specifically, the CNI is likely Cilium (DigitalOcean's default), which uses eBPF instead of iptables for better performance.
Helm Fundamentals
H1 What is the difference between helm upgrade --install and helm install? How does Helm track release state?
Must Know▼
▶ Strong Answer
helm install creates a new release and fails if the release name already exists. helm upgrade --install is idempotent — it creates if not exists, upgrades if exists. This is the correct flag for CI/CD pipelines because the first deployment and all subsequent ones use the same command.

State tracking: Helm stores release state as Kubernetes Secrets (by default) in the target namespace. Each release revision is stored as a separate Secret with the full rendered manifests and metadata. This is how helm rollback works — it retrieves the previous revision's Secret and re-applies it. helm history [release] lists all revisions from these Secrets.

Common gotcha: if you manually edit Kubernetes resources managed by Helm, the next helm upgrade will overwrite your changes — this is why GitOps discipline is critical.
H2 How did you structure your Helm charts for multi-environment deployments (dev/staging/prod)?
Must Know▼
▶ Strong Answer
Pattern used: a single chart with environment-specific values files:
  • values.yaml — base defaults (image repository, default resource limits, service type)
  • values-dev.yaml — lower resource requests, debug logging enabled, single replica
  • values-staging.yaml — production-like config, reduced replicas, feature flags enabled
  • values-prod.yaml — full replicas, production resources, PDB enabled, HPA enabled, real secret references
Deploy command: helm upgrade --install myapp ./chart -f values.yaml -f values-prod.yaml -n production

For secrets: environment values files reference Kubernetes secret names (not the values themselves). Actual secrets are managed separately via Sealed Secrets or external-secrets-operator pulling from a secrets manager — never stored in Helm values files committed to Git.
Docker Fundamentals
D1 Explain Docker image layers. How do you optimize a Dockerfile for build cache efficiency and minimal image size?
Must Know▼
▶ Strong Answer
Each Dockerfile instruction creates a read-only layer. Docker caches layers and only rebuilds from the first changed instruction downward.

Optimization principles:
  • Order by change frequency — put rarely-changing instructions first (OS base, system deps) and frequently-changing ones last (app code COPY). This maximizes cache reuse
  • Multi-stage builds — separate build-stage (includes compiler, dev tools) from runtime-stage (includes only the binary/artifact). Reduces final image from ~800MB to ~50MB for Go apps, for example
  • Minimal base images — use distroless or alpine variants. Reduces attack surface AND image size
  • Combine RUN commands — RUN apt-get update && apt-get install -y pkg && rm -rf /var/lib/apt/lists/* creates one layer instead of three and cleans up the package cache in the same layer
  • .dockerignore — exclude node_modules/, .git/, test files from build context. Reduces context transfer time
In CI, use --cache-from with registry-based caching or GitHub Actions cache to persist layers between pipeline runs.
AWS Fundamentals
A1 You mention IAM with least-privilege. Walk me through how you would design IAM roles for an application running on EC2 that needs to access S3 and write to DynamoDB.
Must Know▼
▶ Strong Answer
Correct approach — IAM Role (not user keys):
  • Create an IAM Role with a Trust Policy allowing ec2.amazonaws.com to assume it (EC2 instance profile)
  • Attach an inline or managed policy with ONLY the needed permissions: s3:GetObject, s3:PutObject on the specific bucket ARN (arn:aws:s3:::my-bucket/*), and dynamodb:PutItem, dynamodb:GetItem on the specific table ARN
  • Attach the role as an EC2 instance profile — the app uses the metadata endpoint (169.254.169.254) to get temporary credentials automatically via the AWS SDK

Least privilege checklist: No wildcards on resource ARNs, no * on actions, no Administrator policy, separate roles per application, log all API calls via CloudTrail.

Linux Fundamentals
L1 A production pod is experiencing high CPU on a Linux node. Walk me through your diagnosis process.
Must Know▼
▶ Strong Answer
Step-by-step diagnosis:
  • 1. Confirm scope: kubectl top nodes and kubectl top pods -A — identify which pod/node is the culprit
  • 2. Node-level inspection: ssh to the node, run top or htop → sort by CPU. Identify PID of the container process
  • 3. Container process: ps aux --sort=-%cpu | head -20 to see top CPU consumers. cat /proc/[PID]/status for process details
  • 4. Is it CPU throttling vs actual high usage? Check container resource limits: cat /sys/fs/cgroup/cpu/cpu.stat — if nr_throttled is high, the container is hitting its CPU limit and being throttled, not necessarily running a hot loop
  • 5. Application profiling: For JVM — kubectl exec -it pod -- jstack [pid] for thread dump. For Node.js — V8 profiler. For Go — pprof endpoint
  • 6. Check recent changes: helm history [release], recent code deploys, traffic spike in Grafana
Common root causes at your stack level: CPU limits set too low causing throttling, inefficient queries causing CPU-heavy serialization, GC pressure, N+1 query patterns.
Prometheus & Grafana
P1 Explain how Prometheus scraping works. What is a ServiceMonitor and how does it differ from a scrape config?
Must Know▼
▶ Strong Answer
Prometheus uses a pull model — it periodically scrapes (HTTP GET) configured targets' /metrics endpoints and stores the time-series data locally.

Traditional scrape config (in prometheus.yml): manually specify targets as static IPs or use service discovery configs. Static and doesn't integrate with Kubernetes dynamic service discovery natively.

ServiceMonitor (Prometheus Operator CRD): a Kubernetes-native way to configure scraping. You define a ServiceMonitor resource that selects Services by label. The Prometheus Operator watches ServiceMonitor objects and automatically generates the corresponding scrape configs in Prometheus. This means you can deploy a new microservice with a Service and a ServiceMonitor and Prometheus automatically starts scraping it — no manual config changes.

ServiceMonitor is the correct approach in production Kubernetes — it integrates with GitOps workflows (the ServiceMonitor lives alongside the app's Helm chart), is dynamically updated, and eliminates manual config drift.
P2 Write a PromQL query to calculate the 99th percentile request latency for an HTTP service over the last 5 minutes.
High Prob▼
▶ Strong Answer
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))

Breakdown:
  • http_request_duration_seconds_bucket — histogram metric with le (less-than-or-equal) labels for each bucket boundary
  • rate(...[5m]) — calculates per-second rate over 5 minutes to smooth out spikes
  • sum(...) by (le, service) — aggregate across replicas, keeping le and service labels
  • histogram_quantile(0.99, ...) — estimates the 99th percentile from the histogram buckets
Also useful: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) for error rate percentage.

SC2 SCENARIO: A new deployment is complete. 10 minutes later, error rate climbs from 0.1% to 8%. The deployment seems fine. What do you investigate?
Must Know▼
▶ Strong Answer
The "10 minutes later" is a significant clue — immediate deployment failures show up in readiness probes. Delayed errors suggest:
  • Warm cache expiry: the new code is hitting cold cache paths not exercised in smoke tests
  • Database connection pool exhaustion: new code version opens more connections, pool fills up after traffic builds
  • Memory leak: GC pressure builds over time, JVM/Node heap grows, then GC pauses cause timeouts
  • External dependency rate limits: new feature calling a third-party API hitting rate limits after brief normal period
  • Background job interaction: a scheduled job in the new version conflicting with live traffic
Investigate: Loki logs for specific error types (|= "timeout", |= "connection refused"), Grafana memory/connection graphs trending upward, check downstream service error rates too. Compare the error pattern — is it uniform (suggests dependency) or gradually increasing (suggests resource leak)?
SC3 SCENARIO: Your Kubernetes cluster is running out of disk space on nodes. Pods are being evicted. How do you respond?
High Prob▼
▶ Strong Answer
Immediate (stop the bleeding):
  • kubectl describe node [node-name] — check conditions section for DiskPressure: True
  • Identify culprits: du -sh /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/* — dangling image layers
  • crictl images — list all images on node. Run crictl rmi --prune to remove unused images immediately
  • Check for runaway logs: du -sh /var/log/containers/* — a pod printing to stdout at extremely high rate fills the overlay filesystem

  • No image GC policy (kubelet GC thresholds not configured)

⚙️ Practical Production Questions

Questions asked by experienced engineers who care about real production judgment, not textbook answers.

PP1 How do you handle secrets in a GitOps workflow? Your Helm values are in Git — how do you avoid committing credentials?
Must Know▼
▶ Strong Answer
Multiple approaches, layered by team maturity:
  • Sealed Secrets (Bitnami): Encrypt secrets with the cluster's public key using kubeseal. Encrypted SealedSecret objects are safe to commit to Git — only the cluster's private key can decrypt them. GitOps-native, works well with ArgoCD
  • External Secrets Operator: Kubernetes controller that syncs secrets from external vaults (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager) into Kubernetes Secrets. The Git repo stores an ExternalSecret resource (safe to commit) that references secret paths, not values
  • GitHub Actions secrets: For CI pipelines, never inject secrets via values files. Pass them as GitHub Secrets → environment variables → --set key=value at deploy time, not stored in files
  • What NOT to do: Store base64-encoded secrets in Kubernetes Secret YAML files committed to Git. Base64 is not encryption — it's just encoding
In production: External Secrets Operator pulling from a secrets manager is the most enterprise-ready approach. Sealed Secrets is excellent for smaller teams without a dedicated vault.
PP2 What's your strategy for Kubernetes resource requests and limits? Why do you not just set limits high to avoid OOM kills?
Must Know▼
▶ Strong Answer
Requests vs Limits distinction:
  • Requests: what the pod is guaranteed — used by the scheduler to decide which node can fit the pod. Sets the QoS tier
  • Limits: the maximum the pod can use. CPU limit → throttling. Memory limit → OOMKill
Why not set limits high?
  • The scheduler uses requests for bin-packing decisions. If requests are 100m CPU but limits are 4 CPU, the scheduler thinks the pod needs 100m — it may pack 40 such pods on a node that actually can't handle 40 × 4 CPU bursts simultaneously. This causes cascading CPU throttling
  • Memory: if all pods set high memory limits but low requests, a memory spike in one pod steals memory from other pods on the same node, potentially causing OOMKills across unrelated services
Practical strategy: Set requests based on steady-state average usage (from Prometheus metrics + VPA recommendations). Set limits at 2-3x requests for memory (to handle spikes), and for CPU consider not setting a hard limit or setting it much higher — CPU throttling is often worse than slightly overusing CPU temporarily. Use Vertical Pod Autoscaler (VPA) in recommendation mode to continuously refine these values.
PP3 How do you perform a zero-downtime Kubernetes cluster version upgrade in production?
High Prob▼
▶ Strong Answer
For a managed cluster (DOKS/EKS — your environments):
  • Pre-upgrade: Read the Kubernetes changelog for deprecated APIs. Check all deployed Helm charts and manifests for deprecated API versions (kubectl convert or pluto tool). Remove all deprecated APIs before upgrading
  • Verify PDBs: Ensure critical services have PodDisruptionBudgets set — without these, node drains can cause downtime
  • Control plane first: Managed clusters (DOKS) upgrade the control plane automatically or via console. Control plane upgrades are transparent to workloads in managed clusters
  • Node pool rolling upgrade: DOKS/EKS upgrades nodes by cordoning, draining one node at a time, replacing with new version. PDBs ensure minimum availability during drain. Node autoscaling must have capacity to absorb pods from draining nodes
  • Validation: After each node upgrade, verify workloads are healthy before proceeding to next node. kubectl get pods -A | grep -v Running
  • Rollback plan: If a workload breaks due to API changes, you can't easily roll back the cluster version — you must fix the workload. This is why pre-upgrade API compatibility checks are non-negotiable
PP4 Your CI pipeline is building Docker images that are 2GB. Deployments are slow and pulling takes too long. How do you fix this?
High Prob▼
▶ Strong Answer
Multi-pronged approach:
  • Multi-stage builds: Separate build dependencies (compiler, test frameworks, dev tools) from runtime. For a Java app: build stage uses maven:3.9-jdk17 (500MB), runtime stage uses eclipse-temurin:17-jre-alpine (80MB). Copy only the JAR
  • Base image audit: docker history image:tag — identify large layers. Switch ubuntu:22.04 (80MB) → alpine:3.18 (5MB) where possible. Use distroless for production (no shell, no package manager — reduces attack surface too)
  • Layer optimization: Sort Dockerfile instructions by change frequency (rarely-changing deps first). This maximizes cache reuse so CI only rebuilds changed layers
  • GitHub Actions caching: Use cache-from: type=gha and cache-to: type=gha,mode=max in docker/build-push-action. Layers are cached in GitHub's cache backend
  • Clean up in build layer: RUN pip install --no-cache-dir, npm ci --omit=dev, delete build artifacts and caches in the same RUN instruction as the install
  • Image pull policy: Set imagePullPolicy: IfNotPresent in production — don't re-pull if the image exists on the node. Use Keel or image caching proxies for faster node distribution
PP5 Explain your approach to Kubernetes RBAC. How do you set up access for a new developer joining your team?
High Prob▼
▶ Strong Answer
RBAC hierarchy: ClusterRoles/Roles (what), ClusterRoleBindings/RoleBindings (who gets what).

Developer onboarding flow:
  • Create namespace-scoped Role with minimal permissions: get/list/watch on pods, deployments, services; get on secrets (read-only, not list — listing secrets exposes all secret names); create on pods/exec (for debugging)
  • NO: delete on pods (prevent accidental deletion), no cluster-level access, no ability to modify RBAC
  • Create a RoleBinding binding the developer's identity (or a Group if using SSO) to the Role in their namespace only
  • For read-only cluster visibility (nodes, events): bind the built-in view ClusterRole at namespace scope
Real-world addition: In DOKS/EKS, integrate with your identity provider (GitHub, Google, AWS IAM) so developers authenticate with their existing credentials — no manual kubeconfig management. Use kubectl auth can-i --as [user] to verify permissions before and after.
PP6 What's the difference between ArgoCD sync and a Helm upgrade? Why would you use ArgoCD over just running helm in your CI?
Must Know▼
▶ Strong Answer
Helm in CI (push model): CI pipeline runs helm upgrade — it pushes changes to the cluster. Once the pipeline completes, there's no ongoing reconciliation. If someone manually changes a Kubernetes resource, CI doesn't detect or correct it (config drift).

ArgoCD (pull model / GitOps): ArgoCD continuously watches the Git repo AND the live cluster state. If drift is detected (manual change, accidental delete), ArgoCD can auto-sync to restore the desired Git state. It's a continuous reconciliation loop, not a one-time push.

Why ArgoCD wins for production:
  • Single source of truth: Git IS the cluster state. Any deviation is visible in ArgoCD's UI and corrected
  • Audit trail: every deployment is tied to a Git commit — you know exactly who changed what and when
  • Multi-cluster management: ArgoCD can deploy the same app to dev/staging/prod clusters from one control plane
  • Rollback = git revert: rolling back is just reverting the Git commit, not running manual helm rollback commands
  • Application health visibility: ArgoCD's UI shows the full resource tree (deployments → replicasets → pods) and their health at a glance
PP7 You have a Kafka consumer group that's falling behind — lag is growing. How do you diagnose and fix it?
High Prob▼
▶ Strong Answer
Consumer lag = messages produced - messages consumed. Growing lag means consumers aren't keeping up with producers.

Diagnosis:
  • Check consumer group lag: kafka-consumer-groups.sh --describe --group [group-name] — shows lag per partition
  • Is lag growing uniformly across all partitions (suggests consumer is too slow overall) or on specific partitions (suggests partition imbalance or a "poison pill" message causing retry loops)?
  • Check consumer CPU/memory — is the consumer resource-constrained?
  • Check for consumer rebalances: excessive rebalancing causes consumers to pause processing. Look for ConsumerGroupRebalance events in logs
Fixes by root cause:
  • Consumer too slow: Increase consumer instances (must have <= partitions, since each partition can only have one consumer in a group). Or optimize consumer processing logic (batch processing, async IO)
  • Partition imbalance: Use Kafka's partition reassignment tool to redistribute
  • Poison pill: A single malformed message causing infinite retry. Implement a dead letter queue (DLQ) for unprocessable messages
  • Producer spike: If it's a temporary spike, consumers will catch up. But if sustained, scale out consumers or increase partitions (note: partition count can only increase, not decrease)

Round 2 — Technical Screening (30 min) Must Pass
Q: What's the difference between a Deployment and a StatefulSet in Kubernetes?
Deployment: for stateless applications. Pods are interchangeable — any pod can replace another. Pod names are random (nginx-abc123). No stable storage per pod.
StatefulSet: for stateful applications (databases, Kafka, Redis). Pods have stable, ordered names (kafka-0, kafka-1). Each pod gets its own persistent volume that follows it across restarts. Scaling and rolling updates happen in order (0, 1, 2...) not randomly. Used for: databases, Kafka, ZooKeeper, Elasticsearch.
Q: What happens when a container exceeds its memory limit in Kubernetes?
The container is OOMKilled (Out of Memory Killed) by the Linux kernel. The pod's restart count increments. If the pod keeps getting OOMKilled, it enters CrashLoopBackOff. Unlike CPU (which is throttled), memory cannot be throttled — it's either available or the process is killed. Fix: increase memory limit, optimize app memory usage, or use VPA recommendations to set appropriate limits.
Q: What is a ConfigMap and when would you use it over an environment variable?
ConfigMap stores non-sensitive configuration data as key-value pairs or files. Use ConfigMap when: configuration is shared across multiple pods, configuration needs to be updated without rebuilding the image, or configuration is complex enough to warrant a file format (e.g., nginx.conf, app.properties). Environment variables in the pod spec are simpler for single-pod, simple config. Key difference: ConfigMap changes can be mounted as volumes and some apps can hot-reload them without pod restart — env vars require pod restart to pick up changes.
Q: Explain what happens during a kubectl drain node operation.
kubectl drain does two things: (1) cordons the node (marks it unschedulable so no new pods land on it), (2) evicts all pods on the node. Eviction respects PodDisruptionBudgets — if evicting a pod would violate a PDB, the drain waits or fails. DaemonSet pods are not evicted by default (use --ignore-daemonsets). Static pods are also skipped. After drain, the node is safe for maintenance — no workloads running on it. After maintenance, kubectl uncordon node makes it schedulable again.

Q: How does TLS termination work in your Kubernetes ingress setup? Where is the certificate stored?
In our setup with nginx-ingress and cert-manager:
  • cert-manager watches for Certificate or annotated Ingress resources requesting TLS
  • cert-manager requests a certificate from Let's Encrypt via ACME DNS-01 challenge (creates a TXT record via Cloudflare DNS API to prove domain ownership)
  • Let's Encrypt issues the certificate; cert-manager stores it as a Kubernetes Secret of type kubernetes.io/tls in the target namespace
  • The Ingress resource references this Secret in spec.tls.secretName
  • nginx-ingress controller reads the Secret, loads the cert into nginx configuration, and terminates TLS at the ingress — all traffic between ingress and backend pods is HTTP (within the cluster's trusted network)
  • cert-manager auto-renews certificates 30 days before expiry

  • Set SLOs per service: e.g., "99.5% of requests return 2xx within 500ms over a 30-day rolling window"
  • Error budget: if SLO is 99.5%, error budget is 0.5% — that's ~3.6 hours of downtime per month. Track error budget burn rate
  • Prometheus + recording rules to calculate SLI: sum(rate(http_requests_total{code=~"2.."}[5m])) / sum(rate(http_requests_total[5m]))
  • Grafana SLO dashboard with burn rate alerts: alert when error budget is burning at 14x the normal rate (will exhaust budget in 1 hour) and 6x rate (will exhaust in 6 hours)
  • Post-incident: every incident that consumed error budget gets a post-mortem. Error budget depletion gates feature deployments — if budget is exhausted, reliability work takes priority over new features
